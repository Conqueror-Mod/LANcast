====================================================================
WHAT I PICKED AND WHY
====================================================================
The roadmap's feature backlog listed "Activity status in the UI" with an
unusually precise note: the pieces already exist behind
/api/libraries/{id}/scan, /api/enrich and /api/probe, and what is missing is
one place in the UI that surfaces them.

That note understated it. Every worker had a status endpoint, but a client that
wanted to show "what is the server doing" had to know the entire roster of
workers and poll the scan endpoint once per library. So no client showed
anything. This is the same shape as the "?profile= shipped and no caller ever
used it" lesson already recorded in the roadmap: the capability existed and the
caller could not reasonably exist.

It was also the right size for one unattended session — additive API, no schema
change, no migration, no ADR needed, and nothing destructive.

Explicitly avoided: anything touching add-ons/plugins, per instruction.

WHAT I BUILT
====================================================================
Server
  internal/api/activity.go       (new)
  internal/api/activity_test.go  (new)
  internal/api/server.go         (+1 route)

  GET /api/activity  ->  { "active": bool, "tasks": [ ... ] }

  Every worker — scan, enrich, probe, coverart, transcode — is normalized into
  one shape: kind, id, title, state, done, total, detail, library_id,
  started_at, error. Design decisions worth reviewing:

  * title is resolved server-side. A scan says "Scanning Films", so a client
    rendering the row never has to join a library id back to a name.
  * total = 0 means indeterminate, and that is honest rather than lazy: a scan
    knows how many files it has seen and never how many it will see. The client
    draws a sweep and a count instead of inventing a percentage.
  * only running and failed are listed. A finished task is not activity.
  * a FAILED SCAN STAYS LISTED. The roadmap's own retrospectives say the same
    thing four times over: the serious bugs in this project were invisible, not
    loud. This gives that class of failure somewhere to appear.
  * nothing is persisted. A restarted server reports idle, which is the truth —
    the workers are in-process and a restart ended their work.
  * reading progress needs no special role; the endpoints that START work
    (scan, probe/refresh) remain admin-only. Unchanged.

  Gathering worker state and shaping it are split into snapshot{} and
  buildActivity(). That follows the existing probe.ParseJSON precedent in
  CLAUDE.md: the shaping rules are then testable against fixtures with no
  worker running and no media on disk. This mattered in practice — see
  "one thing I got wrong" below.

Client
  web/src/components/ActivityPanel.tsx   (new)
  web/src/components/ActivityPanel.css   (new)
  web/src/api/types.ts, hooks.ts, components/AppShell.tsx  (edited)
  internal/web/dist/                     (rebuilt and committed, per convention)

  A pulsing dot + label in the nav, and a popover listing each task with a
  progress bar. Design rules I held to:
  * NO GOLD anywhere except the trigger's :focus-visible ring. This is "what
    the server is doing", not "where you are". Progress uses --nebula-blue,
    failure uses --danger.
  * the indicator is absent entirely when the server is idle. A status light
    that is always lit tells you nothing.
  * .activity__row carries flex-shrink: 0 — the scrollable-column trap from the
    global rules, set up front rather than diagnosed later.
  * prefers-reduced-motion disables both the pulse and the sweep.
  * Escape and outside-click close the popover.

  Polling: 8s idle, 1.5s while active. This is a deliberate exception to the
  codebase's "do not poll forever" comment on useProbeStatus, and the reason is
  in the hook's comment: an indicator that only updates when you open it is not
  an indicator. React Query stops the interval when the tab is hidden, so an
  idle machine still idles.

====================================================================
ONE THING I GOT WRONG, AND ONE FALSE ALARM
====================================================================
1. My first test asserted a failed scan by pointing a library at a directory
   that does not exist. It never failed — the scanner records an unreadable
   path as an Issue and carries on, which is correct behaviour and exactly the
   "scanning marks missing, never deletes" rule. Rather than contrive a
   failure, I split gathering from shaping and tested the shaping against
   fixtures. Better test, and it matches the probe precedent already in the
   codebase.

2. Mid-session I thought I had found a real bug: the client appearing to ignore
   -data and starting a server on an empty second database, which is precisely
   the v0.4.1 bug. It was not. It was my own PowerShell quoting — the path with
   spaces was split, and "D:\My" became a data directory. NOT A PRODUCT BUG.
   I deleted the four stray files and the D:\My directory it created; nothing
   else on D:\ was touched, and D:\My Projects is intact and untouched.
