# ADR 0036 — The EPG: XMLTV, and matching on `tvg-id` alone

Date: 2026-08-16 · Status: accepted

## Context

Live TV shipped as channels: a name, a logo, a group and a URL, playable in any
browser through the ffmpeg pipeline ([ADR 0013](0013-transcode-pipeline.md)).
Both the roadmap and `docs/api.md` closed that section with the same sentence —
*a channel list carries names and logos, not a schedule* — which is a
description of the gap, not a design for filling it.

A guide raises four questions that are each capable of being answered wrongly in
a way that looks fine until somebody watches television with it.

## Decision

### XMLTV, and only XMLTV

Every IPTV provider, every tuner backend (tvheadend, Jellyfin's own grabber) and
every grabber in the `xmltv` project emits it. There is no second format worth
the parser.

The document is read with a **streaming token decoder**, not `xml.Unmarshal`. A
fortnight of listings for six hundred channels is a genuinely large file —
hundreds of megabytes uncompressed — and unmarshalling the document would hold
the parsed tree *and* every resulting programme in memory at once. Gzip is
unwrapped by sniffing the magic number rather than trusting the URL suffix or
the content type, because providers serve `.gz` files as `text/plain` and plain
XML from URLs ending `.gz` about equally often. A label that is wrong half the
time is worse than no label.

### Listings match channels on `tvg-id`, and on nothing else

This is the decision that matters, and it is a decision to **refuse a feature**.

The M3U and the XMLTV file are separate documents with no shared identity except
the optional `tvg-id` attribute. Where it is present, the join is exact. Where
it is absent, the obvious fallback is to match on display name — and that
fallback is refused.

"BBC One" and "BBC One HD" are different channels with different schedules and
names that differ by two characters. Name matching attaches one's listings to
the other with confidence, and **the failure is invisible from the guide**: the
programme titles are plausible, the times are plausible, and the only way to
discover it is to watch a channel and find that what is on is not what the guide
said. Every other match in this system can be inspected — a film matched to the
wrong TMDB entry has a poster you can see is wrong. A mis-attached schedule
looks exactly like a correct one.

So a channel with no `tvg-id` has no listings, and the UI says so in those
words. That is a limit of the playlist, stated, rather than a guess presented as
an answer. It is the same argument as the one in `internal/media`: guessing is
allowed exactly where it can be checked.

The match *is* case-insensitive, because providers publish `bbcone.uk` in the
playlist and `BBCOne.uk` in the guide often enough that a case-sensitive join
loses whole lineups to a shift key. That is a spelling difference, not an
identity guess.

### A programme is not a `media_item`, and the guide is replaced wholesale

[ADR 0002](0002-one-wide-media-item-table.md) chose one wide table for things that are
*works*. A channel already was not one; a programme is not one twice over. There
are hundreds of thousands of them, none of them is playable, and putting a
fortnight of listings into the table that carries watch state and field locks
would mean half a million rows on the hot path of every library query.

Listings are replaced, never merged — the same argument as the channel list, and
stronger. An XMLTV programme carries no id at all, so "the same programme,
updated" is not something this data can express, and a merge would double every
entry on every refresh.

The consequence is an **ordering constraint**: `epg_program.channel_id`
references `channel` and cascades, so replacing a source's channels discards its
guide. A refresh must import the channel list first and the guide second. The
other order produces an empty guide and no error anywhere to explain it, which
is why it has a test in the store *and* one in the API rather than a comment.

Resolving the XMLTV id to a channel id **at import** rather than storing the raw
id and joining at read time follows from the same place: every guide query would
otherwise carry a string join, and listings for channels nobody subscribes to
would be stored for ever.

### The guide refreshes itself; libraries do not

Periodic library scanning is opt-in and off by default, and the guide refresh is
unconditional and on. The asymmetry is deliberate.

A rescan has visible consequences an operator may not want on a timer — items
appearing and disappearing while somebody is browsing. A guide has the opposite
property: **doing nothing is what breaks it.** An unrefreshed guide does not go
blank, it goes *wrong*, and states with total confidence that last Tuesday's
programme is on now. It is the only thing in LANcast that decays into a
falsehood by being left alone.

Twelve hours, because providers publish once a day and carry a week or a
fortnight ahead; hourly would buy nothing but the provider's attention. Listings
are pruned a day after they end rather than the moment they do, so "what was on"
stays answerable for the length of a day.

### A list, not a grid

The UI shows now/next on each channel tile and a **schedule list** under the
player, rather than the channels-down/hours-across grid a television draws.

That grid is right for a remote control and wrong for a browser: it needs
horizontal scrolling, a time ruler, and a column width that makes a three-minute
news bulletin unreadable. What somebody actually asks, sitting in front of a
channel they are already watching, is "what is this, and what is after it" —
which is a list, and costs one request for one channel instead of a fortnight
for six hundred.

## Consequences

- Channels without `tvg-id` never get listings. This is visible and explained,
  and it is the price of never being confidently wrong about what is on.
- The guide is a second import with a second failure mode, reported separately
  from the channel list's: a working list with a broken guide is a usable Live
  TV, and one error field for both would make the channels look broken.
- `internal/livetv` now holds two parsers for two formats from the same feature.
  They share nothing, because they have nothing in common but the word "list".
- Search on the Live TV page reads programme titles as well as channel names,
  which is the question a guide exists to answer. It covers only now and next,
  because that is what the client holds; searching the fortnight is a server
  query and a different feature.
