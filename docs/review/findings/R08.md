## R08-1 A tiny comic or picture file kills the server, and a comic keeps killing it at every start

- **Severity:** S1
- **Class:** C3
- **Confidence:** high
- **Where:** `internal/comic/cover.go:129` (`image.Decode` of the first page), `internal/photo/photo.go:109` and `:135` (`image.Decode` of a library picture, and of ffmpeg's PNG)
- **Failure:** A `.cbz` whose first page is a PNG that declares 1,000,000 × 1,000,000 pixels is 204 bytes. The cover worker decodes it. Go's PNG decoder allocates the whole pixel buffer from the header before reading any data, so it asks for 4 TB and the runtime throws `fatal error: out of memory`. That is not a panic: no defer runs and nothing can recover it, so the process exits. `CoverWorker.one` marks the item checked in a defer, which never runs, so the comic is still pending at the next start, where the cover worker is started again (`internal/serverapp/main.go:793`) and the server dies again. The same header in a `.png` in a picture library takes down the photo worker the same way. A JPEG can declare 65535 × 65535 (about 6 GB for YCbCr) for the same effect on a smaller machine. `internal/picture` already does this correctly: it reads `image.DecodeConfig` and refuses past `MaxPixels` before decoding.
- **Evidence:** a proving test, run in the worktree and not committed:

  ```go
  // internal/comic/zz_bomb_test.go: builds a .cbz holding one PNG with an
  // IHDR of 1000000 x 1000000 RGBA and a five-byte IDAT, then calls Cover.
  ```

  ```
  === RUN   TestZZCoverHugePNG
      zz_bomb_test.go:45: archive is 204 bytes
  runtime: VirtualAlloc of 4000000000000 bytes failed with errno=1455
  fatal error: out of memory
  ```

  With `0x7fffffff × 0x7fffffff` the decoder refuses with `dimension overflow`. Its only guard is integer overflow, not size.
- **Fix sketch:** Run `image.DecodeConfig` first and refuse anything past a pixel limit (reuse `picture.MaxPixels`, or a shared constant) before every `image.Decode` of a file from a library: comic cover, photo, and photo-after-ffmpeg. In `artwork.Cache.Put`, refuse an over-limit image too, so `resize` never decodes one. Also read the photo with a size cap instead of `os.ReadFile`.
- **Verdict:** CONFIRMED. The test reproduces the fatal error. The cover worker has no `recover` (`grep recover()` finds none in the slice), and a fatal OOM cannot be recovered anyway. The photo path calls the same `image.Decode` with no `DecodeConfig` check in front of it.
- **Triage:** Fixed and merged in #1121.

## R08-2 Emptying the trash after a scan deletes everything under a folder the walk could not read

- **Severity:** S1
- **Class:** C4
- **Confidence:** high
- **Where:** `internal/scan/trash.go:41` (`MayEmptyTrash`), `internal/scan/scanner.go:792-800` (the walk skips an unreadable directory), `:1006-1012` (unseen files marked missing)
- **Failure:** With `empty_trash_on_scan` on, a scan where one directory inside a readable location fails to list deletes every row under that directory. Causes include an ACL that refuses the service account, an SMB hiccup on one folder, or a folder being renamed mid-walk. The walk records an `unreadable` Issue and returns `SkipDir`, as designed. Every known file under that folder is then unseen and marked missing. The root re-stat passes, so `MayEmptyTrash` allows the empty: it checks only failed, cancelled, skipped roots and `FilesSeen == 0`, never `Skipped` or the Issues. `EmptyTrash` then deletes those rows with their watch history, positions and ratings. The setting's own documentation (`docs/api.md`, `empty_trash_on_scan`) promises that a scan that "could not read one of its locations" leaves rows alone. A sub-folder is the same failure one level down.
- **Evidence:** a proving test, not committed:

  ```go
  p := Progress{State: StateIdle, FilesSeen: 120, ItemsMissing: 40, Skipped: 1,
      Issues: []Issue{{Path: "Films (B-D)", Reason: "unreadable"}}, RootsScanned: 1}
  MayEmptyTrash(p) // {Allowed:true Reason:}
  ```

  `fs.WalkDirFunc` documents the second call with the `ReadDir` error, which is the branch at `scanner.go:792`.
- **Fix sketch:** Refuse in `MayEmptyTrash` when the scan recorded any `unreadable` directory, which needs a count of unreadable directories on `Progress` beside `Skipped`. A narrower fix is to empty only rows that went missing in a scan with no unreadable directory above them.
- **Verdict:** CONFIRMED. The verdict function allows it (test above). Nothing between the walk and `EmptyTrash` (`scanner.go:473-483`) looks at Issues. The setting is off by default, which bounds the reach but does not change the severity class: rows are deleted on the condition the setting promises to refuse.
- **Triage:** Fixed and merged in #1116.

## R08-3 Film and show titles in a non-Latin script never match, even exactly

- **Severity:** S2
- **Class:** C14
- **Confidence:** high
- **Where:** `internal/meta/score.go:455` (`normalize`), used by `titleScore` at `:442`
- **Failure:** `normalize` keeps only `a-z`, `0-9` and spaces after `SortTitle`. A filename `七人の侍 (1954).mkv` or `Брат (1997).mkv` normalizes to `""`, and `titleScore` returns 0 against every candidate, including the identical title TMDB returns in the library's own language (ADR 0123). The film can never pass the auto-apply threshold on its title and lands unmatched or in review. Accented Latin letters are dropped, not folded, so `Léon` becomes `lon` and scores 0.925 against `Leon`. The same fault was found and fixed for music in `albumText` (`score.go:178-200`, ADR 0115), whose comment names it. Film and TV were left on the old normalizer.
- **Evidence:** a proving test, not committed:

  ```
  "七人の侍" vs "七人の侍": normalize="" titleScore=0.000
  "Брат" vs "Брат": normalize="" titleScore=0.000
  "Léon" vs "Leon": normalize="lon" titleScore=0.925
  ```
- **Fix sketch:** Have `normalize` keep `unicode.IsLetter`/`IsDigit` the way `albumText` does, and fold diacritics (NFD, then drop combining marks) so `Léon` = `Leon`. Rerun the scoring tests, since the threshold was tuned against the old output.
- **Verdict:** CONFIRMED. The test shows a zero for identical strings. `OtherTitles` (`score.go:434`) goes through the same `normalize`, so an original-language alternative does not rescue it.
- **Triage:** Fixed and merged in #1130.

## R08-4 A locked playlist's membership is overwritten when the lock check errors or races

- **Severity:** S2
- **Class:** C4
- **Confidence:** high
- **Where:** `internal/scan/playlists.go:90-106` (`skipLockedPlaylist`), `internal/playlist/import.go:56-110` (`ImportFile`)
- **Failure:** The importer skips an `.m3u` whose playlist carries a `members` lock. But `skipLockedPlaylist` returns "not locked" when either `ItemIDByPath` or `LockedFields` fails, and the import then calls `SetPlaylistEntries`, which replaces the playlist a person edited with the file's lines. The comment says re-importing is "recoverable". It is not: the human edit is gone, and that is the decision CLAUDE.md says a rescan may never re-litigate. A transient `SQLITE_BUSY` during a scan, which the project already sees on CI (`TestScanReconcileRacesBackgroundWrites`), is enough. Separately, the check and the write are not in one transaction, so an edit made while the scan is importing is overwritten too.
- **Evidence:** the code at `playlists.go:91-98`; `ImportFile` has no lock check of its own.
- **Fix sketch:** Fail closed: on any lookup error, skip this file for this scan and record an Issue. Better, move the lock check into the store write, so the statement that replaces entries refuses when a `members` lock exists, in the same transaction.
- **Verdict:** PLAUSIBLE. The mechanism is certain, but it needs a database error or a race in a narrow window, so it is S2 rather than S1 despite the charter's "locked decision" wording. Raise it to S1 if triage counts any path to an overwritten lock as S1.
- **Triage:** Fixed and merged in #1139.

## R08-5 With "write NFO" on, every season folder gets a `tvshow.nfo` that describes a film

- **Severity:** S3
- **Class:** other
- **Confidence:** high
- **Where:** `internal/meta/nfo/nfo.go:536` (`sidecarPath`), `:510` (`rootElement`); written from `internal/enrich/enrich.go:540`
- **Failure:** For a season whose row path is its `Season 01` folder (`media.SeasonDir`), `sidecarPath` gives `Season 01/tvshow.nfo`, and `rootElement` has no season case, so the file's root is `<movie>`. `fetchSeason` returns `StateMatched`, so every matched season with a real folder is written. The result is a `tvshow.nfo` holding `<movie><title>Season 1</title>…` inside each season folder of the user's library. Kodi and Jellyfin read `tvshow.nfo` as "this folder is a show", which can split one series into one show per season in the tools LANcast is meant to coexist with. The convention is `season.nfo` with a `<season>` root.
- **Evidence:** the two functions; `applyRecords` passes `kind == KindSeason` straight to the writer, and `nfoWriterFor` does not filter by kind.
- **Fix sketch:** Either do not write sidecars for seasons, or write `season.nfo` with a `<season>` root. Remove the `tvshow.nfo` files LANcast wrote into season folders, which the marker element identifies.
- **Verdict:** CONFIRMED by reading. Not checked against a real Kodi install. The S3 rating assumes `write_nfo` is uncommon; it is opt-in.
- **Triage:** Before 1.0, wave D. Fixed and merged in #1149.

## R08-6 A provider's API key lands in the log whenever a request fails on the network

- **Severity:** S3
- **Class:** C17
- **Confidence:** high
- **Where:** `internal/meta/tmdb/tmdb.go:673` (`api_key` in the query), `internal/meta/omdb/omdb.go:222` (`apikey` in the query), `internal/artistart/theaudiodb.go:96` (key in the path; package currently unused). Logged at `internal/api/meta.go:337` → `writeInternal` (`server.go:1263`, Error level), and at Debug in `enrich.go:594`, `:622`.
- **Failure:** `http.Client.Do` returns a `*url.Error` whose text includes the full request URL. A timeout, DNS failure or reset on a Fix-match apply produces `fetch confirmed match: Get "https://api.themoviedb.org/3/movie/603?api_key=<key>&…": context deadline exceeded` in `lancastd.log` at Error level. "Report an issue" can attach the log tail to a third-party webhook (`internal/report/report.go`, `Log`). With the built-in keys (ADR 0110) it is the project's own CI-secret key that travels.
- **Evidence:** the endpoint construction at the lines above; `doWithRetry` returns `lastErr = err` from `c.http.Do` unwrapped.
- **Fix sketch:** Send TMDB's key as a v4 bearer token or header, and strip the URL from transport errors before returning them (`errors.As(err, &urlErr)` → return `urlErr.Err` with the path only). OMDb accepts only a query key, so redact it from the error.
- **Verdict:** CONFIRMED by reading. Go's `url.Error.Error()` redacts only userinfo passwords, not query strings.
- **Triage:** Before 1.0, wave D. Fixed and merged in #1149.

## R08-7 The daily artwork prune can delete images that are being written while it walks

- **Severity:** S3
- **Class:** other
- **Confidence:** low
- **Where:** `internal/serverapp/main.go:1898-1913` (`live` is read once, then `artwork.Prune` walks), `internal/artwork/prune.go` (removes any file not in `live`), with writers `artwork.Cache.Put`/`Download` followed later by `PutArtwork` / `SetPersonThumb` (`enrich.go:759-764`, `:884-889`; `comic/cover.go:101-106`)
- **Failure:** Every writer puts the file into the cache first and records its row afterwards. Prune reads the set of referenced hashes once, before a walk that takes seconds to minutes on a large cache, and deletes every file not in that set. A poster, face or comic cover downloaded during the walk, whose row lands after the set was read, is deleted when the walk reaches it. The row then names a file that does not exist, and the tile shows no artwork until that item is refreshed, since `Download` is not repeated for an item that is already enriched. This is likeliest when "Run now" on Maintenance coincides with enrichment after a large scan.
- **Evidence:** the order of operations above. No proving test.
- **Fix sketch:** Skip files whose mtime is newer than the moment `live` was read, which is a one-line guard in `scanCache`/`Prune`.
- **Verdict:** PLAUSIBLE. The window is real. How often the two overlap in practice is not measured.
- **Triage:** Before 1.0, wave C. Fixed and merged in #1152.

## R08-8 Provider responses from TMDB and OMDb are read with no size limit

- **Severity:** S3
- **Class:** C3
- **Confidence:** low
- **Where:** `internal/meta/tmdb/tmdb.go:704`, `internal/meta/omdb/omdb.go:252` (`io.ReadAll(resp.Body)`)
- **Failure:** A misbehaving or intercepted provider endpoint (a captive portal, a proxy) answering 200 with an endless body grows memory until the 15 s client timeout. MusicBrainz (`musicbrainz.go:305`, 4 MiB), TheAudioDB (1 MiB) and artwork downloads (`maxDownload`) all cap theirs, so these two are the exceptions.
- **Evidence:** the two lines.
- **Fix sketch:** `io.LimitReader(resp.Body, 8<<20)`, matching the others.
- **Verdict:** PLAUSIBLE. These are HTTPS endpoints, so reaching this needs a misbehaving provider or a TLS-intercepting proxy the machine trusts. The timeout bounds it.
- **Triage:** Before 1.0, wave D. Fixed and merged in #1149.

## Checked and clean

- **C4, scan deletes:** the walk only marks missing (`MarkMissing`), per location, after re-statting the root, and a cancelled walk returns before reconciliation. `PruneEmptyContainers` deletes only rows with no `container`, no children and no collection members; playlists are exempt. A show TMDB renames is not orphaned by the next scan, because `EnsureShow` falls back to the show's **path** identity (`ON CONFLICT(path)`), which does not change with the title. Matched/locked show rows survive. Containers whose children are all missing are *marked* (`ReconcileMissingContainers`), not deleted.
- **C4, locked album:** `reconcileMusic` keeps a locked album's tracks unless the walk wrote the file (`tags.go:545`, the 2026-11-10 fix). `DeleteEmptyMusicContainers` therefore cannot empty a locked album through a change in grouping rules.
- **C4, enrich/merge/refresh:** `Merge` skips every locked field, `applyRecords` derives `sort_title` only when it is not locked, and genres, credits and artwork respect their locks. `UpsertItem` (post-#1087) keeps locked and settled identity columns through `keepIdentity`. The reinterpreted path in `scanner.go:937-950` clears the metadata stamp, but the enricher still honours locks.
- **C14:** filename parsing in the slice calls into `internal/media` (`Parse`, `ShowDir`, `SeasonDir`, `PartOf`, `ChapterOf`, `IsExtra`, `IsLetterBucket`). The playlist importer's own lowercase `sortTitle` is deliberate and matches the API's (`api/playlists.go:116`), so it is not a second opinion about media titles. `MergeKey` for artist identity is documented as deliberately not `SortTitle`. The one real disagreement is `score.normalize`, R08-3.
- **C3, archives:** pages are served by index from the archive and never extracted, so traversal names (`../x.jpg`) have nowhere to go. `ReadPage`/`readEntry` cap a page at 64 MiB on both declared and actual size, and page count is capped at 5,000. The cb7 read-ahead holds at most 96 MiB. The PDF reader caps reads, inflated streams and pixels, bounds recursion at 64, and is fuzzed. m3u lines are capped at 1 MiB (`playlist.Parse`), and entries resolve only to rows already in the library, never to file reads. EXIF and GPS reads are capped at 128 KiB and 512 KiB. Profile pictures check `DecodeConfig` against `MaxPixels` (the pattern R08-1 asks for).
- **C10:** `.cbz` and `.pdf` are opened per request and closed with it (`api/comics.go`). The only long-held archive, `.cb7` on the shelf, opens with `FILE_SHARE_DELETE` (`openshared_windows.go`).
- **C15:** worker goroutines in `enrich`, `scan/tags.go` and `photo` are joined with a `WaitGroup` before return. Retry timers in tmdb/omdb are stopped on cancel. Response bodies are closed. The cb7 shelf's `AfterFunc` closes only idle archives.
- **C17, rest:** MusicBrainz sends no key. Artwork URLs from TMDB carry no key.
- **C9 (ffmpeg here):** photo, marker and coverart run `exec.LookPath("ffmpeg")`, which goes through the PATH `mediatools.Locator` rewrites for the service (#1096). The marker worker sets no `-hwaccel`.
- **Startup kicks:** the cover and photo workers start at boot from `serverapp`. R08-1 is why that matters: a fatal decode is retried on every start.
- **ADR 0017 grouping:** `Deathly Hallows Part 1/2` in one folder becoming one work is what the ADR specifies ("Baahubali Part 1/2" are separate TMDB films too), so it is not entered.
