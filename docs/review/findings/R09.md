## R09-1 Any process running as the user, or any local account, can make the service run its own ffmpeg as SYSTEM

- **Severity:** S1
- **Class:** other
- **Confidence:** high
- **Where:** `internal/mediatools/mediatools.go:62` (`Detect`), `:113` (`commonDirs`); recorded by `internal/serverapp/main.go:319-330`, `service.go:72-80`, `servermode_windows.go:180`
- **Failure:** The service runs as LocalSystem and executes `ffmpeg.exe` / `ffprobe.exe` from whatever directory `Resolve` settles on, at startup (encoder and filter probes) and for every probe and playback. There are two routes for an attacker to choose that directory:
  1. **By design today, on this machine.** At install, `Detect` runs with the installing user's PATH and records what it finds, and every later start records it again into `config.json`. A winget install of ffmpeg lives under `%LOCALAPPDATA%\Microsoft\WinGet\Links`, which the user owns and can write without elevation. Any unelevated process running as that user, a browser exploit or a malicious npm script for example, replaces `ffmpeg.exe` there. At its next probe the service runs that file as SYSTEM: a medium-integrity to SYSTEM escalation that skips UAC.
  2. **Any local account.** Where no ffmpeg is beside the executable or on the service's PATH, `Detect` falls through to `C:\ffmpeg\bin`, `%ProgramData%\ffmpeg\bin` and `%ProgramData%\chocolatey\bin`. By the Windows default ACLs any authenticated user can create the first two, and the service then finds, records and runs what they put there.
- **Evidence:** Read-only, on the live install: `sc qc lancastd` gives `SERVICE_START_NAME : LocalSystem`. `C:\ProgramData\LANcast\config.json` has `"ffmpeg_dir": "C:\\Users\\Chris\\AppData\\Local\\Microsoft\\WinGet\\Links"`, and that folder is owned by the user (`ls -la`: `Chris 197609`, `ffmpeg.exe` a symlink into the user's winget packages). `icacls C:\` gives `Authenticated Users:(AD)` and `(OI)(CI)(IO)(M)`. `icacls C:\ProgramData` gives `BUILTIN\Users:(CI)(WD,AD,WEA,WA)`. No guard stands between `Resolve` and `os.Setenv("PATH", …)` or `settings.Set`. The binary was not replaced to demonstrate it.
- **Fix sketch:** The service should run only tools in a directory writable by administrators and SYSTEM alone, checked from its DACL and owner on every start (not just at install). That means beside the executable, the managed `tools` install, or a configured directory that passes the check. For a per-user install, copy the two binaries into the protected tools directory rather than recording the user's folder. Drop the guessed locations.
- **Verdict:** CONFIRMED. Route 1 is the live configuration of this machine; ADR 0016 recorded the per-user directory on purpose, so triage has to weigh that intent against the escalation.

## R09-2 An HLS session is handed to whoever asks for the same item and offset, and is then stopped under them

- **Severity:** S2
- **Class:** other
- **Confidence:** high
- **Where:** `internal/transcode/manager.go:624` (`EnsureHLS` reuse loop)
- **Failure:** The reuse test is item id, HLS, and an offset within 6 seconds. It ignores the owner, `AudioIndex` and the decision.
  - (a) A second account that starts the same film is handed the first account's session, with the first account's audio track, quality ceiling and codec decision (for example copied HEVC made for Safari, served to Chrome).
  - (b) A viewer who switches audio track or quality within 6 seconds of their start position gets the old session back, so the switch does nothing.
  - (c) The shared session keeps `Owner` = first account. When that viewer seeks or falls back, `supersedeHLS` / `supersedeOutput` stop it, and the second viewer's segments then answer 404, which the client reads as "this device cannot play HLS" (see the comment at `api/transcode.go:197`).
- **Evidence:** Scratch test, run and failing as predicted:
  ```go
  m := NewManager(t.TempDir(), quiet()); m.bin = "ffmpeg-not-run"
  alice := &Session{ID: "alice", ItemID: 7, Owner: "alice", Output: HLS, StartAt: 0, started: time.Now(), lastTouch: time.Now()}
  m.sessions[alice.ID] = alice
  got, _ := m.EnsureHLS(ctx, 7, "bob", Options{AudioIndex: 3, StartAt: 2})   // got == alice
  m.supersedeHLS("alice", 7)                                                 // removes what bob is reading
  ```
  Output: `bob (audio 3, t=2) was handed alice's session (owner "alice")` and `alice's seek removed the session bob was reading`. `TestTwoViewersSkippingKeepTheirOwnStreams` (`seekceiling_test.go:61`) is the test meant to guard this and passes on the bug. Its second viewer's seek to 400 s reuses the first viewer's 400 s session and leaves its own 115 s session orphaned, which still totals the 2 sessions it asserts.
- **Fix sketch:** Reuse only for the same owner, audio index and output-shaping decision; a different request at the same offset is a new session. Make the two-viewer test assert that each viewer holds a session it owns.
- **Verdict:** CONFIRMED (proving test).
- **Triage:**

## R09-3 The frame rate never reaches the encoder, so every 50 or 60 fps encode on NVENC dies

- **Severity:** S2
- **Class:** C9
- **Confidence:** high (proven at the decision and at the encoder); low only for the exact service log line
- **Where:** `internal/probe/worker.go:242` (`ResultWithStreams`) and `:263` (`ResultFromItem`), which drop `FrameRate`; consumed at `internal/probe/decide.go:579` and `internal/transcode/level.go:79`
- **Failure:** Every playback decision is built by `ResultWithStreams`, which never sets `Stream.FrameRate` (`store.MediaStream` has no such field, and the item's own `FrameRate` column is ignored). `SourceFrameRate` is therefore always 0, and `H264Level` falls back to frame size alone: 1080p is promised level 4.1 and 4K level 5.1 whatever the rate. NVENC refuses a level the stream breaks and produces nothing. So on an NVIDIA server, any 1080p50, 1080p60 or 2160p60 source that needs a video encode (HEVC to a browser, a quality ceiling, an optimized copy) never starts: the HLS playlist wait fails and the player shows the "could not start" error, or a spinner. The same lost rate pins `gopFrames` at 48 and `SegmentLength` at 6.0 s for every source.
- **Evidence:** Scratch test: an item with `FrameRate: 59.94`, HEVC 1920x1080, browser profile → `method=transcode video=encode SourceFrameRate=0`. `H264Level`: `1920x1080 rate unknown -> 4.1; at 59.94 -> 4.2`, `3840x2160 -> 5.1; at 59.94 -> 5.2`. ffmpeg 8.1.2 on this machine's NVIDIA card, with LANcast's encoder arguments on `testsrc2`:
  ```
  1080p60 -level 4.1  → [h264_nvenc] InitializeEncoder failed: invalid param (8): Invalid Level.
  1080p50 -level 4.1  → same
  1080p30 -level 4.1  → ok
  1080p60 -level 4.2  → ok
  2160p60 -level 5.1  → Invalid Level.    2160p60 -level 5.2 → ok
  libx264 1080p60 4.1 → warning "MB rate (489600) > level limit (245760)", encodes
  ```
  QSV could not be tested here (no MFX session); AMF was not tried. This ran from a shell; the failure is in encoder initialisation, so the service should behave the same, but an encode of a real 60 fps file was not run as the service.
- **Fix sketch:** Carry the frame rate through: add it to `store.MediaStream` (it is already in `ProbeResult` and on the item), or fill the rebuilt video stream from `it.FrameRate`. Add a test that goes through `ResultWithStreams` into `Args`, since the existing level tests hand the rate in directly.
- **Verdict:** CONFIRMED (proving test and encoder run).
- **Triage:**

## R09-4 A bit-rate ceiling does nothing when the probe has no video bit rate

- **Severity:** S2
- **Class:** other
- **Confidence:** high
- **Where:** `internal/probe/decide.go:666`
- **Failure:** `videoCompatible` refuses only when `s.BitRate > p.MaxVideoBitRate`. ffprobe gives no stream `bit_rate` for Matroska and often none elsewhere, so the stored value is 0 and passes. With the server ceiling at "1080p · 10 Mbps" (or a client asking for 4 Mbps), a 1080p file with an unknown rate is direct-played, or remuxed with the video copied, at whatever rate it really has. The encode branch at `:586` treats unknown as "cap it", the opposite rule, but is reached only when something else has already forced an encode.
- **Evidence:** Scratch test, profile `MaxHeight 1080, MaxVideoBitRate 10_000_000`, H.264 1920x1080 with `BitRate: 0`: `mov: method=direct video=copy target_bitrate=0`, `matroska: method=remux video=copy target_bitrate=0`. `TestBitrateLimit` and `TestBitrateCeilingSetsTarget` use a known rate only.
- **Fix sketch:** When the stream rate is unknown, estimate it from the container (size × 8 / duration, minus audio) and decide on that; store the estimate.
- **Verdict:** CONFIRMED (proving test).
- **Triage:**

## R09-5 A converted subtitle is cached by path alone and never refreshed

- **Severity:** S2
- **Class:** C6
- **Confidence:** high
- **Where:** `internal/subtitle/extract.go:211` (`cacheKey`), `:159` (`cached`)
- **Failure:** The key hashes the path and a variant. Replace `Film.en.srt` with a re-synced copy, or replace `Film.mkv` with another release of the same name, and the old WebVTT is served for ever. For an embedded track, the same stream index may now be another language. Nothing clears the cache.
- **Evidence:** Scratch test: wrote `Film.en.srt` with "OLD TEXT", served it via `Sidecar`, rewrote the file with "NEW TEXT, re-synced", served again, and got `00:00:01.000 --> 00:00:02.000 / OLD TEXT`. grep finds nothing in `scan` or `api` that removes the cache.
- **Fix sketch:** Put the source's size and modification time in the key (and prune old entries).
- **Verdict:** CONFIRMED (proving test).

## R09-6 Valid UTF-8 subtitles are refused as "not text" when byte 512 falls inside a character

- **Severity:** S2
- **Class:** other
- **Confidence:** high
- **Where:** `internal/subtitle/extract.go:107-110`, `internal/subtitle/convert.go:264` (`LooksLikeText`)
- **Failure:** `Sidecar` reads the first 512 bytes and requires `utf8.Valid` on them. A cut in the middle of a multi-byte character makes the slice invalid. A correct UTF-8 `.srt` in Russian, Greek, Chinese, Arabic or Hebrew with no byte-order mark is refused about half the time, depending only on where byte 512 lands, and the track fails with "this subtitle track could not be converted". The downloaded-subtitle path has the same cut (see Seen in passing).
- **Evidence:** Scratch test with a Cyrillic SRT (`"Привет "` repeated): of 13 header lengths, 6 leave a refused 512-byte head. With a 33-byte header, `Sidecar` returns `subtitle format cannot be converted to WebVTT: Film.ru.srt is not text`. `TestLooksLikeText` covers ASCII, NUL bytes and nil only.
- **Fix sketch:** Drop an incomplete trailing sequence (at most 3 bytes) before validating; decide separately what to do with non-UTF-8 text (Windows-1252 subtitles are common and are refused too).
- **Verdict:** CONFIRMED (proving test).
- **Triage:**

## R09-7 An MJPEG video clip is taken for cover art and plays as sound only

- **Severity:** S3
- **Class:** other
- **Confidence:** high (the decision); not watched in a browser
- **Where:** `internal/probe/probe.go:201` (`isCoverArt`)
- **Failure:** Any video stream whose codec is mjpeg, png, bmp, gif or webp is skipped, whatever its length or frame rate. A camera clip (MJPEG in AVI or MOV, common from older cameras and webcams) has no video as far as `Decide` is concerned, so it is decided `AudioOnly`, ffmpeg maps no picture, and the clip plays as sound.
- **Evidence:** Scratch test: ffprobe JSON for a 60 s 1280x720 30 fps MJPEG AVI with `attached_pic: 0` → `Video()=<nil> method=transcode audio_only=true`. The comment says "single-frame", but the code checks only the codec; `disposition.attached_pic` is not parsed.
- **Fix sketch:** Parse `attached_pic` and use it; keep the codec test only where the disposition is absent.
- **Verdict:** CONFIRMED (proving test, at the decision).

## R09-8 An absurd container duration is accepted, and the server-written playlist grows with it

- **Severity:** S3
- **Class:** C3
- **Confidence:** high at the parser, low end to end
- **Where:** `internal/probe/probe.go:528` (`secondsToMS`), `internal/transcode/vodplaylist.go:72` (`CompletePlaylist`)
- **Failure:** Duration is taken from the file with no upper bound, and `CompletePlaylist` builds one entry per segment in memory on every playlist request. A file whose container claims 10^9 seconds, played with a video encode, asks for about 1.7×10^8 entries, several gigabytes.
- **Evidence:** Scratch test: `ParseJSON` of `"duration":"1000000000"` gives `DurationMS=1000000000000`. No cap in `resolveDuration`, `completeFor`, or `api/transcode.go:83`. Not shown that ffprobe passes such a value through from a crafted file.
- **Fix sketch:** Refuse a duration beyond a sane ceiling (a few days) at parse time, and cap the segment count in `CompletePlaylist`.
- **Verdict:** PLAUSIBLE. Proven at the parser; a crafted Matroska `Duration` element is the remaining step.

## R09-9 The session ceiling does not hold its slot, so concurrent starts exceed it

- **Severity:** S3
- **Class:** other
- **Confidence:** high
- **Where:** `internal/transcode/manager.go:931` (`reserve`), `:567-582`, `:653-672`
- **Failure:** `reserve` checks the count and releases the lock, and the session is added only after ffmpeg has started. Two requests that arrive together both pass at `MaxSessions-1` and both run. - **Fix sketch:** Insert a placeholder session under the lock in `reserve`, and remove it on failure.
- **Verdict:** CONFIRMED (proving test). Bounded: an extra progressive stream ends with its request.

## R09-10 ffmpeg outlives a server that dies, and a session can start after StopAll

- **Severity:** S3
- **Class:** C9
- **Confidence:** high (no job object), low (how often)
- **Where:** `internal/childproc/hide_windows.go`, `internal/transcode/session.go:290`, `manager.go:259`
- **Failure:** Children are tied to the parent only by context. If the server is killed or crashes, an HLS encode writing to files runs to the end of the film, and an optimized-copy conversion keeps writing its output while the restarted server may start the same conversion. On restart `os.RemoveAll(m.root)` cannot remove files an orphan still holds. Separately, `StopAll` empties the map but nothing stops `EnsureHLS` from adding a session afterwards, and that session's context is detached from its request.
- **Evidence:** `childproc` has only `Hide` and `Detach`; no job object anywhere in the slice. Observing the orphan needs the installed service killed mid-encode, which this review could not do.
- **Fix sketch:** On Windows, put children in a kill-on-close job object; have `EnsureHLS` and `Progressive` refuse once `stopped` is closed.
- **Verdict:** PLAUSIBLE.
- **Triage:**

## R09-13 A `%d` in the data directory path breaks HLS output and previews

- **Severity:** S3
- **Class:** other
- **Confidence:** high (HLS), low (previews)
- **Where:** `internal/transcode/args.go:953`, `internal/preview/preview.go:339`
- **Failure:** Both join a directory to a `%05d` / `%03d` pattern. A `%` followed by a conversion in the directory name is read as part of the pattern, so ffmpeg writes to a different, nonexistent path and the session produces no segments.
- **Evidence:** LANcast's HLS arguments into `pct/data%dir/sess`: `[hls] Failed to open file 'pct/data0ir/sess/seg00000.m4s'`, with only `index.m3u8` and `init.mp4` written. `pct/data%20x/sess` worked, so only `%` before a conversion character bites. Previews not run.
- **Fix sketch:** Escape `%` as `%%` in the directory part, or run ffmpeg with the output directory as its working directory and a bare pattern.
- **Verdict:** CONFIRMED for HLS (ffmpeg run).
- **Triage:**

- C3: OpenSubtitles responses are capped (1, 4 and 8 MiB) and the SRT scanner line is capped at 4 MiB. Not capped: ffprobe stdout and `os.ReadFile` of a `.vtt` sidecar; no failure shown, noted here only.
- C17: the OpenSubtitles key and token go only to `*.opensubtitles.com` (`useAccountHost`); the password is not logged.
- C14: subtitle title matching uses `media.Parse`; R09-14 is about matching a name to a video, not about title normalisation.
- C16: `history.Save` writes then renames; preview and subtitle cache writes go through a temporary name.
- mediatools install: a pinned URL with its SHA-256 checked before unpacking; entries are written by base name only, so zip-slip is absent. The trust problem is in where the tools are found, not in how they are fetched (R09-1).
- C10: no long-held file handle in the slice; segments, sheets and subtitles are opened per request and closed.
- C15: every context made in the slice is cancelled; `livebuf`'s fill goroutine exits on Close or EOF; timers in `mediatools.download` are stopped.
