## R09-1 A local user can make the service run their own ffmpeg as SYSTEM

- **Severity:** S1
- **Class:** other
- **Confidence:** high (mechanism), low (how it is reached on a given install)
- **Where:** `internal/mediatools/mediatools.go:113` (`commonDirs`), used by `Detect` at `:74`
- **Failure:** On a machine with no ffmpeg beside the executable and none on the service's PATH (the state of a fresh install, since ffmpeg is not bundled), `Detect` falls through to `C:\ffmpeg\bin`, `%ProgramData%\ffmpeg\bin` and `%ProgramData%\chocolatey\bin`. An unprivileged local account can create those folders and put `ffprobe.exe` and `ffmpeg.exe` in them. The service, which runs as LocalSystem, then finds them, records the directory, prepends it to its PATH and executes them for every probe and encoder test.
- **Evidence:** `icacls C:\` on this machine: `NT AUTHORITY\Authenticated Users:(AD)` and `(OI)(CI)(IO)(M)`; `icacls C:\ProgramData`: `BUILTIN\Users:(CI)(WD,AD,WEA,WA)`. Those are the Windows defaults. `C:\ffmpeg` does not exist here, so the folder is free to create. Not run as the service.
- **Fix sketch:** On Windows, accept a detected directory only if it and its parents are writable by administrators and SYSTEM alone, or drop the guessed locations and keep only beside-the-executable, the recorded setting and PATH.
- **Verdict:** PLAUSIBLE. The lookup order and the ACLs are confirmed by reading; whether `serverapp` adds a guard after `Resolve` was not checked (`internal/serverapp/main.go:319`).
- **Triage:**

## R09-2 An HLS session is reused across viewers, audio tracks and quality settings

- **Severity:** S2
- **Class:** other
- **Confidence:** high
- **Where:** `internal/transcode/manager.go:624` (`EnsureHLS` reuse loop)
- **Failure:** The reuse test is item id, HLS and an offset within 6 seconds. It ignores the owner, `AudioIndex` and the decision. (a) A viewer who starts a film and switches audio track or quality within 6 seconds gets the old session back: the switch does nothing, and the returned playlist starts at the old offset. (b) A second account starting the same film is handed the first account's session, with the first account's audio track, ceiling and codec decision (for example copied HEVC made for Safari, given to Chrome). (c) That shared session still has `Owner` set to the first account, so when the first account seeks or falls back, `supersedeHLS` / `supersedeOutput` at `:647`, `:565` stop it under the second viewer, whose segments then answer 404.
- **Evidence:** `manager.go:625` compares only `s.ItemID`, `s.Output`, `sameOffset`. `api/transcode.go:88` passes per-request `AudioIndex` and a per-request decision from `profileFor(r)`. The comment on `LiveHLS` says file sessions carry per-viewer state. No proving test run.
- **Fix sketch:** Key reuse on owner, audio index and the parts of the decision that change the output; a different request at the same offset is a new session.
- **Verdict:** CONFIRMED by reading the caller; no guard between the handler and the loop.
- **Triage:**

## R09-3 The source frame rate never reaches the encoder settings

- **Severity:** S2
- **Class:** other
- **Confidence:** high (the wiring), low (the NVENC failure)
- **Where:** `internal/probe/worker.go:242` (`ResultWithStreams`), `:263` (`ResultFromItem`); consumed at `internal/probe/decide.go:579`
- **Failure:** Every playback decision is built from `ResultWithStreams`, which fills streams without `FrameRate` (`store.MediaStream` has none; the item's `FrameRate` column is not used). `DecideTrack` therefore always leaves `SourceFrameRate` at 0. `H264Level` then ignores the rate: a 1080p60 source is promised level 4.1 (needs 4.2) and 4K60 gets 5.1 (needs 5.2). `level.go` exists because NVENC refuses a level the stream breaks and produces nothing. `gopFrames` is always 48 and `SegmentLength` always 6.0, whatever the source.
- **Evidence:** The only non-test writer of `SourceFrameRate` is `decide.go:580`, reading `video.FrameRate`; grep finds no caller that sets it except `cmd/hlsharness`. The level and GOP tests pass because they hand the rate in directly. Whether NVENC rejects 60 fps at 4.1 can only be proven as the installed service with a 60 fps file that needs a video encode.
- **Fix sketch:** Carry the item's stored frame rate into the rebuilt `Result` (and add it to the stored stream), with a test that goes through `ResultWithStreams`.
- **Verdict:** CONFIRMED for the wiring; PLAUSIBLE for the dead stream.
- **Triage:**

## R09-4 A bit-rate ceiling does nothing when the probe has no video bit rate

- **Severity:** S2
- **Class:** other
- **Confidence:** high
- **Where:** `internal/probe/decide.go:666`
- **Failure:** `videoCompatible` refuses only when `s.BitRate > p.MaxVideoBitRate`. ffprobe reports no stream `bit_rate` for Matroska, so it is 0 and passes. With the server ceiling at "1080p · 10 Mbps", a 1080p 30 Mbit/s MKV is direct-played or remuxed at full rate. The encode branch at `:586` treats unknown as "cap it", the opposite rule, but is only reached when something else forces an encode.
- **Evidence:** `decide.go:666` against `:586`–`:592`. `TestBitrateLimit` and `TestBitrateCeilingSetsTarget` use a known rate; no test names the unknown case.
- **Fix sketch:** When the stream rate is unknown, estimate from the container (size over duration) before deciding, and store that estimate.
- **Verdict:** CONFIRMED by reading; no fallback to a container rate exists (`ResultFromItem` carries none).
- **Triage:**

## R09-5 A converted subtitle is cached by path alone and never refreshed

- **Severity:** S2
- **Class:** C6
- **Confidence:** high
- **Where:** `internal/subtitle/extract.go:211` (`cacheKey`), `:159` (`cached`)
- **Failure:** The key is a hash of the path and a variant. Replace `Film.en.srt` with a re-synced copy, or replace `Film.mkv` with another release of the same name, and the server keeps serving the old WebVTT for ever; for an embedded track the stream index may now be a different language. Nothing clears the cache.
- **Evidence:** `cacheKey(path, variant)` has no size or modification time; grep finds no removal of the `subtitles` cache in `scan` or `api`.
- **Fix sketch:** Put the source file's size and modification time in the key.
- **Verdict:** CONFIRMED by reading.

## R09-6 Valid UTF-8 subtitles are refused as "not text" when byte 512 falls inside a character

- **Severity:** S2
- **Class:** other
- **Confidence:** high
- **Where:** `internal/subtitle/extract.go:107`–`110`, `internal/subtitle/convert.go:264` (`LooksLikeText`)
- **Failure:** `Sidecar` reads the first 512 bytes and requires `utf8.Valid` on them. A cut in the middle of a multi-byte character makes the slice invalid, so a correct UTF-8 `.srt` in Russian, Greek, Chinese, Arabic or Hebrew with no byte-order mark is refused roughly half the time or more, with "is not text". A Windows-1252 file with an accent in the first 512 bytes is refused too.
- **Evidence:** `utf8.Valid` is false for a truncated sequence. `TestLooksLikeText` covers ASCII, NUL bytes and nil only. No proving test run.
- **Fix sketch:** Trim an incomplete trailing sequence before validating, and decide separately what to do with non-UTF-8 text.
- **Verdict:** CONFIRMED by reading.
- **Triage:**

## R09-7 MJPEG video is always taken for cover art

- **Severity:** S3
- **Class:** other
- **Confidence:** high (the rule), low (what the player shows)
- **Where:** `internal/probe/probe.go:201` (`isCoverArt`)
- **Failure:** Any video stream whose codec is mjpeg, png, bmp, gif or webp is skipped, whatever its length. A camera clip (MJPEG in AVI or MOV) therefore has no video as far as `Decide` is concerned: for a browser the decision is `AudioOnly`, ffmpeg maps no picture, and the clip plays as sound alone.
- **Evidence:** The comment says "single-frame", but the code checks only the codec; ffprobe's `disposition.attached_pic` is not parsed.
- **Fix sketch:** Read `attached_pic` and use it, keeping the codec test only where the disposition is absent.
- **Verdict:** PLAUSIBLE. Needs one MJPEG clip played in a browser.

## R09-8 An absurd container duration builds an unbounded playlist

## R09-9 The session ceiling and the one-stream-per-viewer rule are both racy

- **Severity:** S3
- **Class:** other
- **Confidence:** high
- **Where:** `internal/transcode/manager.go:931` (`reserve`), `:541`, `:582`
- **Failure:** `reserve` checks the count and releases the lock; the session is added only after ffmpeg has started. Two requests arriving together both pass at `MaxSessions-1` and both run. For the same reason two simultaneous `Progressive` calls for one owner and item both find nothing to supersede, which is the exact case the comment at `:520` says is guaranteed.
- **Evidence:** No placeholder is inserted between `reserve` and `m.sessions[s.ID] = s`; `release` is empty.
- **Fix sketch:** Reserve by inserting a placeholder under the lock.
- **Verdict:** CONFIRMED by reading. Bounded: the extra stream ends when its request does.

## R09-10 ffmpeg outlives a server that dies, and a session can start after StopAll

- **Severity:** S3
- **Class:** C9
- **Confidence:** high (no job object), low (how often)
- **Where:** `internal/childproc/hide_windows.go`, `internal/transcode/session.go:290`, `manager.go:259`
- **Failure:** Children are tied to the parent only by context. If the server is killed or crashes, an HLS encode writing to files keeps running to the end of the film, and an optimized-copy conversion keeps writing its output while the restarted server may start the same one. On restart `os.RemoveAll(m.root)` cannot remove files the orphan holds. Separately, `StopAll` empties the map but does not stop `EnsureHLS` from adding a session afterwards, and that session's context is detached from the request.
- **Evidence:** `childproc` holds `Hide` and `Detach` only. Needs the installed service to observe.
- **Fix sketch:** Put children in a kill-on-close job object on Windows; refuse new sessions once stopped.
- **Verdict:** PLAUSIBLE.
- **Triage:**
