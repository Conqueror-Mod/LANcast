## R06-1 A person's shared activity shows the viewer titles from libraries and ratings kept from them

- **Severity:** S2 (a library limit is crossed; triage may read that as S1)
- **Class:** other (access control)
- **Confidence:** high
- **Where:** `internal/api/people.go:54` (`personActivity` calls `s.st.SharedActivity(ctx, id, limit)` and passes nothing about the caller); `internal/store/sharing.go:125` (`SharedActivity` has no viewer argument, no hidden-library clause and no ceiling)
- **Failure:** An administrator keeps a library (or every film above a 12) from a child's account. Any account that has switched on "share what I watch", the administrator included, then finishes a film in that library. The child opens that person on People and `GET /api/people/{id}/activity` returns the whole item row: title, library id, overview, and the rest of the item shape. Continue Watching, Resume, On this day, the watchlist, ratings, Viewings and the year review all strip these items for the same reason (comments at `items.go:813`, `resume.go:281`). This route is the one that does not.
- **Evidence:** proving test, run against `a4fe2355`:
  ```
  === RUN   TestR06ActivityIgnoresViewersHiddenLibraries
      r06_prove_test.go:56: LEAK: member sees hidden title through activity: {"activity":[{"item":{"id":2,"library_id":2,"kind":"movie","title":"Home Video",...
  --- FAIL: TestR06ActivityIgnoresViewersHiddenLibraries
  ```
  The test hides library 2 from the member, checks that `GET /api/items/2` answers 404 for them (the control), has the admin share activity and finish item 2, then reads the admin's activity as the member.
- **Fix sketch:** Run the entries through `s.st.PermittedItems(ctx, s.userID(r), items)` in `personActivity`, the same filter Continue Watching uses. Better still, give `SharedActivity` the viewer's id and put the hidden clause and ceiling in its SQL, so the `limit` counts only rows the viewer may see.
- **Verdict:** CONFIRMED. The proving test fails as described. No wrapper in `server.go:884` adds a check (`GET /api/people/{id}/activity` is routed bare), and `decorateAndWriteItems` is not used here.
- **Triage:** Fixed and merged in #1143.

## R06-2 An account that cannot see every track in a playlist removes the wrong track, and a reorder deletes the tracks it cannot see

- **Severity:** S2 (entries are lost from a playlist other people made; by the bar's "data is lost", triage may raise it to S1. The precondition is a restricted account editing a shared playlist that holds something kept from it)
- **Class:** other (data loss)
- **Confidence:** high
- **Where:** `internal/api/playlists.go:198` (`removePlaylistEntry`, by stored position) and `:143` (`setPlaylistEntries`, replace with exactly the list sent); the listing that the positions are taken from is filtered at `internal/api/items.go:735` (`decorateAndWriteItems` → `PermittedItems`); the client sends the rendered index and the rendered ids, `web/src/components/TrackList.tsx:492` and `:388`
- **Failure:** Playlists are server-wide and any member may edit them (`playlists.go` header). A playlist holds `[A, B, C]`, and B is in a library kept from a member (or rated above their ceiling). That member is shown `[A, C]`. When they press remove on C (row 1), the server deletes stored position 1, which is B, and C stays. When they move a track, the client sends `PUT /entries` with `[C, A]`, and B is dropped from the playlist for every account. The playlist is locked as a human edit, so no rescan brings B back.
- **Evidence:** proving test:
  ```
  === RUN   TestR06PlaylistPositionsSkewForRestrictedViewer
      r06_prove_test.go:115: entries after member removed visible row 1: [1 3] (open=1 private=2 open2=3)
      r06_prove_test.go:118: WRONG ENTRY: open2 still there, the hidden entry was removed instead
      r06_prove_test.go:131: LOST: playlist held 3 entries, now 2 after the member reordered the two they can see
  --- FAIL: TestR06PlaylistPositionsSkewForRestrictedViewer
  ```
- **Fix sketch:** Have the playlist listing carry each entry's stored `position`, and have the client send it back instead of its row index. For `PUT /entries`, merge the caller's order into the stored list, so entries the caller cannot see keep their places, or refuse the write when the stored list holds an entry the caller cannot see. A smaller alternative is to refuse playlist edits from an account that cannot see every entry.
- **Verdict:** CONFIRMED. Both halves are reproduced through the HTTP routes the client uses. No guard was found: `playlistByID` checks only the playlist row, and the response carries no positions.
- **Triage:** Fixed and merged in #1132.

## R06-3 The spec disagrees with the handlers on four library and playlist routes

- **Severity:** S2
- **Class:** C7
- **Confidence:** high
- **Where:** `docs/openapi.json` paths `/libraries/{id}` (delete), `/libraries/{id}/roots/{rootID}` (delete), `/items` (get) and `/playlists` (post); the handlers are `internal/api/libraries.go` `deleteLibrary`, `roots.go` `removeRoot`, `items.go` `listItems` and `playlists.go` `createPlaylist`
- **Failure:** A client generated from the spec gets each of these wrong:
  1. `DELETE /api/libraries/{id}` and `DELETE /api/libraries/{id}/roots/{rootID}`: the spec promises `200` with an `Acknowledged` body. Both handlers answer `204` with no body, and `docs/api.md` (the sections at lines 1029 and 1044) says `204`. A client that parses the promised JSON fails on an empty body. The spec also leaves out the `409` that `deleteLibrary` returns while a scan runs (api.md documents it).
  2. `GET /api/items`: the spec lists 33 query parameters but not `taken_month` or `taken_undated`. The handler reads both (`items.go`, `TakenMonth`/`TakenUndated`), and `docs/api.md:4771` documents them as how a photo timeline bucket is opened. A spec-built client cannot open a timeline month.
  3. `POST /api/playlists`: the spec lists `200/400/401/403`. The handler answers `404 no such library` for an unknown `library_id`.
- **Evidence:** script output for these operations (the full run covered every R06 route):
  ```
  DELETE /libraries/{id} q= [] codes= ['200', '401', '403', '404']          handler: 204, 409
  DELETE /libraries/{id}/roots/{rootID} q= [] codes= ['200', '401', '403', '404']   handler: 204, 409 (writeRootErr)
  POST /playlists q= [] codes= ['200', '400', '401', '403']                 handler: also 404
  GET /items q= ['library_id', ..., 'favourite']                            no taken_month / taken_undated
  ```
  `openapi_test.go` checks methods, path parameter names and `$ref`s, not status codes or query parameters, which is why this passes.
- **Fix sketch:** Correct the four operations in `openapi.json` (`204` with no content; add `409` and `404` where shown; add the two query parameters) and regenerate `web/src/api/schema.ts`. No handler change is needed.
- **Verdict:** CONFIRMED. Each status was read from the handler. `removeRoot` writes `w.WriteHeader(http.StatusNoContent)`. For `createPlaylist`, `notFoundOr` writes the 404.
- **Triage:** Fixed and merged in #1134.

## R06-4 The playback decision crashes when an item has a finished optimized copy and is waiting to be probed again

- **Severity:** S2
- **Class:** other (nil dereference)
- **Confidence:** high
- **Where:** `internal/api/playback.go:61`: `if def := res.Audio(); res != nil && def != nil ...`. The call runs before the nil check, and `res` is nil whenever the item's `probed_at` is NULL (`probe.ResultFromItem`).
- **Failure:** An administrator runs "Re-probe everything" (`POST /api/probe/refresh?scope=all`). Separately, a rescan finds a file changed (`UpsertItem` sets `probed_at = NULL`). Either way, any item with a ready optimized copy then answers `GET /api/items/{id}/playback` with a 500 and writes a crash report, until the probe worker reaches it again. The comment at `playback.go:88` says a full re-probe is "hours of ffprobe". The client asks this route before every play (`PlaybackProvider.tsx:1761`, `:1966`, `:2026`), and paired servers reach it through `GET /api/federation/playback` (`server.go:861`). Every optimized title fails to start for the whole window. Those are the titles the household marked as the ones that most need help playing.
- **Evidence:** proving test (ready copy via the existing `readyCopy` helper, then `ClearProbe(ctx, 0)` as the refresh route calls it):
  ```
  === RUN   TestR06PlaybackPanicsWhileReprobing
      r06_prove_test.go:162: playback while awaiting re-probe -> 500 {"error":{"code":"internal","message":"the server hit an unexpected fault; a crash report was saved"}}
  --- FAIL: TestR06PlaybackPanicsWhileReprobing
  ```
- **Fix sketch:** Test `res != nil` before calling `res.Audio()` (split the init statement). An unprobed original then gets the copy's decision or the `DecideTrack(nil, …)` answer, as it would with no copy.
- **Verdict:** CONFIRMED. `recoverPanics` turns the panic into a 500, so the server stays up. That is why this is S2 rather than S1.
- **Triage:** Fixed and merged in #1131.

## R06-5 The all-libraries cast search names people credited only in libraries kept from the caller

## R06-6 Playlist writes check that ids exist, not that the caller may see them

- **Severity:** S3
- **Class:** other (access control)
- **Confidence:** high
- **Where:** `internal/api/playlists.go:77` (`decodeItemIDs` → `ExistingItemIDs`, which has no account), `:112` (`createPlaylist` checks `GetLibrary`, not `MayOpenLibrary`)
- **Failure:** (a) A member can add any item id to a shared playlist, including ones in a library kept from them or above their ceiling. The answer `400 no such item: N` versus `204` tells them which ids exist in libraries they are not supposed to know hold anything. (b) A member can create a playlist inside a library kept from them. The create answers 200, and from then on the playlist is a 404 to its own creator (`playlistByID` → `GetItem`), so it is made and immediately lost to them. Compare `addHomeShelf`, which checks `MayOpenLibrary` and answers 404 (`homeshelves.go`).
- **Evidence:** code as cited. `ExistingItemIDs` is `SELECT id FROM media_item WHERE id IN (…)` (`internal/store/playlist.go:206`).
- **Fix sketch:** Check each id with the caller's limits (`PermittedItems` over the rows, or a store variant of `ExistingItemIDs` that takes the user), and answer an id the caller cannot see the same way as a missing one. Check `MayOpenLibrary` in `createPlaylist`.
- **Verdict:** CONFIRMED by reading. Neither path reaches an account-aware check.
- **Triage:** Before 1.0, wave C. Fixed and merged in #1152.

## R06-8 A library edit that is half refused is half applied

- **Severity:** S3
- **Class:** other
- **Confidence:** high
- **Where:** `internal/api/libraries.go:261` (`RenameLibrary` is written) before `:270–288` (the path is checked and can be refused)
- **Failure:** `PATCH /api/libraries/{id}` with `{"name":"Films","path":"D:\\typo"}` renames the library, then answers `400 path does not exist`. The caller is told the edit failed, but the library now has the new name, and the audit log records the rename. - **Triage:** Before 1.0, wave C. Fixed and merged in #1152.

## Checked and clean

- **Admin-only routes.** `server.go` wraps every write that touches files, libraries or other accounts in `adminOnly`: library create/patch/delete, roots add/patch/remove, scan and scan-all and cancel, `DELETE /api/items/{id}`, peer shares (list/put/delete), `/api/users/{id}/libraries`, `/api/dashboard/history`, `POST /api/probe/refresh`, `POST /api/markers/refresh` and `/items/{id}/markers/refresh`. Playlists are deliberately member-editable (ADR 0030, `playlists.go` header). Status reads (`GET /api/probe`, `/api/markers`, `/libraries/{id}/scan`) carry counts only.
- **Library-scoped reads.** `facets`, `cast` (except id 0, R06-5), `timeline`, `places`, `people`, `roots`, `scan`, the photo index/search, duplicates and near-copies are all behind `libraryVisible`. Face routes use `ownedVisible`.
- **Item-scoped routes.** `getItem`, `itemCollections`, `collectionFilms`, `itemAfterwards`, `putProgress`, `itemChapters`, `itemMarkers`, `playback`, `continueShow`, `showEpisodes`, `addToWatchlist`, `addItemTag`, `putFavourite` and `putRating` all go through `GetItem(ctx, id, user)`, which applies the ceiling and hidden libraries. `getRating`, `itemTags`, `deleteRating`, `removeFromWatchlist` and `removeItemTag` skip it, and return or change only the caller's own rows, which is correct (removing from your own list must work after access is lost).
- **Listings.** `listItems` sets the ceiling and hidden libraries in the filter. Collection members, playlist entries, the watchlist, item collections, afterwards and to-rate go through `decorateAndWriteItems` → `PermittedItems`, and its `total` adjustment cannot go negative. `continueWatching`, `resume`, `homeSuggestion` and `memories` (photos and watched) call `PermittedItems`. The caller's own history lists apply the hidden clause in the store: `Viewings`, `AllViewings` (export), `ListRatings` and `YearInReview`. `listHomeShelves` drops shelves over hidden libraries. `addHomeShelf` checks `MayOpenLibrary`.
- **C4 (locks).** No handler in this slice edits an item's metadata (that is `meta.go`, R07). Every playlist membership write sets the `members` lock before writing (`createPlaylist`, `setPlaylistEntries`, `addPlaylistEntries`, `removePlaylistEntry`). `deleteItem` with `forget` refuses a present file and an unreadable location, so "scanning marks missing, never deletes" holds. `delete` containment-checks every file and sidecar against that file's own root (`containedEntry`) before removing anything.
- **C1 (containment).** `deleteItem` uses `containedEntry` per file. `itemChapters` uses `itemFilePath`. No other handler in the slice opens a library path.
- **C2/CSRF.** Every state-changing route in the slice is POST/PUT/PATCH/DELETE, so the global `Origin`/`Referer` check and `SameSite=Strict` cover them (R01 checked the middleware). No GET in the slice writes, apart from the R07 note above.
- **C3 (bounds).** Store-side caps: `ListItems` 500, `Viewings` 500, `Watchlist` 500, `SearchCast` 200, `PhotoMemories` 200, `FinishedOnThisDay` 200, `SharedActivity` 100, `ListRatings` 200 (handler), `resume` 100, `continue` capped by the server setting, `ToRate` 20, `hidden_shelves` 256, shelf titles 80, reviews 4000, tag and favourite bodies by `MaxBytesReader`. Uncapped id lists (`?id=` on cast, `item_ids` on playlists) were tested: 40,000 `id=` values on `/api/libraries/0/cast` answered `200 {"people":[]}`, not an SQL-variable error, so the 1 MiB body cap is the effective bound. Not a finding.
- **C11.** `yearInReview` uses the server's local year. `PhotoMemories` and `FinishedOnThisDay` take "today" from SQLite `'localtime'`. Only the export file name is UTC (R06-7).
- **C15.** `RecordHistory` stops its ticker on exit and saves. `chapterCache` is bounded at 512. `ReadChapters` takes the request context.
- **C16.** `exportViewings` ignores `csv.Write` errors. They fail only when the client hangs up mid-download, and nothing persistent depends on them.
- **C17.** No secret passes through this slice.
- **Pagination.** `Viewings` orders by `finished_at DESC, id DESC`, which is total. `Watchlist` orders by `added_at DESC, rowid DESC`. Ties in `ListItems` are noted under Seen in passing.
- **Not applicable here:** C5 (no federation routes in the slice besides the `federationPlay` wrapper around `playback`, covered by R02), C6/C12/C13/C18 (client), C8 (store), C9 (no process launched here except `ReadChapters`, which is `probe`'s), C10, C14.
