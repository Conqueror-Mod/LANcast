## R01-1 Before the first account, any web page in the owner's browser can claim the server or read through it

- **Severity:** S1
- **Class:** C2
- **Confidence:** high (the server's behaviour is proven; how far a given browser lets a page get is noted below)
- **Where:** `internal/api/auth.go:159` (`requireAuth` passes everything while there are no accounts), `internal/api/auth.go:553` (`authSetup`)
- **Failure:** The loopback rule keeps other *machines* out while there is no password. It does not keep out other *origins* in the browser on the same machine, and in this state the middleware skips both the CSRF check and every gate, and never looks at the `Host` header.
  1. *Claiming the server.* While LANcast is installed and no account exists yet, the owner visits any web page. The page sends `POST http://127.0.0.1:<port>/api/auth/setup` with `Content-Type: text/plain` and a JSON body. That is a "simple" request, so the browser sends it without a preflight. The server creates the first administrator with the attacker's name and password. The owner is now locked out of their own setup, and on the next restart the server binds the network with an administrator the attacker knows. An administrator can browse the filesystem and add a library at any path.
  2. *Reading through it.* A page that rebinds its own hostname to `127.0.0.1` is same-origin with the server as far as the browser is concerned, so it can read responses. Every admin route answers it: `GET /api/browse` (filesystem listing), `POST /api/libraries` at any path, then `/api/stream/{id}`. That is arbitrary file read for a web page, for as long as the server has no account. CLAUDE.md treats "no password, loopback only" as a state a server may stay in, not only a few minutes of first run.
- **Evidence:** Both tests pass at `4faabca9`.
  ```go
  func TestR01_UnconfiguredServerAcceptsCrossOriginSetup(t *testing.T) {
      h := newHarness(t)
      req, _ := http.NewRequest("POST", h.srv.URL+"/api/auth/setup",
          strings.NewReader(`{"username":"mallory","password":"attacker chose this"}`))
      req.Header.Set("Content-Type", "text/plain") // a "simple" request: no preflight
      req.Header.Set("Origin", "https://evil.example")
      resp, _ := h.srv.Client().Do(req)
      if resp.StatusCode != http.StatusOK { t.Fatalf("refused: %d", resp.StatusCode) }
      if n, _ := h.st.CountUsers(t.Context()); n != 1 { t.Fatalf("users = %d", n) }
  }
  func TestR01_UnconfiguredServerAnswersAForeignHost(t *testing.T) {
      h := newHarness(t)
      req, _ := http.NewRequest("GET", h.srv.URL+"/api/browse", nil)
      req.Host = "rebind.evil.example:8080"
      resp, _ := h.srv.Client().Do(req)
      if resp.StatusCode != http.StatusOK { t.Fatalf("refused: %d", resp.StatusCode) }
  }
  ```
  `grep -rn "r\.Host" internal` finds no check of the `Host` header on the API path. `TestCrossOriginStateChangeRefused` only covers a configured server.
- **Fix sketch:** Apply `auth.SameOriginRequest` to state-changing methods *before* the `!s.secured` early return, so the CSRF check holds in both states. While the server is bound to loopback, refuse any request whose `Host` is not `localhost`, `127.0.0.1` or `[::1]` (with the port). Both are a few lines in `requireAuth`. The desktop window and the browser at `localhost` send a matching Origin and Host, so neither is affected.
- **Verdict:** CONFIRMED for the server side: there is no guard in the middleware, the handlers, or the listener (`serverapp/main.go` only chooses the bind address). What limits it in practice is the browser. Chrome's local network access permission (rolled out from late 2025) asks before a public page may reach loopback, which blocks both paths there unless the user allows it. I did not test any browser, and Firefox and Safari did not have an equivalent restriction as far as I know. A PUT, PATCH or DELETE needs a preflight that the server does not answer, so path 1 is limited to POST routes (setup, create library, create user, settings reset, restart for update, restore a backup); path 2 has no such limit.
- **Triage:**

## R01-2 Signing in to your own account resets the guess limit for everybody else's, from the same address

- **Severity:** S2
- **Class:** C2
- **Confidence:** high
- **Where:** `internal/api/auth.go:731` and `:827`, `internal/api/passkeys.go:213` and `:272`, `internal/api/twofactor.go:221` and `:471` (every `s.throttle.Reset(key)`); `internal/auth/auth.go:168`
- **Failure:** The per-address throttle allows ten attempts in five minutes, and it is the only limit that applies from inside the house, because the per-account wait is switched off for private addresses on purpose. Any correct password for *any* account clears the address's whole count. So a household member (or anybody who redeemed an invite) on the LAN sends nine guesses at the administrator's password, signs in to their own account once, and repeats. The limit never trips, and the guessing runs at the speed of bcrypt, roughly five to ten a second. The same loop defeats two-factor for somebody who already knows the password: each challenge allows five codes, a new challenge costs one password check, and one in about 333,000 guesses is right.
- **Evidence:** Passes at `4faabca9`: 36 wrong guesses at the administrator from one address, never a 429.
  ```go
  func TestR01_OwnSignInResetsTheThrottleForEveryAccount(t *testing.T) {
      h := newHarness(t)
      h.secure(t, "the admin's long password")
      h.addMember(t, "kid", "the kid's own password")
      for round := 0; round < 4; round++ {
          for i := 0; i < 9; i++ {
              resp := h.do(t, "POST", "/api/auth/login", map[string]any{"username": testUser, "password": "guess"})
              if resp.StatusCode == http.StatusTooManyRequests { t.Fatal("throttled") }
          }
          h.loginAs(t, "kid", "the kid's own password")
      }
  }
  ```
  `TestACorrectPasswordClearsTheThrottle` asserts the reset, for the same account only.
- **Fix sketch:** Do not clear the address's count on success. Either let it decay on its own (ten per five minutes is generous for a real person), or count failures per address *and* name and clear only that pair. From inside the house the per-account wait could also apply to failures that come while a *different* account is signed in from that address, but the first change is enough.
- **Verdict:** CONFIRMED. From outside the house the per-account wait still holds (`accountWait` is keyed on the name and is not reset by another account's success), so this is an inside-the-network fault. That is the case a content-rating ceiling exists for: a child's account guessing a parent's password.
- **Triage:**

## R01-3 Two-factor can be replaced, and fresh recovery codes read, with a session or an API key and no password

- **Severity:** S2
- **Class:** other
- **Confidence:** high
- **Where:** `internal/api/twofactor.go:302` (`startTwoFactor`), `:327` (`enableTwoFactor`)
- **Failure:** `disableTwoFactor` and `newRecoveryCodes` both ask for the password, and the comment says why: "a session left open on somebody else's screen should not be enough to weaken the account or read fresh codes". Enabling asks for nothing, and it does not check whether two-factor is already on. So with a session left open (or a stolen cookie, or an API key, which these routes accept), a caller posts to `/api/profile/two-factor/setup`, then to `/api/profile/two-factor` with a code from the secret they were just handed. `store.EnableTwoFactor` overwrites the stored secret and the recovery codes. The owner's authenticator app stops working, the owner's recovery codes are dead, and the caller holds ten fresh ones. On an account that had two-factor off, the same two requests turn it on with the caller's secret, which locks the owner out of their next sign-in until an administrator removes it, and there is nobody to do that when the owner is the only administrator.
- **Evidence:** Passes at `4faabca9`. `turnOnTwoFactor`, `passwordStep` and `codeStep` are the existing helpers in `twofactor_test.go`.
  ```go
  func TestR01_TwoFactorReplacedWithoutThePassword(t *testing.T) {
      h := newHarness(t); h.withSealer(t); h.secure(t, tfPassword)
      oldSecret, _ := turnOnTwoFactor(t, h)
      resp := h.authed(t, "POST", "/api/profile/two-factor/setup", nil)
      var setup struct{ Key string }
      decodeInto(t, resp, &setup)
      newSecret, _ := base32.StdEncoding.WithPadding(base32.NoPadding).DecodeString(strings.ReplaceAll(setup.Key, " ", ""))
      resp = h.authed(t, "POST", "/api/profile/two-factor", map[string]any{
          "code": auth.TOTPCode(newSecret, time.Now().Add(-30*time.Second))})
      var on struct{ RecoveryCodes []string `json:"recovery_codes"` }
      decodeInto(t, resp, &on)
      if resp.StatusCode != 200 || len(on.RecoveryCodes) != 10 { t.Fatal("refused") }
      a, _ := passwordStep(t, h, testUser, tfPassword)
      r := codeStep(t, h, map[string]any{"challenge": a.Challenge, "code": auth.TOTPCode(oldSecret, time.Now())})
      if r.StatusCode != http.StatusUnauthorized { t.Fatal("owner's code still works") }
  }
  ```
  A second test confirmed `POST /api/profile/two-factor/setup` answers 200 to a request carrying only `Authorization: Bearer <api key>`.
- **Fix sketch:** Put `passwordConfirmed` in front of `startTwoFactor` (the Security pane already asks for the password for the other two actions), and refuse setup with 409 while two-factor is on, so replacing it means turning it off first. Consider refusing API keys on the whole `/api/profile/two-factor` and `/api/profile/passkeys` prefixes, as `keysManageable` does for keys.
- **Verdict:** CONFIRMED. No test covers enabling while already enabled, and `TestEnablingNeedsACodeFromTheApp` only checks the code. The caller cannot sign in afresh with what they gain unless they also have the password, so this is a lockout and a loss of the second factor, not a takeover on its own.
- **Triage:**

## R01-4 An API key is minted with a session alone, and outlives the password change meant to end a compromise

- **Severity:** S2
- **Class:** C2
- **Confidence:** low (the behaviour is certain; whether it is a fault is a design call)
- **Where:** `internal/api/apikeys.go:56` (`createAPIKey`), `internal/api/auth.go:844` and `internal/api/users.go:176` (only sessions are deleted)
- **Failure:** Somebody with a few seconds at an unlocked LANcast window, or a stolen session cookie, posts to `/api/keys`. No password is asked. The owner notices something is wrong and changes their password, or an administrator resets it and "signs them out everywhere". Every session dies. The key does not, and it goes on reading the library, the watch history and the streams as that person until somebody thinks to open the API keys list. Adding a passkey, by contrast, asks for the password for exactly this reason ("a passkey is a new way into the account, and a session somebody left open must not be enough to add one").
- **Evidence:** Passes at `4faabca9`.
  ```go
  func TestR01_APIKeySurvivesPasswordChange(t *testing.T) {
      h := newHarness(t); h.secure(t, tfPassword)
      key, _ := mint(t, h, "minted with no password asked")
      resp := h.authed(t, "POST", "/api/auth/password", map[string]any{
          "current_password": tfPassword, "new_password": "a brand new password"})
      if resp.StatusCode != http.StatusNoContent { t.Fatal(resp.StatusCode) }
      if r := h.authed(t, "GET", "/api/libraries", nil); r.StatusCode != http.StatusUnauthorized { t.Fatal("session lived") }
      if r := h.doKey(t, "GET", "/api/libraries", key, nil); r.StatusCode != http.StatusOK { t.Fatal("key was revoked") }
  }
  ```
- **Fix sketch:** Ask for the current password when minting a key, as `passkeyRegisterOptions` does. That keeps ADR 0061's decision (a routine password change must not break the machine that copies photographs) and closes the route from a borrowed session to a credential that survives the remedy. Optionally, the admin reset (`resetUserPassword`), which is the "this account was compromised" action, could also revoke that account's keys and say so.
- **Verdict:** PLAUSIBLE. ADR 0061 has a section titled "Changing a password does not revoke keys", so survival is a documented decision and on its own is not a finding. What the ADR does not consider is that the key can be made without the password, and `apikeys.go` describes minting as needing "the password-backed credential", meaning only a session. A key cannot reach admin routes, cannot mint keys, and shows in the list with a last-used time, which bounds the damage.
- **Triage:**

## R01-5 A password longer than 72 bytes is answered with a 500

- **Severity:** S3
- **Class:** other
- **Confidence:** high
- **Where:** `internal/auth/auth.go:53` (`HashPassword`), reached from `authSetup`, `authChangePassword`, `createUser`, `resetUserPassword` and `redeemInvite`
- **Failure:** `bcrypt.GenerateFromPassword` refuses input over 72 bytes (`golang.org/x/crypto` v0.54.0). `HashPassword` wraps that as a generic error, and every caller turns it into `500 unexpected server error` and an ERROR line in the log. Somebody who chooses a long passphrase at first-run setup, or pastes one from a password manager set to 80 characters, is told the server failed, with nothing to say the password is the reason. A passphrase of non-Latin text reaches 72 bytes at 24 to 36 characters.
- **Evidence:** Passes at `4faabca9`.
  ```go
  func TestR01_LongPassphraseIsAServerError(t *testing.T) {
      h := newHarness(t)
      resp := h.do(t, "POST", "/api/auth/setup", map[string]any{
          "username": "admin", "password": strings.Repeat("correct horse battery staple ", 3)}) // 87 bytes
      if resp.StatusCode != http.StatusInternalServerError { t.Fatal(resp.StatusCode) }
  }
  ```
- **Fix sketch:** Add `ErrPasswordTooLong` beside `ErrWeakPassword` in `HashPassword` (check `len(password) > 72` in bytes), and answer 400 with the limit in the message wherever `ErrWeakPassword` is handled. Do not pre-hash to lift the limit; that would change what existing hashes mean. Update `docs/api.md` for the new 400.
- **Verdict:** CONFIRMED. No test in `auth_test.go` (either package) uses a long password.
- **Triage:**

## R01-6 Anybody can switch passkey sign-in off for everyone with a thousand requests

- **Severity:** S3
- **Class:** C3
- **Confidence:** high
- **Where:** `internal/api/passkeys.go:103` (`passkeyLoginOptions`), `internal/auth/passkey/challenges.go:57`
- **Failure:** `POST /api/auth/passkey/login/options` is public and not throttled. Each call stores a challenge for five minutes, and the store holds 1,000. A stranger who sends 1,000 requests to the public name every five minutes (about three a second) keeps it full. While it is full, every passkey sign-in and every attempt to add a passkey answers `429 too many sign-ins in progress`. Password sign-in still works.
- **Evidence:** Passes at `4faabca9`.
  ```go
  func TestR01_PasskeyChallengesCanBeExhaustedByAnyone(t *testing.T) {
      h := newHarness(t); h.secure(t, pkPassword)
      h.srvAPI.passkeyRPFor = func(*http.Request) (string, bool) { return pkRP, true }
      for i := 0; i < 1000; i++ {
          if r := h.do(t, "POST", "/api/auth/passkey/login/options", nil); r.StatusCode != 200 { t.Fatal(i) }
      }
      if r := h.do(t, "POST", "/api/auth/passkey/login/options", nil); r.StatusCode != http.StatusTooManyRequests { t.Fatal(r.StatusCode) }
  }
  ```
- **Fix sketch:** Bound challenges per client address (a few dozen), and when the store is full evict the oldest sign-in challenge instead of refusing the new one. Keep registration challenges in their own budget, since those are issued only after a password.
- **Verdict:** CONFIRMED. The cap is there on purpose, to bound memory on a public route; the fault is that hitting it refuses real people instead of the caller who filled it.
- **Triage:**

## R01-7 How long a failed sign-in takes says whether the account exists

- **Severity:** S3
- **Class:** C17
- **Confidence:** high
- **Where:** `internal/api/auth.go:698`
- **Failure:** For a name that matches no account, `authLogin` answers without running bcrypt. For a real account it runs bcrypt at cost 12 first. Measured through the test server: 0.5 ms against 196 ms. The reply text is the same for both, which is the rule the code states, but the timing gives the answer away to anybody on the internet: a list of candidate names is sorted into real and not real at ten requests per five minutes per address. The account picker is kept to the home network for exactly this reason ("a name is half of every login").
- **Evidence:** Passes at `4faabca9`; logged `existing account 196.4452ms, unknown name 515µs` (fastest of five each).
  ```go
  known, unknown := timeIt(testUser), timeIt("nobody-here") // POST /api/auth/login, wrong password
  if known < 10*unknown { t.Fatal("no clear gap") }
  ```
- **Fix sketch:** When the lookup finds nobody, run `auth.CheckPassword` against a fixed dummy hash made once at startup with the same cost, and discard the result.
- **Verdict:** CONFIRMED. The per-account wait (`TestTheWaitDoesNotRevealWhetherAnAccountExists`) hides existence in the 429 path only.
- **Triage:**

## R01-8 Redeeming an invite runs bcrypt before the secret is checked, and the invite throttle refuses nothing

- **Severity:** S3
- **Class:** C3
- **Confidence:** high
- **Where:** `internal/api/invites.go:188` (hash) before `:197` (lookup); `internal/api/invites.go:131` (`inviteUnusable`)
- **Failure:** Two things, one cause: the throttle is consulted only *after* a lookup has failed.
  1. `POST /api/invites/redeem` is public. With any made-up token and an eight-character password, the server spends about 200 ms of one core on bcrypt and only then finds the token is unknown. Nothing limits how often: the throttle changes the 404 into a 429 but the bcrypt has already run. A few dozen requests a second from one stranger occupy every core, which on this machine is the transcoder's CPU. Sign-in is careful about this ("a refused attempt costs the machine nothing").
  2. After the throttle has tripped for an address, a request with a *right* token still succeeds, because success never passes through `inviteUnusable`. The throttle therefore stops no guess from being tested. With 256-bit secrets guessing is hopeless anyway, so the cost of this half is only that the comment and the test (`…GuessingIsThrottled`) claim more than the code does.
- **Evidence:** Passes at `4faabca9`; logged `a junk-secret redeem took 200.5317ms`.
  ```go
  for i := 0; i < 15; i++ { h.do(t, "POST", "/api/invites/check", map[string]any{"token": "guess" + itoa(int64(i))}) } // ends in 429
  start := time.Now()
  h.do(t, "POST", "/api/invites/redeem", map[string]any{"token": "not a real secret", "username": "x", "password": "long enough password"})
  cost := time.Since(start) // ~200 ms: the bcrypt ran
  resp := h.do(t, "POST", "/api/invites/redeem", map[string]any{"token": m.Token, "username": "bad\u0007name", "password": "long enough password"})
  if resp.StatusCode != http.StatusCreated { t.Fatal(resp.StatusCode) } // 201 while "throttled"
  ```
- **Fix sketch:** In `redeemInvite`, check the address is not already over the limit first, then look the token up with `InviteByToken`, and hash the password only once the token is known to be good. `RedeemInvite` still does the single-use delete in its transaction.
- **Verdict:** CONFIRMED. `limitBodies` and the 8 KiB reader bound the body, not the work.
- **Triage:**

## R01-9 The sign-in throttle remembers every address for ever

- **Severity:** S3
- **Class:** C15
- **Confidence:** high
- **Where:** `internal/auth/auth.go:131`, `:150`
- **Failure:** `Throttle.attempts` gains an entry for each address that makes a sign-in, password-change, passkey or two-factor attempt, and an entry is removed only by a successful sign-in from that same address. An expired entry is replaced when its address returns, never swept. On a publicly reachable server every scanner that posts to `/api/auth/login` leaves an entry until the process restarts, and an attacker with an IPv6 /64 can add entries as fast as they can send requests (each is a string, a pointer and a small struct; ten million is on the order of a gigabyte). `inviteThrottle` is the same type. `AccountBackoff` in the next file has a cap and an eviction rule for precisely this reason; `Throttle` predates it.
- **Evidence:** By reading: `Allow` writes `t.attempts[key]` and nothing but `Reset` deletes. No test covers the map's size.
- **Fix sketch:** Sweep expired windows inside `Allow` when the map passes a size (as `twoFactorBook.issue` and `keepCookie` already do for theirs), and cap it as `AccountBackoff.makeRoom` does.
- **Verdict:** CONFIRMED by reading. Slow in ordinary use; the leak only matters for a server on the internet that stays up for months, or under deliberate abuse.
- **Triage:**

## R01-10 Three of the five places that take an account name skip the name rule

- **Severity:** S3
- **Class:** other
- **Confidence:** high
- **Where:** `internal/api/users.go:71` (`createUser`), `internal/api/auth.go:583` (`authSetup`), `internal/api/invites.go:183` (`redeemInvite`); the rule is `validName` at `internal/api/account.go:35`
- **Failure:** `validName` refuses control characters, because they "render as nothing and make two accounts look identical in every list that shows a name", and its comment says the rule is shared so that an administrator "cannot create a name a person could not choose for themselves". It is applied to the two rename routes only. Creating an account three other ways applies `TrimSpace` and nothing else, and one of them is public: somebody redeeming an invite can take the name `admin` followed by a zero-width or control character and appear in the People page, the account picker and the audit log as a second "admin". The length limits also disagree (60 for a rename, 64 for an invite, none for `createUser` and setup).
- **Evidence:** The R01-8 test redeems an invite with the name `"bad\u0007name"` and gets 201.
- **Fix sketch:** Call `validName` in all three. It may be worth extending it to refuse Unicode format characters (category Cf) while there, which is what a zero-width space is.
- **Verdict:** CONFIRMED. An invite holder is somebody the administrator chose, which is what keeps this at S3.
- **Triage:**

## R01-11 Two administrators deleting each other at the same moment leaves none

- **Severity:** S3
- **Class:** C8
- **Confidence:** low
- **Where:** `internal/api/users.go:120` to `:132`
- **Failure:** `deleteUser` counts the administrators and then deletes, as two separate store calls. The server then has no administrator and can only be recovered with `lancastd reset-auth` on the machine. - **Verdict:** PLAUSIBLE. Not reproduced: SQLite serialises writers, but the count is read before either write, so the interleaving is possible. It needs two administrators acting against each other within milliseconds.

## R01-13 Behind a proxy that ends TLS, the session cookie is not marked Secure

- **Severity:** S3
- **Class:** C2
- **Confidence:** low
- **Where:** `internal/api/auth.go:873`, `internal/api/sessioncookie.go:63`
- **Failure:** The cookie's `Secure` flag follows `r.TLS != nil`. `docs/security.md` offers "run LANcast loopback-only behind" Caddy or nginx as a supported way to publish it. In that arrangement the hop to LANcast is plain HTTP, `r.TLS` is nil, and the cookie is issued without `Secure` even though the person is on `https://`. If they later type or follow a plain `http://` address for the same name, the browser sends the session cookie in the clear before the proxy can redirect.
- **Evidence:** By reading; `TrustProxies` reads `X-Forwarded-For` only, and nothing reads `X-Forwarded-Proto`.
- **Fix sketch:** When the request came through a trusted proxy and carries `X-Forwarded-Proto: https`, treat it as TLS for the cookie. Only from a trusted proxy, for the reason `proxy.go` gives about forwarded headers.
- **Verdict:** PLAUSIBLE. `SameSite=Strict` stops the cookie going out on a link followed from another site, and a proxy that sends HSTS closes it after the first visit, so the window is narrow.

## R01-14 On a machine with a public address of its own, the account picker treats the ISP's subnet as the house

- **Severity:** S3
- **Class:** C17
- **Confidence:** low
- **Where:** `internal/api/loginpicker.go:75`
- **Failure:** `onHomeNetwork` counts any address inside a network that one of this machine's interfaces is on. That is what makes a phone on the house's IPv6 /64 count. On a machine that holds a public IPv4 address directly (a VPS, or a PC behind a modem in bridge mode), the interface's network is the provider's subnet, for example a /22 of a thousand strangers, and `GET /api/auth/accounts` hands each of them the list of account names. Only a /0 is excluded.
- **Evidence:** By reading. `loginpicker_test.go` tests a private network and a /64.
- **Fix sketch:** For IPv4, count only private and link-local ranges and drop the interface rule. Keep the interface rule for IPv6, where it was needed, and require at least a /48 there.
- **Verdict:** PLAUSIBLE. Depends on a network layout I could not check; behind an ordinary home router the interface networks are private and this cannot happen. The setting `login_picker` turns the picker off.

## R01-15 The guard on plugin fetches lets through carrier-grade NAT addresses, which is where Tailscale lives

- **Severity:** S3
- **Class:** other
- **Confidence:** low
- **Where:** `internal/netguard/netguard.go:78` to `:91` (`blocked`)
- **Failure:** `blocked` refuses loopback, RFC 1918, link-local, unique-local and anything not global unicast. `100.64.0.0/10` (RFC 6598) is none of those to Go's `net` package: `IsPrivate` is false and `IsGlobalUnicast` is true. A plugin granted `api.example.com` whose owner points that name at `100.x.y.z` therefore connects to a device on the owner's tailnet, which is the "network that machine sits in" the package says it will not reach. `198.18.0.0/15` and `192.0.0.0/24` pass the same way and matter less.
- **Evidence:** By reading, and from the `net` package's definitions. `netguard_test.go` has no case in `100.64.0.0/10`.
- **Fix sketch:** Add an explicit list of reserved IPv4 blocks to `blocked` (`100.64.0.0/10`, `192.0.0.0/24`, `198.18.0.0/15`, `240.0.0.0/4`), with a test case for each.
- **Verdict:** PLAUSIBLE. Needs an administrator to install a hostile plugin and grant it a host, and the server to be on a tailnet or behind carrier-grade NAT.
- **Triage:**

## Checked and clean

- **C2, loopback with no account.** `serverapp/main.go` `bindAddr` forces `127.0.0.1` whenever `CountUsers` is zero, and an unparseable address falls back to `127.0.0.1:8080`. `secured()` fails closed on a database error. `putPort`'s probe listens on the address the server would bind, never wider. The hole is in the browser, not the bind (R01-1).
- **C2, CSRF on a configured server.** `SameSite=Strict` on both `Cookie` and `ClearCookie`; `SameOriginRequest` runs for POST, PUT, PATCH and DELETE before the public-path exemption, so sign-in, setup, two-factor, passkey sign-in and the invite routes are covered too. An `Origin` of `null` is refused. It is skipped only for a key that actually resolved, a stream ticket (reads only), a guest bearer, and guest redemption, each with its reason in the code and a test (`TestAnUnusableBearerHeaderDoesNotDisableCSRF`).
- **C2, password change.** `authChangePassword` and `resetUserPassword` delete all of that account's sessions, including the caller's own, and clear the cookie. Since ADR 0015 this is per account, not every session on the server, which is the documented rule; the charter's wording ("deletes every session") predates accounts. Covered by `TestPasswordChangeRevokesSessions`.
- **C3, body cap.** `limitBodies` wraps the router outside `requireAuth` and outside version negotiation, so the 1 MiB ceiling applies before any gate. The four larger routes are matched by mux pattern and tested against the router (`TestLargeBodiesAreRoutes`). No `io.ReadAll` in any file of the slice. `/api/v1` is not a path prefix (`version.go` negotiates by header), so there is no second spelling of a route to slip past the pattern match.
- **C17, secrets.** Session tokens, API keys, invite secrets and recovery codes are stored as SHA-256 hashes and looked up by hash, so no comparison of a secret happens in Go. The metrics token is compared with `subtle.ConstantTimeCompare`. TOTP candidates, the WebAuthn challenge and the RP ID hash are compared in constant time. Passwords are never logged; a wrong name is not logged at all (it may be a password typed in the wrong box). `logUnauthenticated` logs nothing about the credential. Invite secrets travel in a POST body and the link's fragment, API keys in a header, never a query string. `userJSON` cannot carry the hash. The two-factor secret is sealed with AES-256-GCM under a key outside the database, with a fresh nonce per sealing.
- **Routes that skip the session gate.** `isPublicPath` is an exact list: health, auth status, sign-in and its second factor, setup, passkey sign-in (two routes), the account picker, and the two invite routes, plus the federation patterns (R02) and anything not under `/api/`. Each public handler in this slice was read: `authSetup` refuses once any account exists; `loginAccounts` returns names only and only to the home network; the rest are credential checks. Unknown `/api/` paths get a 404 in the error shape after the gate, not the web app.
- **Every `adminOnly` route in `server.go`** was read against the handler it wraps. `adminOnly` refuses a member, refuses an API key whoever owns it, and passes without a session only while no account exists. The unwrapped routes under `/api/profile`, `/api/keys` and `/api/auth` all read the caller from the session and act on that account only.
- **Session fixation and expiry.** A sign-in always mints a new 256-bit token; nothing accepts a token from the client. Expiry is checked on every lookup and slides 30 days from last use; there is no absolute lifetime, by design (`sessioncookie.go`). Expired rows are purged at each sign-in. Role and name are read through a join on every request, so a demotion or a deletion takes effect at once, for sessions, API keys and stream tickets (`streamTicket` re-resolves the session or key it was minted from).
- **Sign-in throttling, apart from R01-2.** The per-address check runs before the body is decoded and before bcrypt. The per-account wait folds case and spaces the way the `user` table's collation does, tracks names that match nothing, is bounded, and evicts the least-failed entry first. A right password with two-factor on does not clear either counter.
- **TOTP.** RFC 6238 parameters, one step of skew each way, a used step is spent in one SQL statement so a replay or a race wins once, and five tries per challenge. Recovery codes are 8 characters from 31 (about 40 bits), hashed, single use.
- **Passkeys.** `VerifyRegistration` and `VerifyAssertion` check type, challenge, origin (https, host equal to the RP ID), the RP ID hash, user presence and user verification. CBOR decoding is bounded and refuses duplicate keys. Keys are parsed and validated at registration (P-256 point on curve, Ed25519 length, RSA at least 2048 bits with a sane exponent). A challenge is single use, bound to its purpose, and for registration bound to the account that proved its password. The user handle must match the credential's owner. A signature counter that fails to rise is refused. Passkeys are offered only on a TLS request for the public certificate's own name while that certificate is valid.
- **API key scope.** A key cannot reach an admin route, mint, list or revoke keys, or send a problem report; it does not mark its owner as online. An unknown key falls through to the cookie path with CSRF intact. All tested.
- **Invites.** 256-bit secret, stored hashed, seven days, single use enforced by a delete inside the redeeming transaction, always a member, with the invite's rating ceiling and hidden libraries applied in the same transaction. The secret is never in a URL the server sees.
- **Trusted proxies.** `X-Forwarded-For` is read only from listed addresses, right to left, stopping at the first unlisted or unparseable hop; a network wider than /8 (or IPv6 /16) is refused; a list that no longer parses drops entirely.
- **`internal/secret`.** Key created with `O_EXCL` and mode 0600; a key file of the wrong size is an error and is left alone; `Open` refuses short input before slicing.
- **`internal/servermode`.** Links and devices inside a library folder are refused, not followed. The copy is proven before any rename, every step that changes which folder holds a library is a rename and never a delete, and each failure path was traced back to "the mode that was running still has its database under its own name". No fault found.
- **C15, apart from R01-9.** `twoFactorBook`, `passkey.Challenges`, `cookieSent` and `AccountBackoff` are each bounded or swept. Nothing in the slice starts a goroutine.
- **C8.** No `*sql.DB` reaches any file in the slice.
