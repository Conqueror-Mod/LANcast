## R02-1 A paired server's bytes are served from this household's origin with the paired server's Content-Type

- **Severity:** S1
- **Class:** other
- **Confidence:** high (the mechanism); exploitation needs a hostile peer and one navigation
- **Where:** `internal/api/peerplay.go:298` (`copyStreamHeaders`), used by `peerArtwork` (:576), `pipeFromPeer` (:70), `peerHLSSegment` (:151), `peerSubtitleFile` (:181) and `peerStream` (`peerbrowse.go:116`)
- **Failure:** A paired server that turns hostile (or is compromised) answers `GET /api/federation/artwork/{item}/{hash}` with `Content-Type: text/html` (or `image/svg+xml`) and a body containing script. This server relays it unchanged at `https://<this server>/api/peers/{fp}/artwork/{item}/{hash}`. Anyone in this household who opens that URL as a page — "Open image in new tab" on a friend's poster in a browser, or a link — runs the peer's script **in this server's origin**. From there `fetch` is same-origin: the `SameSite=Strict` cookie is attached and the `Origin` check passes, so the script acts as that person, and as an admin it can add libraries at arbitrary paths, read the filesystem browser, mint API keys, and so on. The pairing was meant to trust the far server about its own people, not to give it script on this one. There is nothing to stop it: `copyStreamHeaders` forwards `Content-Type` verbatim, and no response anywhere in `internal/` carries `Content-Security-Policy`. `X-Content-Type-Options: nosniff` appears only in `comics.go`, `picture.go` and `previews.go`.
- **Evidence:** A proving test, run in the worktree and not committed:
  ```go
  func TestR02PeerContentTypePassesThrough(t *testing.T) {
      resp := &http.Response{Header: http.Header{}}
      resp.Header.Set("Content-Type", "text/html; charset=utf-8")
      w := httptest.NewRecorder()
      copyStreamHeaders(w, resp)
      if got := w.Header().Get("Content-Type"); got != "text/html; charset=utf-8" { t.Fatalf("%q", got) }
      if w.Header().Get("X-Content-Type-Options") != "" || w.Header().Get("Content-Security-Policy") != "" { t.Fatal("hardened") }
  }
  ```
  ```
  zz_r02_proof_test.go:22: forwarded Content-Type: "text/html; charset=utf-8"; nosniff: ""; CSP: ""
  --- PASS: TestR02PeerContentTypePassesThrough (0.00s)
  ```
  `grep -r "Content-Security-Policy" internal/` (non-test files) finds nothing.
- **Fix sketch:** On every peer pipe, choose the type per route instead of trusting the peer: artwork only `image/jpeg|png|webp|gif` (never SVG), segments `video/mp4|video/iso.segment|video/mp2t`, the playlist already set locally, subtitles `text/vtt`, stream `video/*|audio/*`, otherwise `application/octet-stream`. Always add `X-Content-Type-Options: nosniff`, plus `Content-Security-Policy: sandbox; default-src 'none'` on piped responses. A server-wide `nosniff` (and a CSP for the SPA) belongs to R07/R10 and would close the class.
- **Verdict:** CONFIRMED. The test proves the pass-through. I found no caller that overrides the header after `copyStreamHeaders`, and no middleware that adds one. What it needs: a hostile peer (a pairing the household chose) and a person opening the URL top-level. An `<img>` or `<video>` will not run HTML, which is why triage may weigh it as S2.
- **Triage:** Fixed and merged in #1088.

## R02-2 The HLS segment route authorises the item in the path, not the session it serves

- **Severity:** S2
- **Class:** C5
- **Confidence:** high
- **Where:** `internal/api/transcode.go:194` (`hlsSegment`: `s.trans.Session(sessionID)` with no check of `sess.ItemID` or `sess.Owner`), reached by peers through `federationplay.go:94` / `server.go:860`, and by guests through `guestgate.go:63` / `auth.go:232`
- **Failure:** `federationPlay` and the guest gate both decide using `{item}` in the path, and then `hlsSegment` serves whichever transcode session `{session}` names. The session's own `ItemID` and `Owner` (`transcode/session.go:18-22`) are never compared with that path item or with `streamOwner(r)`. Example: a friend's server was given HLS session `S` for film B, and the host then stops sharing B's library mid-film. A modified friend server keeps requesting `/api/federation/hls/A/S/seg-0412.m4s`, where A is any item still shared. `peerMayPlay(A)` passes, and the segments of B keep flowing. Each request calls `sess.Touch()`, so the session never idles out. The un-share that ADR 0071 §6 says "takes effect on the next request" does not take effect for a stream that is already running. The guest path `/api/stream/{id}/hls/{session}/{name}` has the same shape.
- **Evidence:** `transcode.go:183-218`: the only checks are `validSegmentName(name)` and `sess == nil`. Searching the tests for a segment request whose session belongs to another item or owner finds none. Session ids are 64 random bits (`transcode/manager.go:1091`), so a caller cannot guess someone else's session. Its realistic use is a session the caller was legitimately given and has since lost the right to.
- **Fix sketch:** In `hlsSegment`, 404 unless `sess.ItemID == pathID` and `sess.Owner == s.streamOwner(r)`. The data is already on the session. Add one federation test and one guest test that ask for another item's session through an allowed item.
- **Verdict:** CONFIRMED by reading. Nothing between `federationPlay` and `os.Open(path)` relates the session to the item. The honest friend server always sends the session's own item in the path, which is why nothing has noticed. The exploit needs a peer that changes the path.
- **Triage:** Fixed and merged in #1089.

## R02-3 One paired server's people can fill the host's guest-session book and lock out every other paired server

- **Severity:** S3
- **Class:** other
- **Confidence:** high
- **Where:** `internal/api/guestsession.go:55` (`maxGuestSessions = 512`, one global book) and :92
- **Failure:** Any signed-in account on paired server P can mint tickets without limit (`guestticket.go:63`, any account, a fresh nonce each time) and redeem them at host H. The nonce store allows 4096 per issuer, but the session book holds 512 **in total**. So 512 redemptions from P fill H's book for 15 minutes (`guestSessionTTL`), and during that time a guest from every other paired server gets `503 busy`. Repeat every 15 minutes to keep it full. `nonce.go:25-31` rejects exactly this design for nonces ("one peer flooding … every other peer's tickets would then be refused"), but the book a ticket is redeemed into has the global bound anyway.
- **Evidence:** `guestBook.add` sweeps expired entries and then refuses at `len(b.m) >= maxGuestSessions`, with no per-peer count. `redeemGuestTicket` spends the nonce, then calls `add`.
- **Fix sketch:** Bound the book per peer (for example 64 per issuer fingerprint), the same way `NonceStore` bounds nonces, keeping the global cap only as a backstop well above per-peer × peers.
- **Verdict:** CONFIRMED by reading. This matters less than it once did: since ADR 0071's amendment the desktop client reaches a friend's films through its own server, not by ticket, so the guest-ticket path mostly serves browsers.
- **Triage:** After 1.0: needs a hostile paired friend, and since ADR 0071 the window no longer uses tickets.

## R02-4 The peer watcher names accounts that opted out of peer visibility to every paired server, every ten seconds

- **Severity:** S3
- **Class:** other (privacy, ADR 0035 / 0045)
- **Confidence:** high
- **Where:** `internal/api/peerwatch.go:147-148` (`for _, user := range users { s.askPeerPresence(ctx, p, user) }`, with `users = s.events.Users()`)
- **Failure:** Account `u_7k2` has `visible_to_peers` off, so it is not in the roster and nobody elsewhere can name it. While `u_7k2` has a window open, this server still sends `GET /api/federation/presence?person=u_7k2` to every paired server every `presenceEvery` (10 s). The far server learns that the account id exists and exactly when it has a window open. The call is also useless: the far side's grants can only name people on this server's roster (`ReadersOf`, foreign key to `remote_person`), so the answer for an opted-out account is always empty. ADR 0045 §3 bounds what crosses as online/watching *for people who opted in*, and here an opted-out account's online pattern is crossing.
- **Evidence:** `watchPeer` filters `users` only by "has an event stream open". `RosterForPeers` (`store/peer.go:409`) is the only place `visible_to_peers` is consulted, and the watcher does not use it. `peerPresence` (`presence.go:283`) does the same for `me`, but only when the person opens People.
- **Fix sketch:** Skip `askPeerPresence` for accounts not in `RosterForPeers` (one query per tick), in both the watcher and `peerPresence`.
- **Verdict:** CONFIRMED by reading. `visible_to_peers` is consulted only by `RosterForPeers` and the settings routes (searched in `internal/`), and it **defaults to 0** (`migrate.go:1183`), so in practice this names most of a household. The id is opaque and `/api/federation/presence` is in `polledPaths`, so an honest far server does not log it. A hostile or curious one can.
- **Triage:** Before 1.0, wave B (see [triage.md](../triage.md)).

## R02-5 Peer JSON answers are decoded with no size limit

- **Severity:** S3
- **Class:** C3
- **Confidence:** high
- **Where:** `internal/api/presence.go:362` (`callPeer`: `json.NewDecoder(resp.Body).Decode(out)`)
- **Failure:** `callPeer` carries the roster fetch, presence, `peerLibraries`, `peerItems`, `peerItem` and `peerTitle`. A paired server answering any of them with an endless or huge JSON array has it decoded in full into memory, bounded only by the 3 s `peerDeadline`. Over a LAN that is hundreds of megabytes per call, and the watcher makes these calls every 10 s per peer per open window. A roster fetched this way then goes to `ReplaceRemotePeople` unchecked. The *pushed* roster is capped at `maxRosterBytes` and `maxRosterPeople` (`rosterpush.go:139-153`), but the *fetched* one is not. `sendPeer` caps at 64 KiB (`togetherrelay.go:93`) and the playlist at 1 MiB (`peerplay.go:137`), so this is the one decoder on the peer path without a cap.
- **Evidence:** As quoted. There is no `LimitReader` or `MaxBytesReader` in `callPeer`.
- **Fix sketch:** `io.LimitReader(resp.Body, maxPeerJSON)` (for example 4 MiB, above a 200-item page with artwork), and apply the push path's roster validation (count, id and name lengths) to the fetched roster as well.
- **Verdict:** CONFIRMED by reading. It needs a hostile or broken peer.
- **Triage:** Before 1.0, wave B (see [triage.md](../triage.md)).

## R02-6 Guest CORS never matches an origin on the default port, which is how a public name is reached

- **Severity:** S3
- **Class:** C5
- **Confidence:** high (the mechanism); low (how many people use the ticket path from a browser)
- **Where:** `internal/api/guestcors.go:70-72` (`strings.EqualFold(a, host)`) with `originHost` (:82)
- **Failure:** A peer's recorded addresses are `host:port`. `ourInvite` writes the public name as `thelighthouse.example:443` (`peers.go:118-119`). A browser on the standard port sends `Origin: https://thelighthouse.example` with no port, because browsers omit the default port. `originHost` returns `thelighthouse.example`, which never equals `thelighthouse.example:443`, so no CORS headers are sent and the guest page cannot read any answer from this host. The failure is closed, not a security issue, but it means the feature fails on the one address ADR 0044 §5b added for friends on other networks.
- **Evidence:** As quoted. `guestcors_test.go:103` asserts that `https://127.0.0.1` ("right host, no port") gets no CORS against a peer recorded at `127.0.0.1:1`. That is right for port 1, and no test covers a peer recorded at `:443`. The suggested fix keeps the existing test green, because 443 ≠ 1.
- **Fix sketch:** Normalise both sides: an origin with no port takes 443 for `https` and 80 for `http`, and compare host and port.
- **Verdict:** CONFIRMED by reading. Reachability is uncertain because the window no longer uses tickets (ADR 0071 amendment).
- **Triage:** After 1.0: reachability is uncertain, since ADR 0071 the window no longer reaches a friend's films by ticket. Check it when Watch Together across servers is next tested.

## R02-7 One account can hold an unbounded number of remote players, each with 16 queued half-megabyte commands

- **Severity:** S3
- **Class:** C3
- **Confidence:** low
- **Where:** `internal/remote/remote.go:189` (`Report` registers any new id), :271 (`Send`, up to `MaxPending` = 16 commands of up to 20,000 ids each), `internal/api/remote.go:120` (512 KiB body)
- **Failure:** A signed-in member script reports N player ids every few seconds (each lives 20 s without a report) and sends 16 play commands with full queues to each one. A full queue is about 160 KB of `int64`s, so 16 of them is about 2.5 MB per player, and nothing bounds N. A thousand fake players hold about 2.5 GB. `MaxPending` and `MaxQueue` were written as a memory bound, but they bound memory per player, not per account.
- **Evidence:** No count of players per `user` in `Manager`. `sweepLocked` removes only players that have gone silent.
- **Fix sketch:** Cap players per account (for example 16, refusing new ids beyond that) and drop a player's oldest commands by total queue length as well as count.
- **Verdict:** PLAUSIBLE. The mechanism is certain, but the actor is an authenticated member of the household, which the project otherwise trusts with far more.
- **Triage:** After 1.0: needs a hostile household member, whom the project trusts with more.

## Checked and clean

- **C5, the peer gate.** All 18 `/api/federation/` routes in `server.go:819-892` are in `peerAuthenticated` (`auth.go:78`), and every handler starts with `federationPeer`, directly or through `federationPlay` or `federationPerson`. An unknown key gets 403, and no client certificate gets 401 (`FingerprintFromState`). Only the peer TLS config asks for a client certificate, so a browser cannot reach that state. The router enumeration test keeps the list honest.
- **C5, the guest gate.** `guestAllowed` holds 9 entries. Every route that names an object declares `item`, and the middleware 404s unless `MayPlay(Friend(peer))` passes. `subtitles/search` is excluded. The listing routes derive scope from `CeilingFor` and fail closed, and `parent` is checked with `MayPlay` first. A guest token on any other route gets 403 before routing. No `/api/federation/` route is reachable with a guest token. The object check uses the peer fingerprint, never `userID()`. The one gap is in the handler behind the gate (R02-2).
- **Tickets.** Signed bytes are domain-separated, versioned and length-prefixed, and decoding rejects trailing bytes. The audience is checked before the key, the pin is "this key's fingerprint is a paired peer" (`State == paired`), Ed25519 is verified, then expiry and a 60 s skew. Every refusal is the same 401, with the reason only in this server's log. Nonces are spent after verification, per issuer, and refused rather than evicted. A ticket names a person and an audience and carries no permissions. The session token is 256 bits from `crypto/rand`, stored as a hash, sent only as a bearer header, and never in a URL or log.
- **Unpairing and revocation.** `removePeer` cascades the roster, grants and shares. Every federation request re-reads the peer row. Guest object checks and room membership (`mayAsk` on join and poll, `Playing` swept per call) are resolved per request. The exception is R02-2.
- **What a paired peer can do.** It can read what was shared with it and the presence of people who granted its named person. It can ask, poll, withdraw, join or leave only its own requests and rooms: `Status` and `Withdraw` check fingerprint and person, and `JoinRemote` admits only a member that `Accept` added. Its learned address comes from the authenticated connection, never loopback. Its roster push is capped and validated. It names its own people, which is the documented trust of a pairing. It cannot name this server's people, because the relay always sends `person` from the caller's own session and `forwardedQuery` strips `person` and `together` from clients.
- **`federationPeer` accepts `added` as well as `paired`.** Its comment says it refuses anything not paired. An `added` row is still a key the admin pasted from an invite, so this widens nothing a share was not already granted to by fingerprint. Recorded so nobody files it.
- **C2.** Federation POST, PUT and DELETE pass the CSRF check because a server sends no `Origin` or `Referer` (`SameOriginRequest` allows that), and they are authenticated by the pin. Guest redemption and guest bearer calls are exempt for the reason written at `auth.go:202-266` (no ambient credential), which is sound. Guest CORS never sends `*` or `Allow-Credentials`, applies only to allow-listed routes plus redemption, matches paired origins only, and adds `Vary: Origin`.
- **C3.** The global 1 MiB body cap (`bodylimit.go`) is applied before auth and covers every federation route. Ticket bodies are capped at 8 KiB, the roster push has its own cap, `sendPeer` reads at most 64 KiB, the peer playlist at most 1 MiB, invite fields are bounded and cleaned, and room and player ids are length-checked. The one gap is R02-5.
- **C15, timeouts and leaks.** `peer.Client` has an 8 s overall timeout. `StreamClient` bounds dial (5 s), handshake (5 s) and response header (6 min, which is documented), and the body is cancelled with the viewer's request context. `callPeer` and `sendPeer` have a 3 s budget across all addresses. `Reach` goroutines end with their context, and their result channel is buffered. `WatchPeers` stops its ticker, and its goroutines are joined per tick. Each call builds a fresh `http.Transport` that is never closed, but idle connections expire after 30 s, so the cost is bounded (a handshake per segment, not a leak). The together, remote and nonce maps are swept on access.
- **C17.** The identity key is written 0600 by temp file and rename, and a corrupt or unreadable key refuses to start instead of being regenerated. The ACME account key is 0600. Presence is never logged (`/api/federation/presence` is in `polledPaths`). `certpin.TLSConfig` compares in constant time. Guest sessions are looked up by token hash in a map, so there is no secret comparison to time.
- **TLS pinning and trust on first use.** Peer dials use TLS 1.3, pin the invite's fingerprint in `VerifyPeerCertificate`, and present the identity certificate. Inbound connections use `RequireAnyClientCert` with a database lookup per request. `peer.Attach` diverts only ClientHellos that carry the `lancast-peer/1` ALPN, and `serverapp` checks `acme-tls/1` first and then hands the hello to the peer branch. `knownserver.Fetch` is the only unverified handshake, and it sends nothing. `Check` and `CheckIdentity` separate unknown, match, rotated and mismatch, `RecordIdentity` never overwrites an identity, and an unparsable store fails toward asking again.
- **Room and player isolation.** Remote players are keyed by `(user, id)`, and a command to another account's player is the same 404 as a missing one. A remote room member is `peer:<fp>/<person>`, which cannot collide with `u_…` ids. Local rooms are listed to every local account, which is the documented household design (`together.go:21`).
- **C1, C8, C9, C11–C14, C16, C18.** Nothing in the slice turns a database row into a path itself (the delegated handlers belong to R03). There is no SQL and no ffmpeg in the slice, no dates shown to users, no client code, and no ignored error on a data-integrity path. `MarkPeerSeen` and the address learning are best-effort by design.
