## R07-1 A subtitle download's `language` writes a file anywhere the server can write

- **Severity:** S1
- **Class:** C1
- **Confidence:** high
- **Where:** `internal/api/subsearch.go:144` and `:150` (`downloadSubtitle`); `internal/subtitle/subtitle.go:324` (`normalizeLanguage` returns unknown input unchanged)
- **Failure:** `POST /api/items/{id}/subtitles/download` is open to every signed-in account and to API keys; it is not `adminOnly`. It builds the destination as `filepath.Join(dataDir, "subtitles", "downloaded", id, fmt.Sprintf("%d.%s.srt", fileID, lang))`. `lang` is `NormalizeLanguage(req.Language)`, which lowercases and trims the text and returns anything it does not recognise unchanged. With `{"file_id": <any real id>, "language": "x/../../../../../escaped"}`, `filepath.Join` cleans the `..` and the file is written outside the data directory. Each extra `../` climbs one more folder. The installed service runs as SYSTEM, so a member can create or overwrite any `*.srt` path on the machine: inside another library's folders, in a system folder, or enough of them to fill a disk. The content is whatever OpenSubtitles serves for that `file_id`, and anyone can upload a file there. Only the first 512 bytes are checked for being text, and the rest can be up to 8 MiB of anything. The built-in key (ADR 0110) means a server needs no setup for this to work. The row is then recorded too. Serving and deleting re-check containment, so the planted file cannot be read or removed through the API afterwards.
- **Evidence:** this test was run in the worktree and is not committed. It used the harness's fake OpenSubtitles server, the same way `TestSubtitleSearchFromAnEpisodeSendsItsShowsID` does:
  ```go
  resp := h.do(t, "POST", "/api/items/"+itoa(id)+"/subtitles/download",
      map[string]any{"file_id": 7, "language": "x/../../../../../escaped"})
  // status 200
  // WROTE OUTSIDE THE DATA DIRECTORY: C:\Users\Chris\AppData\Local\Temp\TestR07SubtitleLanguageEscapesDataDir3153448989\escaped.srt
  //   (data dir C:\Users\Chris\AppData\Local\Temp\TestR07SubtitleLanguageEscapesDataDir3153448989\001)
  ```
- **Fix sketch:** Accept `language` only when it is a known code, using the table `NormalizeLanguage` already has, or failing that only `[a-z]{2,3}(-[a-z0-9]+)?`. Then put the destination through `containedPath(filepath.Join(dataDir, "subtitles"), dest)` before writing, so the next field added to the name cannot reopen this. Add a test that a traversal in `language` returns 400 and writes nothing.
- **Verdict:** CONFIRMED. The proving test wrote the file. `server.go:966` registers the route with no `adminOnly`, and `requireAuth` lets API keys through to non-admin routes (R01's "API key scope"). Nothing between the decoder and `os.WriteFile` looks at the characters of `language`.
- **Triage:** Fixed and merged in #1117.

## R07-2 Reset settings skips what saving settings does, and deletes credentials the docs promise it keeps

- **Severity:** S2
- **Class:** other
- **Confidence:** high
- **Where:** `internal/api/maintenance.go:74` (`resetSettings`), compared with `internal/api/settings.go:535`–`596` (`putSettings`'s side effects); `docs/api.md:5989`
- **Failure:** `POST /api/settings/reset` writes `config.Defaults()` over everything except a short keep-list, and then only calls `rebuild`. None of the effects `putSettings` runs when the same fields change are run:
  - **`optimized_dir`** goes back to the default folder without `requeueMissingOptimized`. This brings back R03-2: every ready copy stays offered and none can be served.
  - **`photo_places`** goes from on to off without `locations.Forget`. The switch reads off, but every location it read stays in the database, and ADR 0078 promises that off deletes them.
  - **`match_music`** defaults to on. If it was off, the store's queue flag (`SetMusicMatching`) stays off until a restart while Settings shows it on.
  - **`scrub_previews` / `detect_markers` / `retro_artwork`**: nothing is kicked, the same "switch looks broken" case `putSettings` comments on.

  The keep-list also leaves out credentials. The docs say "credentials and machine facts survive", but a reset deletes **every webhook with its secret**, the **metrics token** (a Prometheus scraper configured elsewhere starts getting 403s), the **trusted proxies** (behind a proxy, every client then looks like the proxy, which the sign-in throttle and the home-network checks depend on), and the DLNA account and switch. `changedSettings` covers neither webhooks nor the metrics token, so the audit entry does not mention losing them.
- **Evidence:** `maintenance.go:80`–`98` keeps `PasswordHash`, the three provider keys, the OpenSubtitles login, `BuiltinKeysOff`, the TLS paths, `PublicCert`, `ACMEDirectoryURL` and `FFmpegDir`. Every other field of `config.Settings` (`internal/config/settings.go`) comes from `Defaults()`, which has no `Webhooks`, `MetricsTokenHash` or `TrustedProxies`. The handler body stops at `rebuild` (`:109`).
- **Fix sketch:** Also keep `Webhooks`, `MetricsTokenHash`/`MetricsTokenCreated` and `TrustedProxies`, and say so in `docs/api.md`. Move `putSettings`'s after-save block (`settings.go:535`–`596`) into a helper that takes `(prev, next)`, and call it from both handlers.
- **Verdict:** CONFIRMED. I read both handlers side by side. No other code reacts to a settings change: the dispatcher reads webhooks per event, so they really are gone, and `requeueMissingOptimized`, `Forget` and `SetMusicMatching` are only called from `putSettings`.
- **Triage:** Fixed and merged in #1133.

## R07-3 `POST /api/update/download` is documented as 200 with the staged version, but answers 202 with no body

- **Severity:** S2
- **Class:** C7
- **Confidence:** high
- **Where:** `internal/api/update.go:42`–`66`; `docs/api.md:4144`; `docs/openapi.json` `paths./update/download.post`
- **Failure:** Both the prose and the spec say the route "returns the staged version" (`200`, `StagedUpdate`) and that calling it with no update available "is a no-op rather than an error". The handler starts a goroutine and answers `202` with an empty body. It also answers `409 conflict` while a download runs, `412 unverifiable` on a build that cannot verify signatures, and `503` without an updater, and the spec lists none of these. A third-party client built from the spec waits for a body that never comes. The web client already knows the real behaviour (`web/src/api/hooks.ts:3356`), which is why this has not shown up in the app.
  A second, smaller drift is in the same slice. `POST /api/items/{id}/subtitles/download` returns `{key, language, label}`, but `DownloadedSubtitle` in the spec has only `key`.
- **Evidence:** I compared each handler's response keys with the spec's response schema for 35 routes in the slice, using a script over `docs/openapi.json`. These two disagreed. The others matched (see "Checked and clean").
- **Fix sketch:** Rewrite the prose and the spec for `202` with no body plus the 409, 412 and 503 answers, and point to `GET /api/update`'s `downloading`/`staged` for progress. Add `language` and `label` to `DownloadedSubtitle`.
- **Verdict:** CONFIRMED. `openapi_test.go` checks method, path parameters and `$ref`, not status codes or properties, so it cannot catch this. The client comment confirms the handler's behaviour is deliberate and that the docs are what is stale.
- **Triage:** Fixed and merged in #1135.

## R07-4 Downloading a subtitle that is already there answers with another film's subtitle key

- **Severity:** S2
- **Class:** other
- **Confidence:** high
- **Where:** `internal/api/subsearch.go:157`–`167` (`downloadSubtitle` returns `"external-"+subID`); `internal/store/subtitle.go:59`–`68` (`AddSubtitle`: `INSERT … ON CONFLICT(item_id, path) DO UPDATE …` then `LastInsertId()`)
- **Failure:** When the same film downloads the same `file_id` again, the upsert takes its UPDATE branch. SQLite leaves `last_insert_rowid()` unchanged in that case, so `AddSubtitle` returns the row id of whatever was last inserted on that pooled connection. That row may be another film's subtitle or a row in another table entirely. The client is told to load `external-<that id>`, which `ExternalSubtitle(ctx, item, id)` scopes to the item, so the track 404s and no subtitle appears. People hit this by searching again for a film they already fetched subtitles for: auto-match picks the same file.
- **Evidence:** a test run in the worktree and not committed: download `file_id` 7 for film A, then 8 for film B, then 7 for A again.
  ```
  first=external-1 unrelated=external-2 again=external-2
  ```
  The third answer names film B's subtitle.
- **Fix sketch:** Add `RETURNING id` to the upsert and scan it, or `SELECT id` by `(item_id, path)` after the statement. A test should assert that the second download returns the first key.
- **Verdict:** CONFIRMED by the test above. The store half is R05's file, but the user-facing fault is this handler's answer, so it is recorded here once.
- **Triage:** Fixed and merged in #1122.

## R07-5 The activity feed names libraries hidden from the account asking

- **Severity:** S3
- **Class:** other
- **Confidence:** high
- **Where:** `internal/api/activity.go:79`–`87` and `:179`–`188`
- **Failure:** `GET /api/activity` is open to every signed-in account and polled by every window. It lists scans from `s.st.ListLibraries` with no `hiddenFor` filter, so a member whose administrator hid a library sees "Scanning \<hidden library's name\>", its `library_id`, and the scan's `error`, which is `err.Error()` from the walk (`scan/scanner.go:390`) and can carry a filesystem path. `GET /api/libraries` and `GET /api/libraries/{id}/scan` hide the same facts: the first through `hiddenFor`, the second through `libraryVisible`. The feed also lists every account's conversion as `transcode:<session id>`. Since #1089 the segment route checks the session's owner, so that id is no longer a key, only a sign that someone else is converting.
- **Evidence:** `listLibraries` (`libraries.go:19`–`26`) filters by `s.hiddenFor(r)`, and `activity` calls the same `ListLibraries` with no filter.
- **Fix sketch:** Filter the scan rows by `hiddenFor` for anyone but an administrator, and drop `error` for members. Keep transcode rows to the caller's own sessions, the way `transcodeSessions` does, unless the caller is an administrator.
- **Verdict:** CONFIRMED. I checked that no middleware narrows `/api/activity`: it is a plain route at `server.go:1004`.
- **Triage:** Before 1.0, wave C (see [triage.md](../triage.md)).

## R07-6 An item edit and its lock are written separately, so a failure or a refresh in between leaves the edit unlocked

- **Severity:** S3
- **Class:** C4
- **Confidence:** high
- **Where:** `internal/api/meta.go:125`–`134` (`patchItem`)
- **Failure:** `UpdateItemMetadata` commits the new values, and then `LockField` runs once per field, each as its own statement with no transaction. If a lock write fails, for example `SQLITE_BUSY` past the 5 s timeout during a retention `VACUUM` (R04's notes), the client gets a 500 but the edit is saved unlocked. The next provider refresh overwrites the hand edit. The same happens if the enrichment worker is merging that item between the two writes. This is the locked-fields rule losing on a rare path, which is why it is an S3 and not an S1.
- **Evidence:** `store/meta.go:36` (`LockField`) and `:81` (`UpdateItemMetadata`) each call `s.db.ExecContext` on their own. The handler calls them one after the other.
- **Fix sketch:** Add one store method that updates the fields and inserts the locks in one transaction, and have `patchItem` call only that.
- **Verdict:** PLAUSIBLE. The mechanism is certain. I did not reproduce the failing lock write or the race, because both need a contended database.
- **Triage:** Before 1.0, wave C (see [triage.md](../triage.md)).

## R07-7 Settings writes are read, modify, write with no shared lock, so two writers can undo each other

- **Severity:** S3
- **Class:** other
- **Confidence:** low
- **Where:** `internal/api/settings.go:216` to `:513`; `metrics.go:96`–`100`; `maintenance.go:75`–`100`; `mediatools.go:207`–`209`; `customcert.go:99`; `publiccert.go:135`; the three webhook handlers in `webhooks.go`
- **Failure:** Each of these calls `settings.Get()`, changes its own fields on that copy, and `Set`s the whole struct. Only the webhook handlers hold a lock (`webhookMu`), and nothing else takes it. `putSettings` also does I/O between its `Get` and `Set`: `UserByID` for the DLNA account and `checkOptimizedDir`. So a webhook created during a settings save can disappear, a metrics token created then can be silently replaced by the old hash (the scraper's new token is refused), and the media-tools install recording `ffmpeg_dir` as it finishes can be reverted by a save already in flight. Two toggles saved in quick succession race the same way.
- **Evidence:** `grep -n "settings.Set("` lists ten writers in `internal/api`, and only `webhooks.go` holds a mutex around its Get and Set.
- **Fix sketch:** Give `config.SettingsStore` an `Update(func(*Settings) error)` that runs the change under its own lock, and move every writer to it. `webhookMu` can then be removed.
- **Verdict:** PLAUSIBLE. The windows are short and need two writers at once, so I did not reproduce it. The lost write is certain if they do overlap.
- **Triage:** After 1.0: needs two writers within milliseconds; the fix is a refactor of every writer.

## R07-8 The audit record of a restore is written into the database the restore replaces

- **Severity:** S3
- **Class:** other
- **Confidence:** high
- **Where:** `internal/api/backups.go:373` (the `backup.restore` audit), `internal/serverapp/main.go:354` (where the restore is applied and only logged)
- **Failure:** `restoreBackup` writes "Restored the backup X" to `audit_event` in the current database, stages the restore, and restarts. On start, the staged backup replaces that database. The record is then only in the safety backup, and the audit log the administrator reads afterwards has no entry saying a restore happened, who asked for it, or which safety backup holds the previous state. `serverapp` records the apply in `lancastd.log` only. Who may call the route is fine: `adminOnly`, which refuses API keys. What it overwrites is the whole database, after taking a safety backup first (R04-3 covers what comes back with it).
- **Evidence:** `grep -rn "AppendAudit\|backup.restore" internal/serverapp internal/backup internal/store` finds no audit write on the apply path.
- **Fix sketch:** After `serverapp` applies a staged restore, write the `backup.restore` audit event into the restored database, using `Pending.RequestedBy`, the name and the safety backup.
- **Verdict:** CONFIRMED by reading the call path. `backups.go` is R03's file and the fix lands in R10's `serverapp`. It is recorded here because the brief asks R07 about the restore route.
- **Triage:** Before 1.0, wave C (see [triage.md](../triage.md)).

## R07-9 A problem report that fails to send writes the developer's webhook URL, with its token, to the server log

- **Severity:** S3
- **Class:** C17
- **Confidence:** high
- **Where:** `internal/api/reportissue.go:534`–`535`; `internal/report/report.go:167`–`169`
- **Failure:** When `client.Do` fails (offline, DNS, timeout, which is exactly what the "check the connection" message expects), the error is a `*url.Error`. Its text is `Post "https://…/webhooks/<id>/<token>": …`, and `sendReport` logs it at WARN. The URL then sits in `lancastd.log`, which administrators read through `GET /api/logs`, attach to later reports, and paste into issues. The impact is limited because the same URL is compiled into the public binary, but the checklist rule is that no secret goes into a log.
- **Evidence:** `report.Send` wraps the error with `%w` and does not redact it. The handler logs `"error", err`.
- **Fix sketch:** In `report.Send`, unwrap a `*url.Error` and return only its `Err`, or replace its `URL` with the host, before wrapping.
- **Verdict:** CONFIRMED by reading. The standard library's `url.Error.Error()` always includes the URL.
- **Triage:** Before 1.0, wave D (see [triage.md](../triage.md)).

## R07-10 Starting a face pass while another runs answers "started" and does nothing

- **Severity:** S3
- **Class:** other
- **Confidence:** high
- **Where:** `internal/api/faces.go:77`–`85`; `internal/faces/worker.go:155`–`160`
- **Failure:** `POST /api/libraries/{id}/faces` starts `facesW.Run` in a goroutine and answers `202 {"started": true}` straight away. If a pass is already running, for another library or the same one, `Run` returns "a face pass is already running", and that error goes only to the log at ERROR. The administrator is told the second library is being grouped when it is not, and the log reports a fault that is not one. `startSemanticPass` (`semantic.go:94`) works the same way.
- **Evidence:** the goroutine's error is only logged, and the 202 is written regardless.
- **Fix sketch:** Check `facesW.Stats().Running` (and the embedder's) before starting, and answer `409 already_running` when a pass is running.
- **Verdict:** CONFIRMED by reading both sides.
- **Triage:** Before 1.0, wave C (see [triage.md](../triage.md)).

## Checked and clean

- **Live TV switch.** All 15 live routes (`server.go:901`–`915`) go through `s.liveTV`, which answers `409 live_tv_off` while the setting is off. The five channel-source routes are wrapped *outside* `adminOnly`, so a member also gets 409 and not 403. The scheduled guide refresh, including `POST /api/tasks/guide/run`, goes through `RefreshGuides`, which returns before any fetch while it is off. No other route in `internal/api` reads channels or guides. The setting cannot be changed through the API (`live_tv` is only in `config.json`), as `docs/openapi.json` says.
- **Admin-only routes.** Every route in the slice that changes server state or reveals operator data is wrapped in `adminOnly`: settings and reset, cache clear, certificates, webhooks, metrics token, tasks, transcodes list and stop, logs, crashes, audit, update (all four), media tools, retro database, web-core install, face and semantic model installs, face passes, cluster naming and rejection, sensitive marking, collection poster, item edit, unlock, match and refresh, library refresh, reparse and preview, collisions, cover-art and probe refresh, plugins (all eight), all sessions and signing out any session, storage. R07-1 and R07-5 are the exceptions found.
- **SSRF.** Webhook URLs (`webhook.ValidateURL`) take any http(s) host, loopback and LAN included, with redirects off. That is intended: administrators only, and ADR 0097's receivers are household services. The report webhook is fixed at build time or by environment, never a request field. Plugins are uploaded bundles verified against the project key, with no URL fetch. Media tools, face models, semantic models and the retro database download only pinned URLs. Subtitle downloads go to the link OpenSubtitles returns, so a hostile or compromised OpenSubtitles could point the server anywhere. `subtitle.Fetch` is R09's, which notes the key goes only to `*.opensubtitles.com`, but the link host itself is not restricted. Recorded here, not as an entry, because it needs the provider to be compromised. Metadata candidate searches go only to registered providers. Channel sources refuse this server's own origin (`checkSourceURL`), and live TV is off.
- **C17, secrets in responses.** `GET /api/settings` reports `configured`/`source` for TMDB, OpenSubtitles and OMDb and never the keys, gives the OpenSubtitles username and not its password, and gives `metrics_token.{configured, created_at}` and not the hash. Webhook views leave out the secret, which only `POST` returns. Plugin views list `secrets_configured` names, never values. The audit for `settings.update` names changed fields, never values. The metrics token is compared with `subtle.ConstantTimeCompare` on its hash, is accepted only on `GET /api/metrics`, and is shown once. `GET /api/logs` is admin-only. The one log leak found is R07-9.
- **Event stream (ADR 0079).** Events carry topic names only, never payloads. `presence`, `players` and `remote` go through `PublishTo(user, …)` and so reach only that account's windows. Every other topic is a "go and ask again" whose answer comes from routes that apply their own access rules. Guests cannot open the stream (it is not on the guest gate list). The handler unsubscribes on return, ends on request cancel, on hub close or on a failed heartbeat write, and its per-iteration timeout context is cancelled every time. Another account's activity cannot leak through it.
- **Restore.** `POST /api/backups/{name}/restore` is `adminOnly`, refuses API keys, resolves the name inside the backups folder, refuses a backup from a newer schema or one that is not a database, refuses while a restore is already staged, takes a safety backup first (507 if there is no space), and then stages and restarts. What it overwrites is the whole database, and the gap is R07-8.
- **C3.** Every decoder in the slice sits behind the 1 MiB `limitBodies` cap. The larger routes (plugins 32 MiB, report ~32 MiB, picture 10 MiB) are listed in `largeBodies` and read with their own `MaxBytesReader`. MilkDrop uploads are capped at 512 KiB. Log tails are capped at 2000 lines. `listAudit` takes a caller `limit` with no upper bound, but it is admin-only.
- **C15.** Each background job (`storage`, face, semantic, retro and media-tools installs, face and semantic passes, update download, `refetchByID`, `playbackChanged`) has a cancel or timeout and clears its running flag on exit. `storageOverview` coalesces through `measuring`. `faceJob`/`retroJob`/`toolsJob` refuse a second start.

- **C8.** No `*sql.DB` in the slice. The one multi-statement write is R07-6.
- **C1.** Every path in the slice from a row goes through `containedPath`/`containedEntry`: `itemFilePath`, `subtitleFilePath`, and `deleteSubtitle`'s removal. Paths from configuration (data directory, tools, faces, retrodb, plugins) are joined from fixed names. R07-1 is the one place a request field reaches a path.
- **Not applicable:** C5 (no federation routes in the slice), C6/C12/C13/C18 (no client code), C9 (the slice starts no ffmpeg itself; `alignaudio` uses the request's context for its probe), C10, C11, C14 (candidate queries use `media.Parse` and `meta.SortTitleOf`, no new normaliser), C16 (the ignored errors are best-effort audit and log writes).
