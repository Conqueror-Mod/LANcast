## R14-1 Seeking a converted film writes the old clock on top of the new offset, and can mark it watched

- **Severity:** S1
- **Class:** other (progress and resume reporting)
- **Confidence:** high
- **Where:** `web/src/playback/PlaybackProvider.tsx:2400`–`2426` (`seekWith`), with `saveProgress` at `:1038`–`:1043`
- **Failure:** On a converted source, `seekWith` sets `offset.current = t` and calls `setCurrent(0)`, then calls `saveProgress(true)` in the same tick. `saveProgress` is the closure from the last render, so its `current` is still the element's old clock, and it writes `offset.current + current`, which is the *new* offset plus the *old* clock. On a 2 h film converted from the start, an hour in, pressing back 100 s writes 3500 + 3600 = 7100 s. That is past 0.92 of the runtime, so the write says `watched: true`. `SaveProgress` (`internal/store/store.go:3540`) treats the false→true edge as a viewing: it bumps `watch_count`, logs a viewing, and settles the watchlist, which takes the film *off the watchlist*. The next throttled write, five seconds later, puts the position back and sets `watched` to false, but the viewing, the count and the watchlist removal stay. A forward seek does the same whenever new target + old clock passes 92%: from 10 min in, seeking to 1h40 writes 1h50. Without the 92% crossing, the bad position stands until the next write, and stopping in that window keeps it.
- **Evidence:** Proving test (scratch, not committed):
  ```tsx
  await act(async () => pb.play(201, [201]));            // decision: transcode, duration 7200 s
  video.dispatchEvent(new Event("loadedmetadata"));
  reportPosition(3600);                                   // an hour in, offset 0
  writes = [];
  await act(async () => pb.seekTo(3500));                 // back 100 s
  expect(writes.at(-1)?.positionMS).toBe(3_500_000);
  ```
  Output: `writes after seek: [{"id":"201","positionMS":7100000,"watched":true}]`, then `AssertionError: expected 7100000 to be 3500000`.
- **Fix sketch:** In the transcode branch, save the target itself rather than going through `saveProgress`: either pass the position explicitly (`saveProgress(true, t)`) or have `saveProgress` read the clock from a ref that `seekWith` sets to 0 before saving. The direct branch has the same shape (it writes the old `current`), but there it is only the place you left, so nothing is corrupted. Commit the test above with the fix.
- **Verdict:** CONFIRMED by test. Tried to disprove it via the guards: `clockItem` and `livePos.id` both equal the item during an ordinary seek, so neither stops the write; `pos > 0` holds; the 5 s throttle is skipped because the save is forced. The store side was read to confirm the edge counts as a viewing and settles the watchlist.
- **Triage:** Fixed and merged in #1120.

## R14-2 Any failed direct play, a network drop included, withdraws the file's codec claims for two weeks

- **Severity:** S2
- **Class:** other (playback state machine)
- **Confidence:** high
- **Where:** `web/src/playback/PlaybackProvider.tsx:3282`–`3286` (the `error` handler) → `retryWithoutClaims` at `:2175`–`:2188`; `capabilities.ts:136` (`DENIAL_TTL_MS` = 14 days)
- **Failure:** The HLS branch of the error handler is deliberately narrow (only `MEDIA_ERR_SRC_NOT_SUPPORTED` counts, and the verdict waits on a probe). The direct branch is not narrow at all: every `error` on a direct source that is not converted calls `retryWithoutClaims`, which `deny`s every claim the file's streams needed, for 14 days, without looking at `media.error.code`. Three common cases end up there:
  1. A network failure mid-film (`MEDIA_ERR_NETWORK`): the server restarts for an update, the laptop leaves Wi-Fi, or the session expires and the stream answers 401. An HEVC film playing directly in a browser that decodes HEVC withdraws `hevc` (and `hevc10`, `ac3`, … whatever the file used), and every HEVC title on that device is re-encoded for a fortnight. That is the incident the comment at `:2152` describes, reached through a different door.
  2. R03-2's case. The answer said `version: "optimized"`, `/api/stream/{id}?version=optimized` answers 503 because the copy is missing, and the element errors. The player *does* recover (it converts from the original), which answers R03-2's open question, but it withdraws the claims of the *original's* streams (say HEVC + TrueHD), though what failed was a missing H.264 copy. It also tells the viewer "That file would not play directly".
  3. A deck track that errors for any reason, through R14-3.
- **Evidence:** `error: (media) => { … if (transcoding.current) transcodeFailed(); else retryWithoutClaims(); }`. Nothing between the HLS branch and these two calls reads `media.error`. `retryWithoutClaims` → `deny(c)` for each `capabilitiesNeededBy(item.streams, item.container)` claim → `DENIAL_TTL_MS = 14 * 24 * 60 * 60 * 1000`.
- **Fix sketch:** Withdraw claims only on `MEDIA_ERR_DECODE` and `MEDIA_ERR_SRC_NOT_SUPPORTED`. On `MEDIA_ERR_NETWORK`, retry the same direct source at `livePos` (or convert without denying anything). For an optimized-copy source, never deny: drop the id from `optimizedCopies` and re-ask `/playback`.
- **Verdict:** CONFIRMED by reading. Tried to disprove it: `MEDIA_ERR_ABORTED` does not raise `error`, but `MEDIA_ERR_NETWORK` does, after data has started arriving, and nothing upstream filters it. The denial can be undone by hand (`clearDenials`, under Settings), but nothing tells the viewer it happened.
- **Triage:** Fixed and merged in #1120.

## R14-3 A music track that fails direct play is converted on the video element while every control stays on the deck

- **Severity:** S2
- **Class:** other (playback state machine)
- **Confidence:** high
- **Where:** `web/src/playback/PlaybackProvider.tsx:2198`–`2223` (`retryWithoutClaims`), with `media()` at `:677`
- **Failure:** A directly played track plays through the music deck (`deckRef.current = true`). When the deck's active element raises `error`, the deck forwards it, the provider sees a direct source failing, and `retryWithoutClaims` loads the conversion into `videoRef.current`. It does not clear `deckRef`. `media()` still returns the deck, so Pause, Play, seek, volume and mute all act on the dead deck while the video element plays the track. `stop()` and the source effect's cleanup pause the deck too, so pressing Stop or moving to the next track leaves the converted track sounding underneath, with nothing that can reach it. `fallBackFromPoorDecode` has the same shape but is guarded by `transcoding`/`videoRef`, and it only runs for video.
- **Evidence:** Proving test (scratch, not committed): `Audio` is stubbed to record the deck's elements, a `flac` track with a direct decision is played, and `error` is dispatched on the deck's active element.
  ```
  deck src: /api/stream/301
  video src after error: /api/stream/301/transcode
  pause went to: ["deck"]
  AssertionError: expected [ 'deck' ] to include 'video'
  ```
- **Fix sketch:** When the failing source is the deck, release it (`queue(null)`, remove `src`, `load()`), set `deckRef.current = false` and `setMusicPath("element")` before loading the element, the same switch the source effect makes at `:2086`–`:2096`. Better still, re-run the source effect with a "convert" override rather than keeping a second copy of source assignment.
- **Verdict:** CONFIRMED by test.
- **Triage:** Fixed and merged in #1120.

## R14-4 A local Watch Together follower on a converted stream re-seeks on every poll

- **Severity:** S2
- **Class:** other (Watch Together)
- **Confidence:** low
- **Where:** `web/src/playback/TogetherProvider.tsx:81`–`95`, with `together.ts:84` (`shouldResync`) and `together.ts:329` (`followerShouldSeek`)
- **Failure:** The follower effect runs on every poll (a new `session` object every 2 s) and seeks whenever `|displayTime − expected| > 1.5 s`. On a converted stream, a seek restarts the conversion, and while it starts `displayTime` stays pinned at the seek target (`offset = t`, `current = 0`), while the room moves on 2 s per poll. If the first frame takes longer than about 1.5 s, the next poll finds the follower behind and seeks again, which throws the conversion away. `together.ts:290`–`322` documents exactly this loop between two servers ("restarted at 94 s, 104 s and 114 s, each thrown away") and fixes it with `followerShouldSeek`, `followerSeekTarget` and `followerShouldCorrect`, but only `screens/PeerPlayer.tsx` uses them. The local room still uses the bare 1.5 s rule. A follower in a browser tab watching an HEVC film the host plays natively is the ordinary way into it.
- **Evidence:** `grep followerShouldSeek` → used only in `screens/PeerPlayer.tsx:593`; `TogetherProvider.tsx:87` uses `shouldResync(pb.displayTime * 1000, target)` with no settle time and no converting tolerance.
- **Fix sketch:** Have `TogetherProvider` apply the same rules as `PeerPlayer`: settle after a seek, wait for `playing` since the last seek, use the wider tolerance and a lead target while `transcoding` (which would need exposing from the provider).
- **Verdict:** PLAUSIBLE. The loop needs a conversion slower than about 1.5 s to its first frame. The server can write a re-encode's playlist up front, so a local video encode may often beat that, while a copied-video/encoded-audio film (minutes, per `waitNote`) certainly does not. Not driven live (no server may be started in this review).
- **Triage:** Fixed and merged in #1137.

## R14-5 Turning shuffle on drops a playlist's other copies of the playing track

- **Severity:** S3
- **Class:** other (queue: positions versus ids)
- **Confidence:** high
- **Where:** `web/src/playback/queueOrder.ts` `shuffledStartingWith` (`queue.filter((id) => id !== current)`)
- **Failure:** A playlist may hold the same track twice (ADR 0030; CLAUDE.md: "anything that keys a playlist on item id silently shortens it"). `shuffledStartingWith` removes *every* entry equal to the playing id and puts one back at the front, so a playlist `[5, 7, 5, 9]` shuffled while 5 plays becomes `[5, 7, 9]`. The second play of 5 is gone, and the queue count on the panel is one short.
- **Evidence:** Proving test: `shuffledStartingWith([5, 7, 5, 9], 5)` → `shuffled: [5,7,9]`, `expected 3 to be 4`. `queueOrder.test.ts` covers only queues without duplicates (`seq(n)`).
- **Fix sketch:** Remove one occurrence: the one at the playing position, which needs `pos` passed in, or the first if no position is known. Add the duplicate case to `queueOrder.test.ts`.
- **Verdict:** CONFIRMED by test.
- **Triage:** Before 1.0, wave F (see [triage.md](../triage.md)).

## R14-6 One failed poll ends a Watch Together room for this window

- **Severity:** S3
- **Class:** other (Watch Together)
- **Confidence:** high
- **Where:** `web/src/playback/together.ts` `useTogether`, the `tick` catch
- **Failure:** Any error from `GET /api/together/{id}`, whether a Wi-Fi blip, a 500, a server busy for a moment or the 2 s poll racing a restart, sets "That session has ended." and calls `stop()`. For a follower, that drops them out of a room that is still running. For a host, it stops their reports, so the room goes stale for everyone and expires. Only a 404 means the room has ended.
- **Evidence:** `catch { if (!cancelled) { setError("That session has ended."); stop(); } }`. Compare `usePeerRoom` in the same file, which ends only on `ApiFailure` status 404.
- **Fix sketch:** End on 404 (or 403) only, and keep polling through other failures, perhaps with a "reconnecting" note after a few in a row.
- **Verdict:** CONFIRMED by reading.
- **Triage:** Before 1.0, wave F (see [triage.md](../triage.md)).

## R14-7 The last progress write on closing a tab is sent without `keepalive`

- **Severity:** S3
- **Class:** other (progress on unload)
- **Confidence:** high
- **Where:** `web/src/playback/PlaybackProvider.tsx:1143`–`1150` (`pagehide` → `saveProgress(true)` → `apiSend`)
- **Failure:** On `pagehide`, the provider forces a save through `apiSend`, which is a plain `fetch` (no `keepalive` in `api/client.ts`). Browsers cancel ordinary requests from a page being unloaded, so closing a browser tab drops the final write, and resume comes back up to five seconds early, or at the last throttled write. `BookPlayer.tsx:313` already does this right with `fetch(…, { keepalive: true })` for the same reason.
- **Evidence:** `grep keepalive web/src/api/client.ts` → nothing; `BookPlayer.tsx:315` `keepalive: true`.
- **Fix sketch:** Send the `pagehide` write with `keepalive: true`, as BookPlayer does.
- **Verdict:** CONFIRMED by reading. The loss is bounded by the 5 s throttle, which is why this is S3. In the desktop window, ✕ hides rather than unloads and runs `stop()` while the page lives, so this is a browser-tab fault.
- **Triage:** Before 1.0, wave F (see [triage.md](../triage.md)).

## R14-8 Stopping a native film while it is still opening can leave it playing in mpv with no page owner

- **Severity:** S3
- **Class:** C15
- **Confidence:** low
- **Where:** `web/src/playback/mpvBackend.ts` `load()` (the async block) and `removeAttribute`
- **Failure:** `load()` checks its generation once, after the stream ticket arrives. It then calls `holdNativeVideo`, awaits three `sendTheater` commands, and awaits `lancastMpvOpen`, with no further check before the open. If Stop, or a switch to music, lands in that window, `removeAttribute` bumps the generation, releases the hold and calls `lancastMpvStop`. Then the pending `lancastMpvOpen` completes and opens the film anyway. The layout is `hidden` (`nativeOn` is false), so the film is heard and not seen, and nothing on the page will stop it until the next native film or a reload (`PlaybackProvider.tsx:522`).
- **Evidence:** In the code, the only `gen !== this.generation` check before the open is the one right after the ticket. Whether the host serialises `stop` after an in-flight `open` was not checked (`internal/mpv` belongs to R11).
- **Fix sketch:** Re-check the generation after `sendTheater` and immediately after `lancastMpvOpen` resolves. If it moved, call `lancastMpvStop`.
- **Verdict:** PLAUSIBLE. The window is a few IPC round trips, and the outcome depends on the host's ordering.
- **Triage:** After 1.0: A window of a few IPC round trips.

## R14-9 Repeat one on a converted film "seeks" a stream that cannot seek

- **Severity:** S3
- **Class:** other (playback state machine)
- **Confidence:** low
- **Where:** `web/src/playback/PlaybackProvider.tsx:3381`–`3387`
- **Failure:** On `ended` with repeat one, the handler sets `media.currentTime = 0` and plays, and skips the reload on purpose. On a converted source, the element's zero is the session's `t=` offset and the progressive fMP4 is not range-served, so the replay starts from where that conversion began (a resumed film replays from the resume point), or the element cannot seek back at all and sits ended. `offset.current` is left alone, so the clock carries on reading the old base. The direct and native paths are fine.
- **Evidence:** Code only. Not proven in jsdom, which does not model a non-seekable stream.
- **Fix sketch:** When `transcoding.current`, repeat with `seekTo(0)`, which re-requests the conversion from the start, instead of setting `currentTime`.
- **Verdict:** PLAUSIBLE.
- **Triage:** After 1.0: rare: repeat-one on a film.
