## R05-1 The profile page shows titles from a library kept from the account

- **Severity:** S2
- **Class:** other (ADR 0084, library limits)
- **Confidence:** high
- **Where:** `internal/store/history.go:121` (`History`), `:167` (`ProfileStatistics`), `:287` (`MostPlayed`); likewise `internal/store/watchlist.go:59` (`Watchlist`)
- **Failure:** an administrator hides a library from a member (ADR 0084) after that member has played something in it. The member's profile page (`GET /api/profile`, `api/profile.go:81–117`) still lists those titles, with their posters, in History and Most played, and still counts them in the totals. ADR 0084 §6 says the history *"is left out of what they are shown while the library is hidden, so their history does not reveal what the library holds"*. `viewing.go`, `rating.go` and `yearreview.go` apply `hiddenClause` to do this. The three profile-page queries came later (Profile 2.0) and never picked it up. `Watchlist` has the same gap, and also no content-rating ceiling: a title added before the library was hidden, or before the ceiling was lowered, stays on the list (not covered by a test).
- **Evidence:** proving test (run in the worktree, not committed). A member finishes a film three times, then its library is hidden:
  ```
  === RUN   TestR05ProfileHistoryIgnoresHiddenLibrary
      zz_r05_prove_test.go:53: history=1 mostPlayed=1 started=1
      zz_r05_prove_test.go:55: hidden library still on the profile: history 1, most played 1, started 1
  --- FAIL: TestR05ProfileHistoryIgnoresHiddenLibrary (0.13s)
  ```
  Body: `CreateUser(member)`, `CreateLibrary`, `UpsertItem`, `SaveProgress` finished ×3, `SetHiddenLibraries(member, [lib])`, then `History(GroupAll)`, `MostPlayed`, `ProfileStatistics`, each expected empty or zero.
- **Fix sketch:** add `hiddenClause(ctx, userID, "ps.item_id")` to the three queries, as `yearreview.go` does. Put the same clause (and the ceiling, through `accessFor().predicate()`) into `Watchlist`. Extend ADR 0084's stage 2 test to cover `/api/profile`.
- **Verdict:** CONFIRMED. The handler passes the rows straight through: `attachArtworkTo` adds posters and filters nothing, and `History` does not call `GetItem`. Administrators are exempt from hidden libraries, so the test uses a member. Not a duplicate of a wave 1 entry: R13-2 is about "On this day" invalidation, not about access.
- **Triage:**

## R05-2 A book's sort title is rewritten from its folder under a locked title

- **Severity:** S2
- **Class:** C4
- **Confidence:** high
- **Where:** `internal/store/book.go:47` (`SetBookDetails`), called by `internal/scan/books.go:128` on every book pass
- **Failure:** a person renames an audiobook ("Zebra Tales" → "Aardvark Stories"). The edit handler writes `title` and `sort_title`, then locks `title` only (`sort_title` is not an editable field, `api/meta.go`). On the next book pass, `SetBookDetails` skips `title` because it is locked, but sets `sort_title` back to the folder's name, because nothing locks that field separately. The book then shows its new name and sorts as its old one, at Z rather than A. Everywhere else in the store, `sort_title` follows the title's lock: `UpsertItem`'s `keepIdentity("sort_title", "sort_title", "title")`, `ApplyTrackTags` (`add("sort_title", …, locked["title"])`), `ApplyGuess`, and `SetBookPart` in the same file.
- **Evidence:** proving test (not committed):
  ```
  === RUN   TestR05BookSortTitleIgnoresTitleLock
      zz_r05_prove_test.go:86: title="Aardvark Stories" sort_title="zebra tales"
      zz_r05_prove_test.go:88: sort_title = "zebra tales" under a locked title "Aardvark Stories"
  --- FAIL: TestR05BookSortTitleIgnoresTitleLock (0.13s)
  ```
  The existing guard, `scan/books_test.go` ("A locked title stays, whatever the folders say"), asserts only `Title`, so it passes.
- **Fix sketch:** in `SetBookDetails`, skip `sort_title` when `title` is locked, as `SetBookPart` does. Add the sort-title assertion to the books test.
- **Verdict:** CONFIRMED. The `differs` guard does not save it: `sort_title IS NOT ?` is true after the edit, so the update runs on the very next pass and then on none after. The charter's S1 is "a locked field is overwritten". `sort_title` is not itself locked, and the visible damage is sort order, so this is S2. Triage may raise it.
- **Triage:**

## R05-3 Removing a plugin can leave its stored credentials behind for whatever installs under that name next

- **Severity:** S3
- **Class:** C8
- **Confidence:** high
- **Where:** `internal/store/plugin.go:122` (`RemovePlugin`)
- **Failure:** `RemovePlugin` deletes the `installed_plugin` row and then, as a separate statement outside a transaction, the `plugin_secret` rows. `plugin_secret` has no foreign key (revision 44). If the second statement fails (for example `SQLITE_BUSY` after the 5 s timeout, or a disk error), the plugin is gone and its keys remain. Retrying the remove returns `ErrNotFound`, because the plugin row no longer exists, so nothing ever clears them. The code's own comment names the result: a credential *"waiting to be handed to whatever installs under that name next"*.
- **Evidence:** the code at `plugin.go:122–135`. There is no test; it needs an injected failure on the second statement.
- **Fix sketch:** run both deletes in one transaction, or delete the secrets first.
- **Verdict:** PLAUSIBLE. The mechanism is certain. The trigger needs a failure between two statements a few microseconds apart, which is rare. It is kept because the cost (a credential handed to a different plugin) is a C17-shaped outcome.
- **Triage:**

## Checked and clean

- **C8, `*sql.DB` leaking:** no exported function in the slice returns `*sql.DB`, `*sql.Tx` or `*sql.Conn` (R04's check covered the package, and nothing in this slice changes that).
- **C8, multi-statement writes:** every write in the slice made of two or more dependent statements runs in a transaction (`SaveRatings`, `ReplaceGenres`, `replaceTagGenres`, `ReplaceCredits`, `PutArtwork`, `SetPlaylistEntries`, `AppendPlaylistEntries` with its `MAX(ord)` read inside, `RemovePlaylistEntry`, `SetBookNarrators`, `SaveProbe`, `SetCollectionPoster`, `ClearCollectionPoster`, `SetHomePrefs`, `SetReadingPrefs`, the history reset). The sweep's other hits are either one statement per branch (`NameCluster`, `SetSeriesDirection`, `RefreshSensitivity`, `SetFavourite`, `ClearMetadataStamp`) or independent and idempotent steps (`ReconcileMissingContainers` loops to a fixed point; `SetPhotoMeta`'s hash upsert). The exception is R05-3.
- **C4, locked fields:** `ApplyGuess` skips each locked field separately, and `sort_title` goes with `title`. `ApplyAlbumMatch` and `ApplyArtistMatch` skip a locked match unless the person confirmed it, fill year and genres only when they are empty, and respect the `year` and `genres` locks. `MarkMusicUnmatched` and `RequeueArtistOf` skip locked rows. `SetEdition` honours an `edition` lock. `SetBookPart` and `SetBookNarrators` (the `credits` lock) are clean. `SaveProbe` writes `duration_ms`, which is a lockable name, but the edit endpoint cannot set that lock, so no person can hold it. The same applies to `genres`, `credits` and `artwork` on ordinary items. The one `artwork` lock a person can set, on a collection's poster, is respected: the enricher stores collection art only when it first creates the collection. `UpdateItemMetadata` itself does not check locks. Its callers do (the enricher merges with the locked set, and the edit handler is the person), and `PendingEnrichment` excludes `match_state = 'locked'`. Outside R05-2, no write in the slice overwrites a lock.
- **C4, playlists:** `playlist_entry` is keyed `(playlist_id, ord)`. Reads order by `ord` and never deduplicate. Removal is by position, with an in-transaction resequence. Appends read the next position inside their transaction. The API locks `members` *before* every membership write, and the scanner skips a playlist with that lock. `EnsurePlaylist` is `ON CONFLICT DO NOTHING`, so a re-import never renames an edited playlist. Nothing in the store keys a playlist on item id.
- **Wrong-user rows:** every query on `playback_state`, `viewing`, `user_rating`, `user_watchlist` and `user_favourite` in the slice is scoped by `user_id`, including the correlated sub-queries in next-episode, after-film suggestions, unwatched counts and "to rate". `peer_progress` having no user is already recorded by R04 (Seen in passing).
- **Library limits:** `resolveCeiling` fails closed for a friend and, since R04-4's fix, for an account read error. Hidden libraries are applied there and in `viewing`, `rating` and `yearreview` through `hiddenClause`. The gaps are R05-1.
- **C11, dates:** every calendar computation in the slice is done by SQLite with `'unixepoch', 'localtime'`: Year in Review (`localYear`/`localMonth`), "On this day" for photos and for finished titles, and the photo timeline. Photo `taken_at` is parsed `InLocation(time.Local)` (`photo/exif.go:239`), so the round trip is consistent. Nothing builds a user-facing date from UTC.
- **C16 and SQL built from strings:** every concatenated SQL fragment in the slice is a package constant (`itemCols`, `unmatchableKinds`, `effectiveRating`, `showOf`, …), a column name picked from a fixed list in code (`setLibraryOption`, `SetHomePrefs`, `SetReadingPrefs`, `PictureByHash`), `?` placeholders, or integers formatted from database ids (`hiddenClause`). No caller-supplied string reaches SQL text. The ignored errors are `RowsAffected` reads and the `yearEnds` read above.
- **Indexes:** not assessed. No hot path in the slice was measured, and the charter does not admit "could be faster" without a measurement.
- **C1–C3, C5–C7, C9, C10, C12–C15, C17, C18:** not applicable to the store slice, except C17 as it touches R05-3.
