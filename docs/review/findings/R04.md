## R04-1 A rescan that re-upserts a file overwrites its locked title, year and episode numbers

- **Severity:** S1
- **Class:** C4
- **Confidence:** high
- **Where:** `internal/store/store.go:812` (`UpsertItem`, the `ON CONFLICT(path) DO UPDATE SET` list)
- **Failure:** A person corrects a film's title (which locks `title`), or a provider matches it to "The Matrix". Then either (a) the drive holding it goes offline for one scan and comes back, or (b) the file's mtime or size changes (re-muxed, tags edited, replaced with a better copy at the same path). The scanner skips unchanged files only when the row is not missing and size and mtime match (`scan/scanner.go:928`), so in both cases it calls `UpsertItem`. The upsert unconditionally sets `kind`, `title`, `sort_title`, `year`, `series`, `season`, `episode`, `edition` and `platform` from the filename guess. It does not consult `item_lock`, and it does not clear `metadata_updated_at`, so enrichment never revisits the row. The locked title is gone for good, and an unlocked provider title stays a filename guess until somebody runs Refresh metadata by hand. Remounting a whole drive does this to every file on it at once.
- **Evidence:** A proving test, run in this worktree and failing (not committed):
  ```go
  func TestR04ProbeUpsertOverwritesLockedTitle(t *testing.T) {
  	ctx := context.Background()
  	st := openTestStore(t)
  	root := t.TempDir()
  	lib, _ := st.CreateLibrary(ctx, "Movies", "movie", root)
  	path := filepath.Join(root, "alien.1979.mkv")
  	y := 1979
  	f := ScanFile{LibraryID: lib.ID, Kind: "movie", Path: path, Title: "alien", SortTitle: "alien",
  		Year: &y, Container: "mkv", SizeBytes: 100, MTime: 1}
  	id, _ := st.UpsertItem(ctx, f)
  	st.db.Exec(`UPDATE media_item SET title = 'Alien (Director''s Cut, my edit)' WHERE id = ?`, id)
  	st.LockField(ctx, id, "title")
  	st.MarkMissing(ctx, []int64{id})        // drive unplugged for one scan
  	st.UpsertItem(ctx, f)                    // drive back: byte-identical file re-upserted
  	var title string
  	st.db.QueryRow(`SELECT title FROM media_item WHERE id = ?`, id).Scan(&title)
  	if title != "Alien (Director's Cut, my edit)" {
  		t.Fatalf("locked title overwritten by the re-upsert: now %q", title)
  	}
  }
  ```
  ```
  --- FAIL: TestR04ProbeUpsertOverwritesLockedTitle (0.18s)
      zz_r04_probe_test.go:46: locked title overwritten by the re-upsert: now "alien"
  ```
  No test in `internal/scan` covers a changed or reappearing file with a lock on it. `TestReappearingFileClearsMissing` checks only the `missing` flag.
- **Fix sketch:** In the update branch, keep a column when `item_lock` holds that field for the row (`title = CASE WHEN EXISTS(SELECT 1 FROM item_lock WHERE item_id = media_item.id AND field = 'title') THEN media_item.title ELSE excluded.title END`, and the same for each lockable column). Beyond that, a row that is already matched (`match_state` matched or locked) should keep its identity fields when a file only reappears or changes bytes: "a rescan reconciles files, it does not re-litigate identity". Add the permanent test above, in both the missing→back and the mtime-changed form.
- **Verdict:** CONFIRMED. The proving test fails on 4faabca9. I tried to disprove it by looking for a later step that restores the value. `scan.upsertFile` returns straight from `UpsertItem` (`scanner.go:1582`). `ClearMetadataStamp` is called only on the reinterpreted-kind path (`scanner.go:941`). Enrichment skips locked fields, so it could not restore a locked value even if it ran. Nothing restores it.
- **Triage:**

## R04-2 reset-auth leaves passkeys behind, and the next first admin inherits them

- **Severity:** S1
- **Class:** other (credential revocation)
- **Confidence:** high
- **Where:** `internal/store/user.go:184` (`DeleteAllUsers`); `internal/api/auth.go:599` (first-run setup always uses `store.LocalUserID`)
- **Failure:** `lancast reset-auth` is the recovery path for an operator locked out of their own server, which includes the case where somebody else has taken the admin account. `DeleteAllUsers` deletes `session` and `user` and nothing else. `passkey` has no foreign key to `user` (revision 70), so every passkey survives. The first admin created afterwards is always given the id `"local"`, which is the same id the previous first admin had. `PasskeyByCredentialID` joins `user` on that id, so every passkey registered to the old owner, including one an intruder added, signs in as the new administrator. The same applies to the old owner's `retro_account` (a sealed RetroAchievements key), `library_hidden`, `home_shelf`, `user_picture` and so on, though those are account data rather than credentials. API keys, presence grants, tags and favourites do cascade (they have `REFERENCES user ON DELETE CASCADE`), which is why only the non-FK tables show the problem.
- **Evidence:** A proving test, run and failing (not committed):
  ```go
  func TestR04ProbeResetAuthLeavesPasskeys(t *testing.T) {
  	ctx := context.Background()
  	st := openTestStore(t)
  	st.CreateUser(ctx, LocalUserID, "owner", "h1", RoleAdmin)
  	st.AddPasskey(ctx, Passkey{UserID: LocalUserID, CredentialID: []byte("cred-old"),
  		PublicKey: []byte("pk"), Algorithm: -7, Name: "someone's phone", RPID: "example.test"})
  	st.DeleteAllUsers(ctx)
  	st.CreateUser(ctx, LocalUserID, "newadmin", "h2", RoleAdmin) // first-run setup
  	if p, err := st.PasskeyByCredentialID(ctx, []byte("cred-old")); err == nil {
  		t.Fatalf("the pre-reset passkey %q resolves to account %q after reset-auth", p.Name, p.UserID)
  	}
  }
  ```
  ```
  --- FAIL: TestR04ProbeResetAuthLeavesPasskeys (0.17s)
      zz_r04_probe_test.go:71: the pre-reset passkey "someone's phone" resolves to account "local" after reset-auth
  ```
- **Fix sketch:** In the same transaction, have `DeleteAllUsers` delete every credential table that has no FK: at least `passkey`, plus `retro_account` and `retro_unlock_queue`. The `playback_state`/`viewing` carve-out that ADR 0058 and the function comment justify stays. Add the test above to `user_test.go`.
- **Verdict:** CONFIRMED. To disprove it I checked whether the passkey sign-in adds any check the store does not. `rp_id` must match the current public name, and on the same server it does, so that is no barrier. The new admin would see the old passkey in their own passkey list and could delete it, but only if they look, and the list gives no hint that it predates the reset. `TestDeleteAllUsersKeepsWatchHistory` shows the history carve-out is deliberate. Nothing shows that keeping passkeys is.
- **Triage:**

## R04-3 Restoring a backup brings revoked API keys and passkeys back to life

- **Severity:** S2
- **Class:** other (credential revocation)
- **Confidence:** low (it may be accepted as inherent to restore)
- **Where:** `internal/store/backup.go:159` (`clearSnapshotSessions`), `internal/store/restore.go:135`
- **Failure:** An administrator revokes an API key after a suspected leak (ADR 0061: revocation is "a person pressing a button"), or deletes a passkey for a lost phone. Later they restore a backup taken before that, such as one of the automatic pre-update backups after a bad update. The restored database holds the old `api_key` and `passkey` rows, so the leaked key and the lost phone work again. ADR 0058 clears sessions from every snapshot for exactly this reason ("Sessions are server-side precisely so they can be revoked; a restore handing them back undoes that"), but the two other revocable credentials are not treated the same way. Used TOTP recovery codes also come back.
- **Evidence:** `clearSnapshotSessions` runs `DELETE FROM session` only; `RestoreSnapshot` calls only `DeleteAllSessions`. `api_key` (revision 42) and `passkey` (revision 70) ride along in `VACUUM INTO`.
- **Fix sketch:** Decide it explicitly. Either clear `api_key` and `passkey` at snapshot time as sessions are (people re-issue keys and re-register passkeys after a restore), or keep them and have the restore result list them ("3 API keys and 2 passkeys from <date> are active again") so the operator can revoke them. Either answer belongs in ADR 0058's amendment.
- **Verdict:** PLAUSIBLE. The mechanism is certain from the code. Whether it is a fault depends on intent: a restore also reverts password hashes, which is clearly inherent, and these credentials could be argued to belong with them. The ADR's own reasoning about sessions argues the other way.
- **Triage:**

## R04-4 Library limits fail open when the account lookup errors

- **Severity:** S2
- **Class:** C16
- **Confidence:** low (the trigger is a transient read error; not reproduced)
- **Where:** `internal/store/access.go:40` (`HiddenLibraries`), `internal/store/access.go:181` (`accessFor`)
- **Failure:** `HiddenLibraries` treats *any* error from `SELECT role FROM user WHERE id = ?` as "no account, no limit" and returns nil. `accessFor` does the same for the `max_content_rating` read and returns an empty `accountAccess`. The comment means the `sql.ErrNoRows` case (unsecured loopback, where there is no account). But a `database is locked`, an I/O error or a cancelled context also lands there, and for that one request a member with hidden libraries or a content ceiling gets the unrestricted listing (`ListItems`, `MayOpenLibrary`, the history and year clauses through `hiddenClause`).
- **Evidence:**
  ```go
  if err := s.db.QueryRowContext(ctx, `SELECT role FROM user WHERE id = ?`, userID).Scan(&role); err != nil {
      // No account row means no limit, for the reason resolveCeiling records.
      return nil, nil
  }
  ```
- **Fix sketch:** Return nil only on `errors.Is(err, sql.ErrNoRows)`, and propagate every other error so the handler answers 500 instead of an unrestricted page. Apply the same change in `accessFor`.
- **Verdict:** PLAUSIBLE. Under WAL a plain read rarely sees `SQLITE_BUSY`, and a cancelled context usually means nobody is reading the answer, so real exposure needs an I/O-level failure. The code fails open on a security boundary, which is the wrong direction, but I could not name an everyday input that triggers it.
- **Triage:**

## R04-5 Two admins deleting each other at once leave the server with no administrator

- **Severity:** S3
- **Class:** C8
- **Confidence:** high
- **Where:** `internal/store/user.go:239` (`DeleteUser`); the check lives only in `internal/api/users.go:116`
- **Failure:** With exactly two admins A and B, A deletes B while B deletes A. Each handler runs `CountAdmins` (2), passes, then calls `DeleteUser`. Both succeed and the server has no admin. The only recovery is `reset-auth` on the host. `SetUserRole` was rewritten to prevent exactly this race (the count and the write share one transaction), and `ErrLastAdmin`'s comment says the rule is "refused at the store rather than trusted to a check in one handler", but `DeleteUser` has no such check.
- **Evidence:** `DeleteUser` runs `DELETE FROM user WHERE id = ?` with no role count. `deleteUser` in `api/users.go` does check-then-act across two store calls.
- **Fix sketch:** Inside `DeleteUser`'s transaction, read the target's role, and if it is admin, count admins and return `ErrLastAdmin` when the count is ≤ 1, as `SetUserRole` does. Map `ErrLastAdmin` to 409 in the handler.
- **Verdict:** CONFIRMED by reading. `_txlock=immediate` serialises the two transactions, but neither one counts, so serialising them does not help.
- **Triage:**

## R04-6 Deleting an account leaves its ratings, reviews and banked totals behind

- **Severity:** S3
- **Class:** other (data retention)
- **Confidence:** high
- **Where:** `internal/store/user.go:239` (`DeleteUser`)
- **Failure:** `DeleteUser` removes the rows of thirteen user-keyed tables by hand, because those tables have no FK to `user`. It misses `user_rating` (revision 21, which holds `score` and free-text `review`) and `profile_totals` (revision 30). A deleted member's written reviews and banked watch totals stay in the database, and in every backup taken afterwards, under an id no account will ever have again. The function comment says "deleting a person means deleting their data".
- **Evidence:** `user_rating.user_id TEXT NOT NULL` and `profile_totals.user_id TEXT PRIMARY KEY`, neither with a FK, and neither appears in `DeleteUser`. The orphans are invisible in the app, since every read is keyed by user id, which is why nobody has noticed.
- **Fix sketch:** Add `DELETE FROM user_rating WHERE user_id = ?` and `DELETE FROM profile_totals WHERE user_id = ?` to the transaction. A test that lists every table with a `user_id` column from `sqlite_master` and fails when `DeleteUser` leaves rows in one would stop the next table from being forgotten.
- **Verdict:** CONFIRMED by reading the schema and the function. To disprove it I looked for cascades: neither table has one, and no trigger exists in `migrate.go`.
- **Triage:**

## R04-7 Switching RetroAchievements accounts can send the old account's queued unlocks under the new one

- **Severity:** S3
- **Class:** C8
- **Confidence:** high
- **Where:** `internal/store/retroaccount.go` (`SetRetroAccount`, and `SetRetroToken`'s two un-transacted statements)
- **Failure:** A LANcast user earns achievements while RetroAchievements is unreachable, and they queue with backoff (`next_at` up to 6 h ahead). Before those come due, the user connects a *different* RetroAchievements account (`PUT /api/me/retroachievements` with a new username), which upserts the row. The `CASE` nulls the old account's token, but `retro_unlock_queue` is left alone. If the user then turns earning on for the new account before the queued rows come due, `sendRetroUnlocks` (`api/raplay.go:224`) adds the *new* account's token to each queued body. Achievements earned by account A are awarded to account B. `DeleteRetroAccount` clears the queue, but switching without disconnecting does not. Separately, `SetRetroToken(nil)` nulls the token and then deletes the queue in two statements without a transaction, so a failure between them leaves rows the "turn off" was meant to drop.
- **Evidence:** `SetRetroAccount`'s `ON CONFLICT` touches only `retro_account`. The sender reads the current token per row (`acct.TokenSealed`) and never compares the row to the account it was queued under. The queue does not record that account at all.
- **Fix sketch:** In `SetRetroAccount`, when `ra_ulid` changes, delete the user's `retro_unlock_queue` rows in the same transaction (or store `ra_ulid` on each queued row and have the sender drop mismatches). Put `SetRetroToken`'s two statements in one transaction.
- **Verdict:** CONFIRMED by reading both ends. The window is real: queued rows with a future `next_at` are not swept by the "token is empty, drop it" branch until they come due.
- **Triage:**

## R04-8 Turning "visible to peers" off does not stop presence the account already granted

- **Severity:** S3
- **Class:** C5
- **Confidence:** low (this may be intended: the grants are separate, per-person consent)
- **Where:** `internal/store/presencegrant.go:117` (`ReadersOf`)
- **Failure:** An account grants a remote person presence, then turns `visible_to_peers` off, expecting to disappear from that server. The roster this server sends drops them, but their own outgoing `presence_grant` rows remain. `ReadersOf` does not join `user.visible_to_peers`, so `/api/federation/presence` keeps naming them and reporting what they are watching to that remote person, and `mayAsk` keeps letting that person ask to join them. ADR 0035's wording, as quoted in `peer.go` ("an opt-out that cannot take back what it gave is not an opt-out"), suggests the switch should withdraw everything.
- **Evidence:** `SELECT user_id FROM presence_grant WHERE fingerprint = ? AND person_id = ?`, with no condition on the granting account's visibility.
- **Fix sketch:** Join `user` in `ReadersOf` and require `visible_to_peers = 1` (keeping the grant rows, so turning visibility back on restores them). Alternatively, if per-person grants are meant to outrank the switch, say so on the settings screen.
- **Verdict:** PLAUSIBLE. The behaviour is certain. Whether it is wrong depends on how ADR 0035/0045 rank the two consents, and neither file in this slice settles that.
- **Triage:**

## Checked and clean

- **C8, no `*sql.DB` leaves the package:** no exported function or field in `internal/store` returns `*sql.DB`, `*sql.Tx` or `*sql.Conn`. The only other importer of `database/sql` outside tests is `internal/marker/introlab` (a lab tool with its own database).
- **C8, multi-statement writes:** every function in the slice with more than one `Exec` runs in a transaction, except `UpsertItem` (its follow-up statements are idempotent requeues, and a failure leaves the row correct but un-requeued), `EnsureCollection` and `ApplyTrackTags` (R05 territory, not judged here), and `SetRetroToken` (in R04-7). `DeleteUser`, `DeleteAllUsers`, `RedeemInvite`, `SetUserRole`, `SetHiddenLibraries`, `AddPeer`, `ReplaceRemotePeople`, `LearnPeerAddress`, `UseRecoveryCode`, `DeleteRetroAccount` and `CreateLibrary` are all single transactions.
- **C8, one-way migrations:** there are no down migrations by design (`migrate.go:11`). A database newer than the build is refused before anything runs (`migrate`, `InspectSnapshot`, `VerifyCopy`), and `BeforeMigrate` snapshots an existing database before the first pending revision. Each revision runs in its own transaction, together with its `ALTER TABLE ADD COLUMN`s and the version bump, so a failure leaves the previous revision intact, never a half-applied one.
- **Migration 18 (the only table rebuild):** foreign keys are switched off around it and `foreign_key_check` runs before commit. The pragma is set on the pool rather than on a pinned connection, which would be unsafe with concurrent users of the pool. At `Open` time nothing else holds a connection, so the `Exec` and the `Begin` reuse the same idle connection. It is fragile but not faulty, and `migrate18_test.go` exercises it.
- **schema.sql vs migrations:** `schema.sql` is revision 1 only, and a fresh install migrates 2→96 like an old one, so there is one path to the current shape, not two. Re-running `schema.sql` on every open is harmless: every statement is `IF NOT EXISTS`/`OR IGNORE`, and no migration drops an index or column that `schema.sql` re-creates.
- **Sessions:** stored as a hash, expiry checked on read whether or not the purge has run, joined to `user` so a deleted account stops resolving at once, all cleared on a password change (`DeleteAllSessions`), and cleared from every snapshot and every restore. Sign-out by handle is scoped by user for non-admins.
- **API keys:** stored as a hash, joined to `user`, cascade on account delete, and revocation is scoped by owner in the `WHERE`.
- **Invites:** the token is hashed. Redemption deletes the invite and creates the user in one `BEGIN IMMEDIATE` transaction (`_txlock=immediate`), so concurrent redemptions serialise and the loser gets `ErrInviteUnusable` (`TestARacedInviteMakesOneAccount`). A taken name rolls back and leaves the invite usable.
- **Library sharing:** `SharedLibraries` and `CeilingFor` are keyed by peer fingerprint and cascade on unpair and on library delete. `CeilingFor` does not repeat `SharedLibraries`' retro exclusion, but the grant handler refuses retro, comics and audiobook libraries and nothing can change a library's kind afterwards, so no retro row can exist.
- **Peers:** `RemovePeer` cascades to addresses, remote people, presence grants, library shares and peer progress. `ReplaceRemotePeople` upserts and then prunes, so routine refreshes keep consent.
- **C17, secrets:** sessions, API keys and invites are stored as hashes. The TOTP secret and the RetroAchievements key and token are sealed (`internal/secret`). Recovery codes are stored hashed, so their `==` compares hashes of high-entropy codes, which is not a timing oracle. Passkeys hold only public keys. The unlock queue stores bodies with the token field emptied.
- **Backup and restore under WAL:** `Snapshot` uses `VACUUM INTO` (consistent while live, no `-wal` needed) and re-opens the copy in `journal_mode(DELETE)` to clear sessions, leaving one self-contained file. `RestoreSnapshot` moves `-wal`, `-shm` and `-journal` aside with the old database under a collision-free stamp, copies rather than moves the snapshot, `fsync`s, and puts everything back on failure. Restoring over a running server is the caller's check (`serverapp`); a held file makes `moveAside` fail and roll back, with a message naming the likely cause. `VerifyCopy` checkpoints with `TRUNCATE` on a single connection and refuses if busy.
- **C16:** the ignored errors in the slice are `TouchAPIKey` (deliberately best-effort), the `RowsAffected` reads, and the queue sender's `DoneRetroUnlock`/`RetryRetroUnlock` (a failure re-sends an unlock, and RetroAchievements answers "already has" harmlessly). None sits on a data-integrity path.
- **SQLITE_BUSY:** `_txlock=immediate` plus `busy_timeout(5000)` turns snapshot-upgrade failures (517) into waits. `retention.Vacuum` holds an exclusive lock for a full rewrite, and on a large database that could outlast the 5 s timeout for a concurrent write; it is unmeasured, so it is not recorded as a finding.
- **Retention:** prunes only `audit_event` (an operator setting, 0 = keep) and `provider_cache` (refetchable). The persisted stamp survives restarts, and a policy change makes a pass due.
- **C1, C3, C6, C7, C9–C15, C18:** not applicable to this slice. No filesystem path comes from a row here, no network input is parsed, and there is no client code, ffmpeg or long-held file handle (`VerifyCopy` and `InspectSnapshot` close their handles before returning).
