## R15-1 An account is deleted by one press of a button that sits beside "Remove picture"

- **Severity:** S2
- **Class:** other
- **Confidence:** high
- **Where:** `web/src/screens/settings/users.tsx:242`
- **Failure:** In Settings → Users, an administrator presses "Remove" on somebody's row, perhaps meaning the "Remove picture" button drawn just before it. The account is deleted at once: `DELETE /api/users/{id}` runs on the click, with no second press and no dialog. Their sessions end, and their watch history, positions, playlists' ownership and settings go with the row (R04-6 records what is left behind). Nothing restores it short of a backup. Every other destructive control in the same pane asks first: Remove two-factor is two presses (`:208`), add-ons ask "Remove? Yes / No" (`addons.tsx:199`), Reset settings asks "Reset everything?" (`troubleshooting.tsx:186`), Clear watch history states the count and asks (`privacy.tsx:222`). The one that removes a whole person does not.
- **Evidence:**
  ```tsx
  {!isSelf && (
    <button className="set-btn set-btn--danger" disabled={del.isPending}
      onClick={() => del.mutate(user.id)}>
      Remove
    </button>
  )}
  ```
  `useDeleteUser` (`hooks.ts:539`) sends the DELETE with no further step, and `deleteUser` (`internal/api/users.go:112`) deletes the row.
- **Fix sketch:** The same two-press confirm the two-factor row uses: "Remove…" swaps to "Remove <name> and their history? / Keep" in the row.
- **Verdict:** CONFIRMED. Read the handler chain end to end; no confirm exists in the component, the hook or the server. `disabled={del.isPending}` stops a double send, not the first one.
- **Triage:** Fixed and merged in #1137.

## R15-2 A refused write to "Let others here see what I have watched" leaves the switch showing what the server refused

- **Severity:** S2
- **Class:** other
- **Confidence:** high
- **Where:** `web/src/screens/settings/privacy.tsx:78` (`SharingToggle`), `:40` (`WebhookConsent`)
- **Failure:** Somebody who shares their history turns the switch off. The PUT fails (a 500, a dropped connection, a session that lapsed between loading the pane and clicking). The switch stays off, because the local `pending` value is only cleared when the stored value *changes*, and a refused write changes nothing. An error line appears beside it, but the control itself says "not sharing" while the server goes on showing their finished titles on everybody's People page. The playback-webhooks consent switch has the same shape. `PeerVisibility`, ten lines below, already fixes exactly this with `onError: () => setPending(null)`, and its comment says why it matters for a privacy control; the two switches above it were not given the same line.
- **Evidence:** A proving test, run in this worktree and not committed (`web/src/screens/sharingRefused.r15.test.tsx`): auth status says `sharing: true`, `PUT /api/profile/sharing` answers 500, the test clicks the switch, waits for `.set-error`, and asserts the switch is still ticked.
  ```

  AssertionError: expected false to be true // Object.is equality
   ❯ src/screens/sharingRefused.r15.test.tsx:78:27
       78|     expect(box().checked).toBe(true);
   Tests  1 failed (1)
  ```
- **Fix sketch:** Pass `{ onError: () => setPending(null) }` to both `set.mutate` calls, as `PeerVisibility` does, and add the failing case to `sharingToggle.test.tsx`.
- **Verdict:** CONFIRMED by the test above. The webhook switch was confirmed by reading: same `pending`/`stored` pair, same missing `onError`.

## R15-3 An API key is revoked by one press

- **Severity:** S3
- **Class:** other
- **Confidence:** high
- **Where:** `web/src/screens/settings/security.tsx:181`
- **Failure:** Settings → Security lists API keys, each with a "Revoke" button that revokes on the click. A misclick on the wrong row cuts off whatever third-party client held that key, and a key cannot be un-revoked: the client has to be given a new one by hand. Survivable, which is why this is S3 and R15-1 is not, but it is the only irreversible control in Account settings with no second press.
- **Evidence:** `onClick={() => revoke.mutate(k.id)}`; `apiKeys.test.tsx:227` presses "Revoke" once and expects the DELETE, so the suite certifies the single press.
- **Fix sketch:** Two presses in the row ("Revoke <name>? / Keep"), and update the test.
- **Verdict:** CONFIRMED by reading the row and its test.
- **Triage:** Before 1.0, wave A (see [triage.md](../triage.md)).

## R15-4 Pressing Create twice makes two playlists, and a failed create or rename says nothing

- **Severity:** S3
- **Class:** other
- **Confidence:** high
- **Where:** `web/src/screens/Playlists.tsx:171` (`TitlePrompt`), `:321` (create), `:199` (rename)
- **Failure:** On a library's Playlists page, "New playlist" opens a prompt whose Create button is disabled only while the field is empty. The prompt stays open until the POST succeeds, so a double-click, or Enter pressed twice, sends `POST /api/playlists` twice and makes two playlists with the same name; the second success navigates to the second one and the first is left behind. If the POST fails, nothing is drawn: `TitlePrompt` renders no error, so the prompt just stays where it was. Rename has the same silent failure. Delete, in the same file, does disable itself while pending (`:235`), which shows the intent.
- **Evidence:** `disabled={value.trim() === ""}` on the confirm button and `if (e.key === "Enter" && value.trim()) onConfirm(value.trim())` on the field; neither reads `create.isPending`. No `isError` is read anywhere in `TitlePrompt`, `RenameTile` or the create branch.
- **Fix sketch:** Give `TitlePrompt` `busy` and `error` props; disable the confirm button and ignore Enter while busy, and draw the error under the field.
- **Verdict:** CONFIRMED by reading. Not driven in a test, since the behaviour is a pair of absent guards.
- **Triage:** Before 1.0, wave F (see [triage.md](../triage.md)).

## R15-5 Deleting a playlist from its page can delete it and leave you on it

- **Severity:** S3
- **Class:** other
- **Confidence:** low
- **Where:** `web/src/screens/Detail.tsx:1382`
- **Failure:** A playlist's page confirms deletion by relabelling its button ("Delete this playlist?"). The second press calls `deletePlaylist.mutate(undefined, { onSuccess: back })`, and the button is not disabled while that is pending (`SecondaryButton` takes no `disabled`). A third press while the first DELETE is in flight sends a second one. TanStack Query fires a call's own `onSuccess` only for the latest `mutate` call, so the first (successful) delete does not run `back`, and the second gets a 404 and does not either. The person is left on the page of a playlist that no longer exists, which then refetches into "This item could not be loaded".
- **Evidence:** The `SecondaryButton` at `:1383` has no `disabled`; the label changes to "Deleting…" but the press still reaches `onPress`, which calls `mutate` again because `confirmDelete` is still true.
- **Fix sketch:** Ignore the press while `deletePlaylist.isPending`, or give `SecondaryButton` a `disabled` prop.
- **Verdict:** PLAUSIBLE. The double send is certain from the code; the stranded page depends on the per-call callback rule in TanStack Query v5, which was not reproduced here, and needs a press inside the DELETE's round trip.
- **Triage:** Before 1.0, wave F (see [triage.md](../triage.md)).

## R15-6 Gold at full strength on controls at rest, and on an accepted face

- **Severity:** S3
- **Class:** C18
- **Confidence:** high
- **Where:** `web/src/screens/FacePeople.css:365`, `:54`, `:266`; `web/src/screens/RetroWebPlay.css:100`; `web/src/screens/Player.css:187` (low confidence)
- **Failure:** design.md: gold at rest is the ~20% hairline, full strength means *where you are*, and never gold on two elements in one focus scope. These rules draw full `--gold` with no focus, hover or selection in the selector:
  - `.facenamer__suggestion[data-taken]`: a suggested face the person has accepted is bordered in full gold, and the button is disabled (`FacePeople.tsx:254`), so it can never be where you are. Gold here means "accepted", a state, which is the exact misuse the rule names.
  - `.faces-page__scan` and `.facenamer__save`: a primary action bordered in full gold at rest, so with focus on any other control in the namer, two things are gold.
  - `.rweb__start`: the browser player's Start button, the same pattern.
  - `.player__volume-slider { accent-color: var(--gold) }`: the slider's fill is gold whether or not it has focus. Low confidence, since a range's fill could be read as its value rather than an accent.
  The detail page's Play button is gold-bordered at rest too, but design.md names it ("a gold-bordered play button", line 217), so it is not entered.
- **Evidence:** the selectors above, each with `border-color: var(--gold)` or `border: 1px solid var(--gold)` and no state in the selector. `FacePeople.css:362` says the taken mark is "an accepted suggestion, marked before the refetch confirms it".
- **Fix sketch:** `--gold-dormant` at rest with full gold under `:focus-visible`/`:hover`, as `Auth.css` does; mark an accepted face with the ✓ and opacity it already has, and drop the gold border.
- **Verdict:** CONFIRMED for the four FacePeople and RetroWebPlay rules by reading the selectors and the disabled state; the volume slider stays low confidence.
- **Triage:** Before 1.0, wave F (see [triage.md](../triage.md)).
