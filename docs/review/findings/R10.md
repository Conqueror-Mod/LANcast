## R10-1 Any local account can plant an "update" that the service installs into Program Files and then runs as SYSTEM

- **Severity:** S1
- **Class:** other (local privilege escalation; same family as R09-1)
- **Confidence:** high
- **Where:** `internal/selfupdate/stage.go:455` (`Apply`), `:432` (`Pending`); called from `internal/serverapp/main.go:1545` (`applyStagedUpdate`, on every shutdown) and gated only by `main.go:869` (a version check)
- **Failure:** The staging folder is `<data dir>\update-staged`, and in service mode the data directory is `C:\ProgramData\LANcast`. Nothing in the installer or the server sets permissions on that folder, so it inherits ProgramData's defaults, which let `BUILTIN\Users` create files and folders in it. `Apply` trusts whatever `staged.json` is there: the signature and digest are checked only in `update.downloadFrom`, before `Stage` writes, and never again. So any unprivileged local account (or malware running as one) creates `update-staged\staged.json` naming `{"version":"v99.0.0","files":["LANcast.exe"]}` plus its own `LANcast.exe`. Startup's discard check passes because v99 is "newer". At the next clean stop of `lancastd` (a restart from Settings, an in-app update, a reboot) the service, running as LocalSystem, moves the planted file over `C:\Program Files\LANcast\LANcast.exe`, and the next start runs it as SYSTEM. The tray and the desktop window run the same exe, so every user who opens LANcast runs it too. Worse, `Apply` never applies `safeStagedName` to the manifest's names (only `Stage` does), so a name like `..\..\Windows\System32\x.dll` makes the service move an attacker's file to any path on the machine.
- **Evidence:** ACL on the live data dir (read-only `icacls`):
  ```
  C:\ProgramData\LANcast NT AUTHORITY\SYSTEM:(I)(OI)(CI)(F)
                         BUILTIN\Administrators:(I)(OI)(CI)(F)
                         CREATOR OWNER:(I)(OI)(CI)(IO)(F)
                         BUILTIN\Users:(I)(OI)(CI)(RX)
                         BUILTIN\Users:(I)(CI)(WD,AD,WEA,WA)
  ```
  `(CI)(WD,AD)` is "create files / create folders" for Users, inherited by every folder. `grep` for `SetNamedSecurityInfo`/`icacls`/`AccessControl` in the installer and server finds only `mediatools.Protect` (the tools folder from #1096) and `servermode.GrantUser`; nothing touches the data dir or `update-staged`.
  Proving test (run in the worktree, not committed), a hand-written manifest and files, nothing from `Stage`:
  ```go
  os.WriteFile(filepath.Join(st, "LANcast.exe"), []byte("planted"), 0o644)
  os.WriteFile(filepath.Join(st, manifestName), []byte(`{"version":"v99.0.0","files":["LANcast.exe","../../escape.dll"]}`), 0o644)
  // ...source for the traversal name placed at st/../../escape.dll
  Apply(data, install)
  ```
  ```
  r10_probe_test.go:27: install/LANcast.exe = "planted"
  r10_probe_test.go:29: escape.dll written OUTSIDE the install dir at ...\002\escape.dll
  --- PASS: TestR10PlantedManifestIsApplied
  ```
  Even a genuine staging can be raced: `Stage` does `RemoveAll` then `MkdirAll`, and the new folder inherits the same Users ACE, so a watcher can create `LANcast.exe` (owned by itself) before the service writes into it, and rewrite it later.
- **Fix sketch:** Make `Apply` re-verify instead of trusting the folder: stage `checksums.txt`, `checksums.txt.sig` and the archive (or keep the per-file digests from the signed list in the manifest *and* the signature over that list), and in `Apply` call `release.VerifyChecksums` and check every file's SHA-256 before moving it; refuse any name failing `safeStagedName` or not in `installFiles`. Also create `update-staged` with `mediatools.Protect`'s protected DACL (SYSTEM + Administrators only) and refuse to apply from a folder whose owner/DACL fails `mediatools.ServiceGuard`. Longer term, give `C:\ProgramData\LANcast` itself a protected DACL in the installer or `service install`, since other subfolders may share this shape (see R10 entries below).
- **Verdict:** CONFIRMED. I looked for anything between the folder and the move that could stop it. `Pending` checks only that the JSON parses with a version and files. Startup's check (`main.go:869`) only discards a version that is not newer. `Apply` stats each file and renames it, with no digest, signature, owner or name check. The proving test shows a manifest that `Stage` never wrote being applied, including a name that leaves the install directory. The ACL is read from the live install. This applies only in service mode. A per-user server's data directory is in that user's profile, where the planter and the server are the same account.
- **Triage:** Fixed and merged in #1124.

## R10-2 Any local account can stage a restore of its own database, and is a LANcast administrator after the next restart

- **Severity:** S1
- **Class:** other (local privilege escalation; same root cause as R10-1)
- **Confidence:** high
- **Where:** `internal/backup/restore.go:122` (`ApplyPending`), called first thing in `internal/serverapp/main.go:351`; `backup/dir.go:203` (`Resolve` checks only the name's shape)
- **Failure:** `C:\ProgramData\LANcast\backups` inherits `BUILTIN\Users:(CI)(WD,AD)` from ProgramData (live `icacls` below). An unprivileged local account writes `backups\lancast-backup-20990101-000000.db` (any SQLite file with LANcast's schema and a `user` row whose bcrypt hash it chose) and `backups\restore-pending.json` naming it. `ApplyPending` runs on the next service start, before the database opens, and checks only that the name has the backup shape and lives in the folder; it does not check who wrote the marker or the file. The database is replaced, and the attacker signs in as an administrator. Inside LANcast an administrator can add a library at any path and browse the filesystem as SYSTEM (C2's reason for the loopback rule), read every account's data, install plugins and set webhooks. The marker file is absent in the normal state, so there is no race to win; the attacker only waits for a restart (or a reboot).
- **Evidence:**
  ```
  C:\ProgramData\LANcast\backups NT AUTHORITY\SYSTEM:(I)(OI)(CI)(F)
                                 BUILTIN\Administrators:(I)(OI)(CI)(F)
                                 CREATOR OWNER:(I)(OI)(CI)(IO)(F)
                                 BUILTIN\Users:(I)(OI)(CI)(RX)
                                 BUILTIN\Users:(I)(CI)(WD,AD,WEA,WA)
  ```
  `ApplyPending` reads `d.pendingPath()`, `Resolve(out.Name)`, then `store.RestoreSnapshot(ctx, dbPath, path)`; no owner or signature check anywhere on the path. `Dir.Create` uses `MkdirAll(…, 0o700)`, which sets no ACL on Windows.
- **Fix sketch:** Give the data directory a protected DACL (SYSTEM and Administrators full control, Users nothing or read on non-secret folders only) at `service install` and on every service start, the way `mediatools.Protect` does for the tools folder, and have `ApplyPending` refuse a marker or backup whose owner is not SYSTEM/Administrators (`mediatools.ServiceGuard` already reads owner and DACL). One fix covers R10-1, R10-2 and R10-3.
- **Verdict:** CONFIRMED by reading, and not run, because it needs the service restarted. `store.RestoreSnapshot` validates the file as a LANcast snapshot at a revision this build can migrate. An attacker gets a valid one by running a portable LANcast as themselves, creating an account, and copying that database into `backups\`. Nothing on the path compares the marker or the file against who wrote them.
- **Triage:** Fixed and merged in #1115, #1125.

## R10-3 Every local account can read the server's private keys, its secrets key and the live database

- **Severity:** S1
- **Class:** C17
- **Confidence:** high
- **Where:** the data directory as created by the installer and the service (`installer/lancast.nsi`, `internal/config`); the 0600 modes in `internal/identity/identity.go:240`, `internal/tlscert/tlscert.go:191`, `internal/secret/secret.go:51`, `internal/config/settings.go:501` mean nothing on Windows
- **Failure:** In service mode every file under `C:\ProgramData\LANcast` inherits `BUILTIN\Users:(RX)`. A guest or child account on the same PC (or malware running as one) can copy `identity\key.pem` and impersonate this server to every paired server (ADR 0044: it is never regenerated, so the leak is permanent), copy `tls\key.pem` and impersonate it to every client that pinned it, copy `secrets.key` and decrypt every stored secret (TMDB/OpenSubtitles keys, webhook secrets, RetroAchievements token), and copy `lancast.db` (with `-wal`) for every account's password hash, TOTP secret and viewing history. Backups in `backups\` are readable the same way. The code comments say each file is "written 0600", which reads as protection and is none on Windows.
- **Evidence:** live, read-only:
  ```
  C:\ProgramData\LANcast\secrets.key      NT AUTHORITY\SYSTEM:(I)(F)  BUILTIN\Administrators:(I)(F)  BUILTIN\Users:(I)(RX)
  C:\ProgramData\LANcast\lancast.db       … BUILTIN\Users:(I)(RX)
  C:\ProgramData\LANcast\identity\key.pem … BUILTIN\Users:(I)(RX)
  C:\ProgramData\LANcast\tls\key.pem      … BUILTIN\Users:(I)(RX)
  ```
  `docs/security.md` lists "a user with filesystem access to the data directory" as out of scope, and line 185 says "the data directory is owned by the service account". The first assumes such access takes privilege; on a default install it takes any login. That is why this is filed rather than left to the threat model.
- **Fix sketch:** Same fix as R10-2: a protected DACL on the data directory (owner Administrators, SYSTEM and Administrators full control, no Users ACE), applied by `service install` and re-asserted at each service start, plus a test that reads it back. Update `security.md` to say what the folder's ACL is.
- **Verdict:** CONFIRMED from the live ACLs. The disproof I tried is the threat model: `security.md` puts "filesystem access to the data directory" out of scope. That holds only if the access needs privilege, and on a default install it does not. Triage may still accept it for a single-person PC; on a family PC with separate accounts it is a real boundary.
- **Triage:** Fixed and merged in #1115.

## R10-4 A plugin that loops never stops: the sandbox has no time limit, no memory limit, and a cancelled context does not reach it

- **Severity:** S2
- **Class:** C15
- **Confidence:** high
- **Where:** `internal/plugin/runtime.go:84` (`wazero.NewRuntime(ctx)` with the default config), `:171` (`Call`); `:241` (`io.ReadAll(resp.Body)` with no bound); `bundle.go:180` (`readZip`, unbounded)
- **Failure:** wazero only interrupts guest code on context cancellation when the runtime is built with `RuntimeConfig.WithCloseOnContextDone(true)`, and this one is not. No caller sets a deadline either. So a provider plugin whose `search` loops on some title (a bug is enough; hostility is not required) never returns: the enrichment goroutine that called it is stuck for the life of the process, holding `enrichMu` (`serverapp/main.go:644`), so enrichment of every item stops until a restart, and shutdown gives up on it after `workerStopGrace` and closes the store under it. There is no memory cap either (the default allows 65,536 pages, 4 GiB, per instance, and `Call` instantiates afresh each call), and the host fetch reads a granted host's response with no size limit before copying it into guest memory. ADR 0021's "deny by default" holds for authority (http, secrets, no WASI filesystem or env); it does not hold for CPU and memory.
- **Evidence:** proving test (run, not committed): a hand-assembled module exporting `spin` (`loop br 0 end`), called through `Plugin.Call` with a 1 s `context.WithTimeout`:
  ```
  === RUN   TestR10SpinIgnoresDeadline
      r10_probe_test.go:35: still running 4 s after its 1 s deadline expired
  --- PASS: TestR10SpinIgnoresDeadline (5.00s)
  ```
  `grep` for `WithCloseOnContextDone`, `WithMemoryLimitPages` and `NewRuntimeConfig` in the repo finds nothing.
- **Fix sketch:** Build the runtime with `wazero.NewRuntimeConfig().WithCloseOnContextDone(true).WithMemoryLimitPages(n)` (a few hundred pages is plenty for a metadata provider), wrap every `Call` in `context.WithTimeout` (for example 30 s), bound `defaultHTTPGet` with `io.LimitReader` (a few MiB) and `readZip` with the bundle's own size cap. Add the spin test above as the regression test.
- **Verdict:** CONFIRMED by the proving test. It needs an administrator to install the plugin, and a buggy plugin is enough; hostility is not required. It is S2 rather than S1 for that reason: the hang is of enrichment, not of the server.
- **Triage:** Fixed and merged in #1138.

## R10-5 Any local account can drop `lancast-faces.exe` into the data directory, and the service runs it as SYSTEM, with no restart needed

- **Severity:** S1
- **Class:** C9 (a child process the service runs) / other (local privilege escalation)
- **Confidence:** high
- **Where:** `internal/serverapp/main.go:536-551` (`faceTool := &faces.Tool{Dir: faceDir, …}`, where `faceDir` is `<data>\faces`); `internal/faces/tool.go:102` (`Path` looks in `Dir` **before** the install directory)
- **Failure:** The face worker is optional and usually absent. `Tool.Path` looks for `lancast-faces.exe` first in `C:\ProgramData\LANcast\faces`, then beside `LANcast.exe`, then on `PATH`. That folder exists on any install that downloaded the face models, and it inherits the Users "create files" ACE. An unprivileged local account writes its own `faces\lancast-faces.exe`. The next time anything asks for the worker, the service starts it as LocalSystem. Opening Settings → Photos does that: it calls `GET /api/faces/capabilities`, which runs `probe` → `<exe> capabilities`. So do the photo worker and a semantic search. On the owner's machine the real worker sits in Program Files, so the planted copy wins the lookup. R09-1 closed this hole for ffmpeg with `mediatools.ServiceGuard`. The face worker has no guard.
- **Evidence:** live, read-only:
  ```
  C:\ProgramData\LANcast\faces … BUILTIN\Users:(I)(CI)(WD,AD,WEA,WA)
  Test-Path C:\ProgramData\LANcast\faces\lancast-faces.exe   → False
  Test-Path C:\Program Files\LANcast\lancast-faces.exe       → True
  ```
  `grep Guard|mediatools internal/faces` finds nothing, and `Path()` is only a `fileExists` check. The same folder supplies `onnxruntime.dll` (`main.go:542`), which the worker loads. It is SYSTEM-owned here because it was downloaded. On an install that has not downloaded it yet, a planted DLL would be loaded the same way.
- **Fix sketch:** As the service, look for the worker only beside `LANcast.exe` in Program Files. Otherwise, apply `mediatools.ServiceGuard` to `faceDir` and refuse the folder when it fails, as `Locator` does for ffmpeg. The protected data-directory DACL from R10-2 also closes this, but the lookup order should not depend on that.
- **Verdict:** CONFIRMED. I tried to find a check between `Path()` and `exec.CommandContext` in all four callers (`tool.go:296`, `worker.go:241`, `embed.go:329`, `embedtext.go:206`). There is none. `facesCapabilities` is reachable by any signed-in session. The planted file is absent today, so the attack needs no race.
- **Triage:** Fixed and merged in #1126.

## R10-6 A service that fails to start is never restarted, though the install comment says it retries

- **Severity:** S2
- **Class:** other
- **Confidence:** high
- **Where:** `internal/service/manager_windows.go:51-75` (`setRecoveryActions`); `internal/serverapp/service_windows.go` (`Execute` returns `false, 1` when `run` fails)
- **Failure:** Recovery actions are set, but `FailureActionsOnNonCrashFailures` is left false. When `run` returns an error, `Execute` reports a clean stop with exit code 1. Windows counts that as a non-crash failure and takes **no** recovery action. So the case the comment names never retries (its words: "a server that cannot start at all … retries a few times, gives up"). A start can fail on a transient condition: the port is still held by the old process after an in-app update restart (`cannot listen on …: Another LANcast may still be running`), the database file is locked, or a pre-migration step fails. Any of these leaves the server down with nobody at the machine. A restart happens only when the process dies, through a panic or a kill.
- **Evidence:** live, read-only:
  ```
  > sc.exe qfailureflag lancastd
  FAILURE_ACTIONS_ON_NONCRASH_FAILURES:  FALSE
  > sc.exe qfailure lancastd
  FAILURE_ACTIONS : RESTART -- Delay = 5000 milliseconds. / 15000 / 60000
  ```
  `grep -rn NonCrash` in the repo finds nothing. `x/sys/windows/svc/mgr` has `SetRecoveryActionsOnNonCrashFailures(true)` for exactly this case.
- **Fix sketch:** Call `s.SetRecoveryActionsOnNonCrashFailures(true)` after `SetRecoveryActions` at install. For existing installs, also call it once at service start (it needs the service's own handle, which SYSTEM has). The limit of three attempts and then stop still keeps a newer-schema database from looping.
- **Verdict:** CONFIRMED for the mechanism: the live flag is FALSE, and `Execute` exits cleanly with code 1 on a `run` error. How often a start fails for a transient reason is not measured. The usual update path applies the swap on a clean stop and starts a fresh process, so the window is a few seconds.
- **Triage:** Fixed and merged in #1141.

## R10-7 Any local account can create the server's single-instance mutex first and keep the service from starting

- **Severity:** S3
- **Class:** other
- **Confidence:** low
- **Where:** `internal/singleton/singleton_windows.go:70` (`acquire`), `serverapp/service_windows.go` (`serviceServe` exits when `held` is false)

## R10-8 SSDP answers an M-SEARCH from any address, including the internet when the machine's preferred address is public

- **Severity:** S3
- **Class:** other
- **Confidence:** low
- **Where:** `internal/dlna/run.go` (`Announce`: every parsed M-SEARCH is answered with `send.WriteToUDP(…, from)`); `internal/serverapp/dlna.go` (`preferredIP` takes the first stable IPv4, and `HomeFirst` prefers a private address but does not require one)
- **Failure:** The DLNA HTTP side refuses non-private callers (`api/dlna.go:46`), but the SSDP side has no such check. Two setups expose it: a machine whose LAN address is public (R01-14 describes such a host), or one where UDP 1900 is reachable from outside. There, a spoofed `M-SEARCH * ssdp:all` of about 100 bytes makes the server send five responses (about 1.3 KB) to the spoofed source. That is a small reflection amplifier, and it discloses the server's `LOCATION`. Separately, the listener binds once to the address it sees at start. After a DHCP change it no longer hears searches until DLNA is toggled, while the announcements move to the new address.
- **Evidence:** Reading only. Not run, because it needs the listener on port 1900, which belongs to the live service.
- **Fix sketch:** Answer only sources that are private, link-local or on the same subnet as the bound address, matching the HTTP side's rule. Re-bind when `preferredIP()` changes.
- **Verdict:** PLAUSIBLE. The code answers any source. Whether port 1900 is reachable from outside depends on the host. On a typical NAT'd home LAN it is not.
- **Triage:** Before 1.0, wave B (see [triage.md](../triage.md)).

## R10-9 A swap that fails halfway leaves new files the old version never had

- **Severity:** S3
- **Class:** other
- **Confidence:** high
- **Where:** `internal/selfupdate/stage.go:524-541` (`Apply`'s loop and `rollback`)
- **Failure:** `rollback` only undoes the step that moved an old file aside. Some staged files have no counterpart in the install, such as a DLL new in this release (`lancast-cheevos.dll` when it first shipped). Such a file is moved into place and recorded nowhere. If another file then fails, the rollback restores the old exe beside the new DLL. The comment promises "the worst outcome is an install that did not update". This outcome is an install that partly did.
- **Evidence:** Reading only. `done` gets an `undo` entry only inside `if _, err := os.Stat(target); err == nil`.
- **Fix sketch:** Record every move, including "installed a new file", which is undone by removing that file, and roll them all back. Alternatively, copy every file to `target.new.<stamp>` first, and rename them into place only once the whole set sits beside its targets.
- **Verdict:** CONFIRMED by reading. An extra DLL that the old exe does not load is harmless today, so the effect is limited to a future release whose old and new files must match.
- **Triage:** After 1.0: no current release ships a pair that must match.

## R10-10 Shutdown closes the database while unowned goroutines may still use it

- **Severity:** S3
- **Class:** C15
- **Confidence:** low
- **Where:** `internal/serverapp/main.go:1054-1114` (`go periodicScan`, `periodicPrune`, `periodicBackup`, `hooks.Run`, `runDLNA`, `RunOptimizer`, `RunRetroUnlockQueue`, `WatchPeers`); `:1339` (`waitForWorkers` waits only for `workers`); `:368` (`defer st.Close()`); `:1325` (`case err := <-errc: return err` skips the worker wait entirely)
- **Failure:** Only goroutines added to `workers` are waited for before the store closes. The periodic scan, prune, scheduled backup, optimizer and RetroAchievements queue run on `ctx` and are cancelled, but nothing waits for them. One that is mid-statement when `st.Close()` runs fails with `sql: database is closed`: a scan stops mid-reconcile, or a prune or queue write is left half done. When a listener fails after start (`errc`), `run` returns without calling `cancelEnrich()` or waiting at all, and the deferred close runs under every worker. No corruption has been observed. The store's multi-statement writes are transactional (C8), which limits the damage to errors and lost work.
- **Evidence:** Reading only.
- **Fix sketch:** Run every long-lived goroutine under the same `workers` group, or under a second group that is waited for before `st.Close`. Route the `errc` path through the same cancel-and-wait as the normal stop.
- **Verdict:** PLAUSIBLE. Every listed loop checks `ctx` between items, so the window is one statement long. I found no test that shuts down during a scan.
- **Triage:** Before 1.0, wave C (see [triage.md](../triage.md)).

## R10-11 The systemd unit breaks on a path with a space and runs the server as root

- **Severity:** S3
- **Class:** other
- **Confidence:** high
- **Where:** `internal/service/service.go:86` (`SystemdUnit`)
- **Failure:** `ExecStart=%s -data %s -addr %s` writes the paths unquoted. systemd splits on whitespace, so `-data "/srv/my media/lancast"` becomes two arguments, and the service either starts on the wrong data directory or fails. The unit has no `User=` line, so the server and every ffmpeg it runs are root. `security.md` says so, but the unit could avoid it at no cost with `DynamicUser=` or `User=lancast`.
- **Evidence:** `service_test.go:56` asserts the unquoted form, and only for a path without spaces.
- **Fix sketch:** Quote each `ExecStart` argument the systemd way (`"…"` with `\"` escapes). Add a `User=` line, and create that account in the documented install steps.
- **Verdict:** CONFIRMED by reading for the quoting. Running as root is a known and documented choice, so triage may decide it is not a finding.
- **Triage:** Before 1.0 for the quoting (wave G). The `User=` line is after 1.0: documented in security.md; costs an install step.

The service then writes into a file the attacker owns, and the rename keeps that owner, so the attacker can later rewrite `config.json` (webhooks, keys, listen address) or a renewed TLS key. Same root cause and same fix as R10-2. Not run.

## Checked and clean

- **Release verification.** The signature is Ed25519 over `checksums.txt`, with a compiled-in key. A build with no key refuses (`release.Signable`). The archive's SHA-256 must be in the signed list. Names outside `installFiles`, and names with paths, are skipped. Every fetch is capped at 256 MiB, and the release lookup URL is a constant. The archive name comes from the unsigned tag but must appear in the signed list, so a forged tag cannot name an unsigned file. Signing happens before staging only; `Apply` does no check of its own, which is R10-1.
- **Version comparison.** `Newer` needs exactly three numeric parts on both sides and refuses any suffix:
  - `Newer("0.11.x","1.0.0")` is false, because the "x" does not parse, so it fails closed.
  - `Newer("0.11.5","1.0.0")` is true, and `Newer("1.0.0","0.11.9")` is false.
  - `dev` never updates, and a two-digit minor compares numerically.

  Startup discards a staged update that is not newer than the running build (`main.go:869`). That check is the only gate on a planted staging (R10-1).
- **Shutdown order for the `workers` group.** Workers are cancelled and waited for (bounded at 3 s) before the HTTP server shuts down. The staged swap runs after serving stops. The event streams are closed before `Shutdown`, so it does not wait on them. The rest is R10-10.
- **Webhooks (C17, SSRF).**
  - Only an administrator can create one. The URL must be http(s) with a host and no userinfo.
  - Redirects are not followed, and response bodies are drained only up to 64 KiB. The timeout is 10 s.
  - Four workers serve a 256-slot queue that drops rather than blocks.
  - Each delivery carries an HMAC-SHA256 signature made with a 32-byte random secret.
  - Logs carry the hook id, never the URL or the secret.

  Private targets are allowed on purpose, since a LAN receiver is the normal case.
- **Problem reports (C17, no phone-home).** A report is sent only when a person presses Send. The destination is compiled in from a CI secret, or set by an env override. Only an administrator may attach the log tail, and the request says so. The account is sent as "admin" or "member", never a name. Request logs record `r.URL.Path` without the query, so tickets and keys in query strings do not reach the tail.
- **Crash logs.** Written locally under `crashes\`, pruned to 50, never uploaded.
- **Update check (no phone-home).** A plain GET to a constant URL, which can be switched off. The first check runs 2 minutes after start, then daily.
- **Plugin authority.**
  - Host functions check the manifest grant on every call, and secrets are resolved per plugin.
  - Fetches go through `netguard` (R01-15 covers CGNAT), are rate-limited and cached, and are logged with redacted URLs.
  - WASI is instantiated with no filesystem mounts, env or args.
  - Installed bundles are re-digested on every load, and capabilities come from the stored grant, not the manifest.

  Resource limits are R10-4.
- **Single-instance lock.** A global mutex whose DACL lets other sessions open it for `SYNCHRONIZE` only, with a fallback to a session-local name. `ERROR_ACCESS_DENIED` is read as held. The squat is R10-7.
- **Service install.** `mgr.CreateService` quotes the executable path and escapes each argument, so there is no unquoted service path. The data directory must be given explicitly. Uninstall stops the service, then deletes it. #1096's `mediatools.Protect` gives `tools\` the DACL `O:BAD:PAI` with SYSTEM and Administrators full control and Users read. The service re-checks that owner and DACL on every start. Nothing gives the rest of the data directory the same treatment (R10-1, R10-2, R10-3, R10-5).
- **Backups under WAL, and retention.** Snapshots use `VACUUM INTO` (R04 checked the snapshot itself). Scheduled backups rotate only their own kind. Pre-migration backups keep 3, and hand-taken ones are never deleted. A restore marker is removed before the restore is tried, so a bad backup cannot loop. Where the marker comes from is R10-2.
- **DLNA HTTP.** Refuses non-private callers. It runs only when the server is LAN-bound, has a password and has a chosen account; R03-6 covers the gap when the account is cleared. SSDP binds the LAN address with `SO_REUSEADDR`, per the global rule. Announcements go out every 10 minutes, with a byebye on stop.
- **Events hub.** Coalesces per subscriber, with a capacity-one nudge. `Close` ends every stream and refuses later subscriptions. No goroutine per subscriber is left behind.
- **Face model downloads.** Every asset, including the models and the ONNX runtime zip, is pinned by SHA-256 and checked before it is placed.
- **Linux.** `GOOS=linux go vet ./...` exits 0.
- **C10.** No file in the slice is held open for a long time. The log file is the service's own.
- **C11.** Backup names use `Format` on a local time. Crash report ids are UTC on purpose: they are ids, not dates shown to the user.
