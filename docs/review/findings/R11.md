## R11-1 Following the rotation prompt's instruction cannot detect an impostor, and accepting it gives the impostor the session

- **Severity:** S1
- **Class:** other (trust on first use / certificate pinning)
- **Confidence:** high
- **Where:** `cmd/lancast/picker.html:236-252` (rotation view), `cmd/lancast/servers.go` (`lancastServerAcceptRotation`, `lancastServerIdentity`), `internal/knownserver/knownserver.go:281` (`Check` returns `TrustRotated` whenever an identity is on record), `web/src/lib/serverIdentity.ts:48`
- **Failure:** The client has accepted a remote server and recorded its identity. Something else now answers at that address with its own certificate: ARP spoofing on the LAN, a hijacked DNS name, or a proxy in front of a public name. `Check` sees a new key and an identity on record, and returns `TrustRotated`. The picker shows "Identity you accepted", which is the identity **from the client's own record**. It asks the person to have the operator read out the identity from their Settings › General, and its button says "The identity matches — connect". The real operator's screen shows the real server's identity, and the record holds the same value. So the comparison matches every time, whoever is answering. Nothing in the comparison involves the new key. Accepting stores the impostor's key as the pin and relaunches the window against it. The window then sends its session cookie to the impostor, which can use it against the real server. After that, the identity check (`lancastServerIdentity`) only compares a fingerprint that the page itself reports from `GET /api/identity`. That page belongs to the impostor, and the response is unsigned. The impostor returns the recorded value, which the picker has just displayed, and the check passes.
- **Evidence:** `picker.html:241-243` fills `rotate-identity` from `result.identity_display`, which `lancastServerProbe` sets from `prev.Identity` (the stored record). `AcceptRotation` writes `newPin` with no other condition (`knownserver.go:368`). `serverIdentity.ts:48-49` gets `fingerprint` from `/api/identity` on the origin being checked and passes it straight on. Nothing anywhere asks the server to prove it holds the identity key. ADR 0070's amendment says the client "asks the person to confirm out of band that the server is still that one". That confirmation compares two copies of the same number.
- **Fix sketch:** Make the identity prove itself over the new connection. Add an unauthenticated endpoint where the server signs `(client nonce ‖ the SPKI of the TLS key serving this connection)` with its Ed25519 identity key. Have `lancastServerAcceptRotation` verify that signature against the recorded identity before saving the pin, so no person needs to compare anything. Until then, the honest prompt asks the operator to read out the **certificate** fingerprint (`certificate_fingerprint`, already in Settings) and compares it with "Certificate fingerprint now".
- **Verdict:** CONFIRMED. I tried to disprove it by looking for any later check that ties the new key to the identity. There is none. `RecordIdentity` never overwrites, but it is never reached with a different value, because the impostor reports the recorded one. The picker does show the new certificate fingerprint ("Certificate fingerprint now"), so a careful person could compare that instead. The text, the heading and the button all point them at the identity.
- **Triage:** Fixed and merged in #1118, #1119.

## R11-2 Every native binding is open to every document the window shows, including a remote server's page and anywhere it navigates

- **Severity:** S2
- **Class:** other (host-object exposure)
- **Confidence:** high
- **Where:** `internal/webview2/webview.go:207` (`msgcb`, no check of the source), `:583` (`Bind` injects through `AddScriptToExecuteOnDocumentCreated` for every document), `edge/chromium.go:202-221` (no `NavigationStarting` or `NewWindowRequested` handler), `cmd/lancast/main.go:492` (every binding, on every page)
- **Failure:** The window exposes about 55 functions to whatever top-level document it holds, and never asks which origin is calling. The picker's trust decisions (`lancastServerAccept`, `lancastServerAcceptRotation`, `lancastServerForget`) are among them, along with `lancastDesktopSet` (run at login, devtools on), `lancastLaunchGame`, `lancastSwitchServerMode` and the retro core installer. With ADR 0070 the window shows *remote* servers' pages, and the person chose those servers for their libraries, not to manage this machine. Any script on a remote server's origin can call `lancastServerAccept("other-host:8443", "x")`, which fetches that host's key, records it as trusted with no fingerprint shown to anybody, saves it as the server to open next time, and relaunches the window there. The same script can turn devtools and run-at-login on, start any installed game, or forget trusted servers. Nothing limits navigation either: a server page, or a link without `target`, can send the main frame to any https site. Because the bindings are injected for every document, that site gets the same functions.
- **Evidence:** `msgcb` decodes `{method, params}` and calls `w.bindings[method]` directly. `MessageReceived` never reads `args.Source`. The only handlers registered are WebMessageReceived, PermissionRequested, WebResourceRequested, NavigationCompleted and AcceleratorKeyPressed. The shipped client's external links all carry `target="_blank"`, which opens a separate WebView2 popup without the bindings, so the client itself does not leak them today. The exposure comes from server-side script, not from the client's own links.
- **Fix sketch:** Register `NavigationStarting` and cancel any top-level navigation whose origin is not the window's server, the picker (`about:blank`/NavigateToString) or the loopback public name, and send those URLs to the system browser instead. In `msgcb`, check `args.Source` against the same origin. Give the picker's trust bindings only to the picker document, not to server pages.
- **Verdict:** CONFIRMED for the mechanism. The impact is PLAUSIBLE: it needs a remote server operator who acts against their own guests, or script injected into a server origin. Each binding guards its own inputs well (games must be installed, the mode switch goes through UAC, mpv's command set is closed), so the worst concrete case is the silent trust change above.
- **Triage:** Fixed and merged in #1129.

## R11-3 A pin mismatch in the window is a click-through warning, and a remote server is not re-checked before the window opens

- **Severity:** S2
- **Class:** other (certificate pinning)
- **Confidence:** high
- **Where:** `cmd/lancast/connect.go:83` (`resolve` returns the stored pin for a remembered remote server without fetching its current key), `internal/webview2/edge/chromium.go` (no `ServerCertificateErrorDetected` handler), `cmd/lancast/main.go:305-307, 332-336`
- **Failure:** At launch, the window for a remembered remote server opens directly, with `--ignore-certificate-errors-spki-list=<stored pin>`. If that server now presents a different key, whether from a real rotation or an impostor, the picker's `Check` never runs. The window gets Chromium's own certificate interstitial instead, and that offers a way to proceed. The project's own text describes it: "a browser security warning inside a native app window, and clicking through it lands on a blank page", and the startup alert tells people "accepting it leads to a blank page". Proceeding sends the navigation request, with the origin's session cookie, to whichever key answered. ADR 0070 promises the opposite: "Nothing is sent to the new key before that". `watchForRecovery` reloads the same URL, so the same applies when the window reconnects mid-session.
- **Evidence:** `resolve` gives `target{address, pin: known.Pin}`, and `runWindow` passes `l.target.pin` to `clientwindow.Open`. `knownserver.Fetch`/`Check` are only reached through picker bindings. `clientwindow_windows.go:422-436` sets the switch, which exempts one key and leaves every other certificate to normal validation, and normal validation in WebView2 includes the proceed link.
- **Fix sketch:** Handle `ServerCertificateErrorDetected` (`ICoreWebView2_14`) with `COREWEBVIEW2_SERVER_CERTIFICATE_ERROR_ACTION_CANCEL`, and show the picker's rotation or refusal view in its place. Also, before opening a remote target, run `knownserver.Fetch` + `Check` and send anything but `TrustMatch` to the picker.
- **Verdict:** CONFIRMED on the code: there is no handler and no pre-check. That the interstitial offers a way through was not observed again here, because no server or window was run. It rests on the repository's own report at `main.go:305-307`. If triage takes that report as current, consider S1, since a session crosses to an unverified key.
- **Triage:** Fixed and merged in #1127.

## Checked and clean

- **mpv.** It loads only `http://127.0.0.1:<port>/v/<random 192-bit key>` from the relay (`player_windows.go` `open`), never a server-supplied URL or path. The relay builds `/api/stream/<id>` itself from an integer, forwards only range headers, binds 127.0.0.1, pins TLS with `certpin.TLSConfig`, and refuses https with no pin. The ticket stays out of mpv's URL and log. `command` is a closed switch with clamped numbers, and filters are built from a fixed vocabulary (`amovie` excluded). Options turn off `config`, `load-scripts`, `ytdl`, and input bindings. No mpv option can be carried through the page.
- **Syscall lifetimes.** `mpv` keeps every C string alive across its call (`runtime.KeepAlive` on `ptrs`, `name`, `n`, `pa`/`pb`). Doubles go through `Call` correctly, because Go's Windows amd64 trampoline mirrors integer argument registers into XMM0–3. `String` frees with `mpv_free`. `Close` wakes, quits, joins the loop, then destroys. The window classes in `overlay.go` are `sync.OnceValue`, so callbacks are not minted per window. The low-level keyboard hook is unhooked on `remove` (deferred in `open`). The COM handler objects in `edge/` are handed to native code as `uintptr` and kept alive by the `Chromium` struct. The vendored comment names the theoretical moving-GC risk, which current Go does not have. The `vsync` adapter is closed and zeroed once.
- **Single instance and raise.** The events and the 512-byte section live in `Local\`, so they are per session and only processes of the same logged-on session reach them. The payload length is bounded on both sides and cleared after reading. The pane goes into script only through `json.Marshal` (`desk.go` `inPageScript`), so it cannot break out of the string. Stopping the listener sets both events, joins with a 2 s bound, and closes every handle.
- **Tray handover and exit.** `desk.exit` closes the window through `Dispatch`, so `PostQuitMessage` reaches the window's thread. After `Open` returns, `native.shutdown()` cancels any pending restore and restores the display. `stopStartedServer` kills and reaps with a bound.
- **Display mode.** The restore record is written before the switch and removed after the restore. Recovery puts the device back to its registry mode, and nothing here writes the registry. Stopping a film restores after 5 s unless the next film reuses the rate.
- **Devtools in release builds.** They are off unless `desktopprefs.DevTools` is set: `Debug` turns off both the context menu and `AreDevToolsEnabled`. That preference can be written by any page through `lancastDesktopSet` (R11-2).
- **Downloads and popups.** There is no `DownloadStarting` handler, so WebView2's own download UI and folder are used, as in a browser. `target="_blank"` links open a separate WebView2 popup, which is not given the bindings or the message handler.
- **The certificate pin switch.** `validPin` accepts exactly a base64 SHA-256 before it goes into the switch list, so no extra switches can be appended. An existing `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` is refused rather than merged.
- **C13.** `picker.html` uses no `confirm()` or `alert()`. `alert()` in `cmd/lancast` is a native message box shown before the window exists or after it has closed, never over the page. The client's own uses are R16's.
- **C10.** No file in the slice is held open: the preferences, trust record and restore record are read and written whole.
- **C15.** The relay's server goroutine ends with `Close`, which runs when the service port moves. On shutdown the process exits with it. The raise watchers are joined. The probe bindings use an 8 s context that they cancel themselves.
- **C1–C9, C11, C12, C14, C16–C18.** These do not apply: the slice serves nothing, writes no SQL, runs no ffmpeg, and shows no dates. The ticket never reaches a log or a URL.
