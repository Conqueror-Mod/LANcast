## R12-1 Any local account can plant the face worker, or its ONNX runtime, where the service runs it as SYSTEM

- **Severity:** S1
- **Class:** other (R09-1's class, which #1096 fixed for ffmpeg only)
- **Confidence:** high
- **Where:** `internal/faces/tool.go:105` (`Tool.Path`: the faces folder first, then beside the exe, then `exec.LookPath`); `internal/serverapp/main.go:535-552` (`Dir` and `ModelsDir` are `<data dir>\faces`); `cmd/lancast-faces/onnxlib.go:20` (`runtimePath` loads `onnxruntime.dll` from `-models`)
- **Failure:** As a service, the data directory is `C:\ProgramData\LANcast`. That folder inherits ProgramData's `BUILTIN\Users:(CI)(WD,AD,WEA,WA)`, which lets any local account create files and folders inside it. #1096's own comment in `mediatools/guard_windows.go:113` says exactly this. `Tool.Path` looks for `lancast-faces.exe` in `<data dir>\faces` **before** the copy beside `LANcast.exe` in Program Files. So an unprivileged local user, or anything running as them, creates `C:\ProgramData\LANcast\faces\lancast-faces.exe`. The next time the service asks the worker anything, it runs that file as LocalSystem. `GET` on the faces and semantic status routes calls `Capabilities` (`internal/api/faces.go:29`, `semantic.go:37`), which starts the worker with `capabilities`, and a face or semantic pass runs `detect` or `embed`. The same applies to `onnxruntime.dll` where the worker is installed but the runtime has not been downloaded yet: the real worker, running as SYSTEM, loads whatever DLL is at `<data dir>\faces\onnxruntime.dll`. The third fallback, `exec.LookPath`, searches the service's PATH, which is R09-1's first case again.
- **Evidence:** on the owner's machine (read-only):
  ```
  > icacls C:\ProgramData\LANcast\faces
  NT AUTHORITY\SYSTEM:(I)(OI)(CI)(F)
  BUILTIN\Administrators:(I)(OI)(CI)(F)
  CREATOR OWNER:(I)(OI)(CI)(IO)(F)
  BUILTIN\Users:(I)(OI)(CI)(RX)
  BUILTIN\Users:(I)(CI)(WD,AD,WEA,WA)
  ```
  The faces folder holds the models and `onnxruntime.dll` but no `lancast-faces.exe`, and `C:\Program Files\LANcast\lancast-faces.exe` exists. So a planted `faces\lancast-faces.exe` would win over the installed one today. Files already in the folder are safe: the write grant is container-inherit only, so it does not reach existing files. The attack is to create a file that is missing, which is the normal state for the worker.
- **Fix sketch:** Look for the worker beside the executable only, and drop the faces-folder and PATH lookups for the service. Give `<data dir>\faces` the same protected DACL that `mediatools.Protect` gives the tools folder, and run the #1096 guard over the worker and `onnxruntime.dll` before every start. Better still, protect `C:\ProgramData\LANcast` as a whole once at install, because any future "look in the data dir" lookup has the same hole.
- **Verdict:** CONFIRMED. Tried to disprove: (a) is the data dir really ProgramData for the service? `service.go:51` builds it from `%ProgramData%`. (b) Does the ACL let a non-admin create a file there? Yes, `(CI)(WD,AD)` on the folder, shown above. (c) Is the faces folder checked first? Yes, `tool.go` checks `t.Dir` before `os.Executable()`'s folder, and the comment says so on purpose. (d) Is the worker run as the service? It is a child process of the service, with no token change. Nothing in the chain checks the file's owner. Not run end to end, because that means writing into ProgramData on the owner's machine.
- **Triage:** Fixed and merged in #1126.

## R12-2 The page can point a console at any DLL on any path, including a network share, and the window loads it

- **Severity:** S2 (triage may want S1: it turns script in the page into native code in the desktop app)
- **Class:** other
- **Confidence:** high
- **Where:** `cmd/lancast/retro_windows.go:143` (`setCoreOverride`, bound as `lancastRetroSetCore` at `:662`); `internal/retro/cores/cores.go:198` (`Resolve` takes any override that `os.Stat` finds); `internal/retro/libretro/dll_windows.go:181` (`syscall.LoadDLL`)
- **Failure:** The header of `retro_windows.go` states the boundary: *"A compromised page can at most play a game it can already see, with a core this machine already has."* `lancastRetroSetCore(platform, path)` is callable by any script in the window. It checks only that the path is absolute, ends in `.dll` and exists. `filepath.IsAbs` is true for a UNC path, and `os.Stat` resolves `\\host\share\x.dll` over SMB, or over the WebDAV redirector with `\\host@SSL\share\x.dll` across the internet. The next `lancastRetroOpen` for that console calls `LoadLibrary` on it, and `DllMain` runs before `Open` gets to check that it is a core. So script in the page, from an XSS anywhere in the client or from a server the person connected to that is not their own, runs native code as the desktop user. `internal/webview2/webview.go:207` (`msgcb`) does not check the message's origin either, so the binding answers whatever page is loaded.
- **Evidence:** `setCoreOverride` validation, in full: `!strings.EqualFold(filepath.Ext(path), ".dll") || !filepath.IsAbs(path)`, then `os.Stat(path)`. The override is written to `cores.json` and read back by `cores.Resolve`, which again only stats it. The one legitimate caller is `RetroCoreSettings.tsx:38`, a text field the person types into.
- **Fix sketch:** Take the path out of the page's hands. Choose the file with a native open-file dialog run by the binding, so the page asks for a choice and never supplies a path. Refuse UNC and device paths (`\\`, `\\?\`) in `Resolve` whatever the source. Have `libretro.Open` load with `LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR|LOAD_LIBRARY_SEARCH_SYSTEM32` so a core's own dependencies are not found on PATH.
- **Verdict:** CONFIRMED on the mechanism; the precondition is attacker script in the page. Tried to disprove: the binding is registered unconditionally in `bindings()`; there is no origin check in `msgcb`; `Resolve` is given `coreOverrides()` directly. The severity rests on how likely a hostile page is. Wave 1 fixed the known XSS-shaped paths (R02-1), and the window pins the server's key, so today this needs a hostile server or a new XSS. That is why it is S2 and not S1.
- **Triage:** Fixed and merged in #1142.

## R12-3 A game whose icon has an oversized header size crashes the desktop app every time the Games screen draws it

- **Severity:** S1 (the window crashes; the trigger is a malformed icon in an installed game)
- **Class:** C3
- **Confidence:** high
- **Where:** `internal/games/icon.go:204` (`pix := d[hdr:]`, with `hdr` read from the file at `:195`); reached from `cmd/lancast/games.go:148` (`lancastGameArt`, kind `icon`)
- **Failure:** `decodeDIB` checks that the bitmap header claims at least 40 bytes, and never that it fits the data. An icon entry, in an `.ico` or in an executable's `RT_ICON` resource, whose `biSize` is larger than the entry slices out of range and panics. The binding runs on the window's UI thread with no `recover`, so the panic ends the desktop app's process, window and tray together. The server is a separate process and keeps running. The Games screen fetches the icon through a query (`web/src/lib/games.ts:181`) the first time it shows the game in each run of the app, so the app crashes again every time the person opens Games, until the game is uninstalled or games are switched off.
- **Evidence:** scratch test, run and deleted:
  ```go
  func TestR12DIBHeaderPastEnd(t *testing.T) {
  	d := make([]byte, 40)
  	binary.LittleEndian.PutUint32(d[0:], 1000) // header size larger than the image
  	binary.LittleEndian.PutUint32(d[4:], 16)
  	binary.LittleEndian.PutUint32(d[8:], 32)
  	binary.LittleEndian.PutUint16(d[14:], 32)
  	defer func() {
  		if r := recover(); r != nil {
  			t.Fatalf("decodeDIB panicked: %v", r)
  		}
  	}()
  	_, _ = decodeDIB(d)
  }
  ```
  ```
  --- FAIL: TestR12DIBHeaderPastEnd (0.00s)
      zz_r12_proof_test.go:16: decodeDIB panicked: runtime error: slice bounds out of range [1000:40]
  ```
- **Fix sketch:** Refuse `hdr > len(d)` in `decodeDIB`, add a fuzz target over `IconPNG`'s ICO and PE paths (the PE resource walk has the same shape), and wrap the window's binding dispatch in a `recover` that turns a panic into a rejected promise.
- **Verdict:** CONFIRMED. Tried to disprove: `icoBest` checks that the entry fits the file but not the DIB inside it; `exeIcon` hands the `RT_ICON` bytes to the same decoder; PNG-in-ICO entries take another branch, so only DIB icons trigger it. No `recover` on the path: `callbinding` calls `v.Call(args)` directly. The input is uncommon, which is why the risk is a crash loop for the few who meet it, not a common crash.
- **Triage:** Fixed and merged in #1128.

## R12-4 When the saved game cannot be fetched, the game plays on blank and its first save replaces the one on the server

- **Severity:** S1 (data loss)
- **Class:** C16
- **Confidence:** high
- **Where:** `internal/retro/host/session.go` `loadSRAM` (the `err != nil` branch) with `maybeFlushSRAM`; `internal/retro/saves/saves.go` `Write` (rotates `cur` to `prev` unconditionally); `internal/api/romsaves.go:245` (`putSave` accepts any upload)
- **Failure:** `loadSRAM` calls `LoadSRAM`. On an error, such as the 30-second timeout, the server restarting for an update, or Wi-Fi dropping, it tells the page "Your saved game could not be fetched" and plays on with blank save RAM. Its comment says "the save on the server is untouched until this one is newer", but nothing enforces that. The checksum baseline is taken from the blank RAM, so the first time the game writes its save RAM it is uploaded within five seconds, or at once on pause or close. Many cartridges format blank save RAM at boot, and any in-game save writes it. The server's `Write` renames the real save to `.prev` and stores the blank one. A second change rotates again, and the real save is gone. The same path with `LoadState("auto")` is quieter: a failed fetch is ignored without a word, the game starts from the beginning, and closing it writes a new `auto` over the Continue point.
- **Evidence:** `loadSRAM`: `if err != nil { s.cfg.OnEvent(... "Your saved game could not be fetched." ...) } else if len(data) > 0 { copy(mem, data) }; s.sramSum = crc32.ChecksumIEEE(mem)`. `maybeFlushSRAM` uploads whenever the CRC differs from `sramSum`. `saves.Files.Write` keeps exactly one previous generation. `putSave` has no precondition (no `If-Match`, no "based on" hash).
- **Fix sketch:** When the save could not be fetched, do not upload save RAM for that session: hold it locally, and offer to send it once a fetch succeeds, or refuse to start the game. Better, make the upload conditional: the client sends the SHA-256 of the save it loaded (it has the bytes), and `putSave` answers 409 when the current file's hash differs. Treat a failed `auto` fetch the same way: no `auto` written on stop unless the fetch said 404.
- **Verdict:** CONFIRMED by reading; not run against a server. Tried to disprove: is there a guard in `remote.StoreSRAM` or `putSave`? No, both send and store unconditionally. Does the session skip flushing after a load error? No, `sramSum` is set either way. Does the page stop the game on that error event? `retro_windows.go` only forwards the event. Recoverable after one rotation (the `.prev` file), and lost after two.
- **Triage:** Fixed and merged in #1123.

## R12-5 A repeated form key gets past the RetroAchievements allow-list and the softcore rule

- **Severity:** S3
- **Class:** other
- **Confidence:** high
- **Where:** `internal/retro/ra/connect.go` (`Check`: `v.Get("r")`, `v.Get("h")`, `v.Get("u")` read the first value; `WithToken` forwards every value)
- **Failure:** `Check` decides on the first value of each key, and the request is forwarded with all of them. RetroAchievements' `dorequest.php` reads form fields the PHP way, where the last value wins. So the player, or any script holding the person's session, can send `r=ping&r=submitlbentry` (leaderboard entries, kept off until LANcast is approved) or `h=0&h=1` (a hardcore unlock, which ADR 0112 §5 forbids before approval) under the person's sealed token. The account is the person's own, so nobody else's data is at stake. What is at stake is LANcast's standing with RetroAchievements, which the softcore-only rule exists to protect.
- **Evidence:** scratch test, run and deleted:
  ```go
  for _, form := range []string{
  	"r=ping&r=submitlbentry&u=me&i=1&s=999",
  	"r=awardachievement&u=me&a=5&h=0&h=1",
  } {
  	v, kind, err := Check(form, "me")
  	if err != nil { t.Logf("refused %q: %v", form, err); continue }
  	t.Errorf("accepted %q as %q; forwarded as %q", form, kind, WithToken(v, "TOKEN"))
  }
  ```
  ```
  accepted "r=ping&r=submitlbentry&u=me&i=1&s=999" as "ping"; forwarded as "i=1&r=ping&r=submitlbentry&s=999&t=TOKEN&u=me"
  accepted "r=awardachievement&u=me&a=5&h=0&h=1" as "awardachievement"; forwarded as "a=5&h=0&h=1&r=awardachievement&t=TOKEN&u=me"
  ```
- **Fix sketch:** In `Check`, refuse any key that appears more than once (`len(v[k]) > 1`), or rebuild the forwarded form from single values only.
- **Verdict:** CONFIRMED that `Check` accepts the request and that `raplay.go:153` forwards `WithToken(form, …)` unchanged. The last-value reading is PHP's documented behaviour for `$_POST`. It was not sent to RetroAchievements.
- **Triage:** Before 1.0, wave G (see [triage.md](../triage.md)).

## R12-6 The desktop keeps playing an old copy of a game after its file is replaced by one of the same size

- **Severity:** S3
- **Class:** other
- **Confidence:** high
- **Where:** `internal/retro/remote/remote.go` `Download` (`if st.Size() == f.SizeBytes { continue }`); the cache key is `cmd/lancast/retro_windows.go:311` (`gameCache`: origin and item id)
- **Failure:** A cached file counts as current if its size matches the listing. ROM sizes are mostly powers of two, so replacing a bad dump with a good one, or a translation patch with the original, keeps the same size and the same item id, because the path is unchanged. The desktop then plays the old bytes for ever. RetroAchievements hashes the local file, so the client identifies the old game while the server's identify worker describes the new one. A save state written against one does not load into the other.
- **Evidence:** the only check is the size comparison above. The server's file listing carries no hash or modification time (`File{Name, SizeBytes, Present}`).
- **Fix sketch:** Have `GET /api/items/{id}/files` include each file's modification time or SHA-256 (the identify worker already hashes the entry file), and re-fetch when it changes. This is an API change, so `docs/api.md` and `openapi.json` change with it.
- **Verdict:** CONFIRMED by reading. Tried to disprove: no other invalidation of `retro/games/<origin>/<id>` exists in the client; deleting the item and rescanning gives a new id and would clear it, which a person would not think to do.
- **Triage:** After 1.0: needs an API change (a file hash in the listing).

## Checked and clean

- **Core DLLs, where from and who can write there.** The default cores are installed under the client's per-user data directory (`os.UserConfigDir()`, so `%APPDATA%\LANcast\client\retro\cores`), which only the desktop user can write. The process that loads them runs as that same user, so no privilege boundary is crossed. Install: pinned stable archive URL, archive SHA-256 checked before it is opened, each DLL checked against its own SHA-256 and size, written to a temporary file and renamed, partial installs count as absent (`Installed` hashes). `Resolve` checks only the size at play time, which is fine for a same-user directory. The override path is R12-2.
- **`lancast-cheevos.dll`.** Loaded by full path from beside the executable (`DLLPath`), which is Program Files in an install and admin-only to write. It refuses a DLL without the shim's exports or with the wrong interface version. It is shipped by the updater (`update/download.go:41`), not fetched separately.
- **RetroAchievements credentials.** The desktop never holds them: rcheevos signs in with the placeholder `lancast`/`lancast`, and the server swaps in the person's username and adds their sealed token (`ra.Check`, `WithToken`) before forwarding to the fixed base URL. `Check` refuses a password field and a different username. The token is redacted from the answer (`RedactToken`). A password is sent once, to RetroAchievements, at connect; the API side is R03/R04's and was found clean there.
- **libretro binding.** Strings, the game's bytes and variable values that a core may keep are allocated on the process heap, not in Go memory, and freed at `Close`. Every array a core hands over is bounded (`SetVariables` 4,096, input descriptors 1,024, memory descriptors 1,024, C strings 1 MiB, audio batch 2^20 frames, frame pitch below 1 MiB and height below 65,536). The struct mirrors match the header's 64-bit layout, including `retro_hw_render_callback`. Callbacks are created once and stay valid because the DLL is never unloaded. Every session runs on one permanent locked OS thread (`onCoreThread`), which is what Mupen64Plus-Next's fiber needs. A frame whose `width*bpp` exceeds `pitch` would panic in `ToBGRA`, but only a broken core sends one, and a core is native code that can crash the process anyway, so it is not entered.
- **Save state written while a game runs.** `serialize` runs on the core thread between frames, so the bytes are consistent. The upload is a copy, sent on a goroutine. `finish` waits up to 30 seconds for uploads before unloading. A state is refused before reaching the core when its core name or version differs (`stateMismatch`).
- **Ticketed remote access (client side).** The ticket goes in an `Authorization` header and never in a URL. The pin is required for https, and none is allowed for http. File names from the server are re-checked before becoming a path (`LocalPath` refuses `\`, `:`, absolute paths and `..`). Saves are capped at 64 MiB on read. Whose save a ticket reaches is enforced server-side and was found clean in R03.
- **Server save files.** The folder is a hash of the account id, the slot matches `^(sram|auto|state-[0-9])$`, the size is capped before rename, and the file is synced before rename. R03-5 (row written after the file) is already recorded.
- **Launchers (Steam, Epic, GOG, EA, Battle.net, Xbox).** No string from the page reaches a process. The page passes an id, the client rescans, and `LaunchURI` validates per source: Steam digits, Epic hex, Xbox AUMID regex, GOG digits plus a quote-free path. Executables (`ExecutableTarget`) must be absolute `.exe` files inside the recorded install folder. The check is lexical, but the registry and manifest data it guards are written by installers that already run code, so following links would not change who can attack it.
- **MilkDrop and EEL (C3).** Upload and delete are `adminOnly`, and the body is capped by `MaxBytesReader`. The server never interprets EEL: `eel.Check` is a validator with bounds on size (64 KiB), expression depth (128, counted on every recursive descent: parenthesis, unary and assignment) and loop nesting (4), plus a literal `loop()` count of at most 1,048,576. The interpreter is eel-wasm in the viewer's browser, capped by eel-wasm itself. ADR 0091 records nested-loop slowness in the tab as an accepted risk for admin-chosen presets. Fuzz: `eel.FuzzCheck` covers the checker against its own limits and `milkdrop/fuzz_test.go` covers preset parsing. Since there is no server-side interpreter, there is nothing else to fuzz. Shader conversion runs in wazero with a 32 MiB memory limit, a deadline, close-on-cancel, 1 MiB of output and one conversion at a time. Preset ids match a pattern and are held to the folder by `path`.
- **ROM and disc parsers (C3).** Cue sheets and m3u lists are read up to 64 KiB. The PARAM.SFO, directory and SYSTEM.CNF sizes are capped at 64 KiB (`maxCNF`), and every SFO offset is checked against the buffer. `cueSerial` takes only the base name of a track. **R03's passing note on `read.go:488` does not hold:** `M3UDiscs` already drops any disc outside the game's folder before `GameFiles` sees it, so `cueFiles` is never called on an outside `.cue`.
- **Locked fields (C4).** The identify worker reads `LockedFields` before each write, skips a `locked` match state, and leaves locked artwork alone.
- **Downloads (C17, C15).** No secret appears in a download URL or log. Response bodies are closed, and stall timers are stopped by `defer`. Thumbnails and listings are capped at 16 MiB with a 60-second client timeout.
- **C1, C2, C5–C8, C11–C14, C18:** do not apply to this slice's code. It has no handlers, no store, no React and no dates shown to a person.
